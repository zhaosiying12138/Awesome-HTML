先给出全书唯一需要背住的一句话

Warp Specialization 不是“让几个 warp 跑不同代码”这么简单；它是把一个原本由同一组 warp 顺序推进的循环，变换成多个长期并发的角色循环，并为跨角色的数据存储、所有权、完成事件、内存可见性、控制派遣和寄存器额度补齐协议。

如果你来自 LLVM，可以先用一个不完全但很有用的类比建立方向：

  • PartitionScheduling 像在结构化 SSA 图上做一轮面向硬件角色的 graph partition；
  • Shared/TMEM ARef 像把“跨并发域的 SSA 边”重新物化成显式 memory object、ownership edge 和同步状态；
  • TMEM async token 更接近某个片上对象的 MemorySSA/mod-ref 次序边，而不是 payload；
  • ttg.warp_specialize 是一个 concurrent-region ABI，不是普通函数调用，也不是顺序 region；
  • LLVM persistent switch-loop 则把这个 ABI 变成一组常驻 worker warps 的任务派遣状态机。

这个类比能帮你进入源码，但不能替代 GPU 协议：MemorySSA 不会自动替你产生 mbarrier，region isolation 也不会自动满足 TCGen05 的 inter-thread ordering。

这里的“ABI”只是一种教学简称，意为 compiler 内部各 passes 共同遵守的 region contract；它不表示 ttg.warp_specialize 对外承诺跨版本二进制或 IR 兼容性。

0.2 六道证据闸门

任何一个自动 WS case 都要依次通过：

  1. 前端是否表达了请求；
  2. loop 是否满足当前 eligibility；
  3. graph 是否真的得到多个 partitions；
  4. 跨角色 storage/ownership、barrier、warpgroup 和寄存器协议是否物化；
  5. LLVM/PTX 是否形成目标控制流和指令结构；
  6. assembler/disassembler 是否接受产物。

即便六道都通过，也只说明编译器构造了目标结构。若没有同 target 的设备 launch、数值比较、死锁压力测试与 profiling，仍不能声称运行正确、无死锁或更快。

  • 解释为什么 compile-only PASS 不是 runtime correctness 或 speedup；
  • 在阅读后文时始终追问：这一层究竟证明了什么？

第一部分　先建立正确的 GPU 心智模型

1. 为什么普通 SIMT 循环会需要角色分工

先暂时忘掉 Triton pass 名字。考虑一个最简 GEMM K-loop：

for k in range(0, K, BLOCK_K):
    a = load_A_tile(k)
    b = load_B_tile(k)
    acc = dot(a, b, acc)
store(acc)

在未特化的版本中，CTA 内每个 warp 运行同一静态程序，只因 layout 不同而处理不同数据切片。即便 compiler 做了 ordinary software pipelining，让第 k+1 次 load 与第 k 次 MMA 交叠，load、MMA 和 epilogue 的指令仍要从同一组 warps 的 instruction streams 中发出。

这会遇到三类结构性摩擦：

  1. 指令流异质。 TMA issue 很短，MMA issue 也可能只需 elected thread，而 epilogue 是大量 vector/register work。把它们混在同一 warp 流里，会让本来可独立推进的硬件管线相互穿插。
  2. 寄存器需求异质。 搬运角色可能只需很少寄存器，epilogue/reader 却需要大量普通寄存器；统一上限会迫使每个 warp 为最宽角色付费。
  3. 等待原因异质。 一处在等 TMA transaction bytes，一处在等 Tensor Core completion，一处在等 TMEM load 写回寄存器。把它们都称为“stall”看不出该让谁继续前进。

Warp specialization 的基本想法是把循环中的工作分给不同角色：

producer role   : 提前发起 global → shared 的 TMA
compute role    : 消费 shared tile，发起 TCGen05 MMA
reader/epilogue : 在 MMA 完成后从 TMEM 读取并做 vector work/store

角色一旦分开，GPU warp scheduler 就能在某个角色等待时发射另一个角色。但这句话只描述机会，还没有描述正确性。分开后立刻出现四个新问题：

  • producer 写的 tile 放在哪里，consumer 怎样定位同一个 slot？
  • producer 什么时候可以覆盖这个 slot？
  • MMA 什么时候真的完成，另一 warp 何时可以发起 TMEM load？
  • worker warps 怎样被派遣、回收，并与 default warps 一起退出 kernel？

因此，真正的 WS 变换对象不是几条 op，而是一个协议系统。

第一个常见误解：角色并不等于硬件要求整 warp 都做同一种事

TMA 和 tcgen05.mma 都可能由 elected thread 发起。Triton 把它们放进独立、低寄存器的 worker partition，是调度与资源生命周期策略；不能反推成“硬件规定必须牺牲一个完整 warp 才能发 TMA/MMA”。

1.1 从“同一程序、不同数据”到“不同程序、协作数据”

普通 SIMT 的主语是：同一指令流作用于不同 lanes/warps 的数据切片。WS 增加了另一个维度：不同 warp partitions 长期执行不同指令流，却共同完成一个 CTA tile。

这意味着编译器必须同时维护两种等价性：

  • 算法语义仍等价于原循环；
  • 角色间通信与同步满足硬件 memory/execution model。

第一种等价性主要由 SSA、控制流、loop-carried state 和 partition cloning 约束；第二种等价性由 Shared/TMEM storage、mbarrier、proxy fence、TCGen05 ordering、named/cluster barrier 与 setmaxnreg 约束。只证明其中一种都不够。

1.2 一个贯穿全书的最小问题

后文一直追踪同一个问题：

descriptor/TMA 产生 A/B shared tile
            ↓
TCGen05 MMA 修改同一块 TMEM accumulator
            ↓
另一角色把 accumulator 从 TMEM 读进 registers 并写回 global

每一层都只是在回答这条链的一个部分：

层次 回答的问题

2. 两条正交轴：SWP 切时间，WS 切角色

这是全书最重要的抽象。很多源码难点都来自把这两条轴混成了一条。

2.1 Software pipelining 在时间轴上做什么

Software pipelining（SWP）让同一角色的不同 loop iterations 交叠。同步版本是：

iteration k:   load(k) → mma(k)
iteration k+1:                    load(k+1) → mma(k+1)

三 stage 的概念结果是：

prologue      : load(0), load(1)
steady state  : load(k+2)  与  mma(k) 同时在途
epilogue      : mma(last-1), mma(last)

Triton 用 CoarseSchedule 给 op 分配 (stage, cluster)：

  • stage 表示跨 iteration 的时间偏移；
  • cluster 保留同一 stage 内不可交换的依赖次序。

之后 loop pipeliner 扩展 iter args、旋转 buffer index、产生 prologue/steady/epilogue。这里还没有把 load 与 MMA 交给不同 warps。

2.2 Warp specialization 在角色轴上做什么

WS 让同一时刻的不同硬件角色由不同 warp partitions 执行：

维度 SWP WS
切分对象 loop iteration/stage operation/dataflow role
主要 IR 状态 (stage, cluster)、rotating iter args partition attrs、ARef、并发 regions
主要收益机会 隐藏相邻 iteration 的 latency 让异构 hardware pipelines 由独立指令流持续推进
新增 correctness 压力 prologue/epilogue、loop-carried dependency、buffer phase 跨角色 storage、ownership、completion、ordering、dispatch、register ownership
是否自动包含另一者 否 否

可以把最终计划想成一个二维网格：横轴是 iteration time，纵轴是 role。SWP 决定同一行怎样沿横轴展开；WS 决定一列中的工作由哪些 warps 执行。当前实现让两者共享 schedule 信息，所以拆分之后必须重新投影和整理每个 role 的 schedule。

2.3 为什么分区后还要再次调度

第一次 ScheduleLoops 面对完整 loop，可能把 descriptor load 安排到较早 stage，把 MMA 和 reader 放到后面。PartitionLoops 之后，每个 worker 只保留原图的一部分：

  • load role 可能只剩 TMA 与 barrier；
  • MMA role 可能只剩 get-slot 与 tc_gen5_mma；
  • reader role 可能只剩 TMEM load 与 epilogue。

原 schedule 对每个 role 只是投影，不是一份可以原样复制的完整 schedule。若某个 role 已无可重叠的 latency op，ScheduleLoops.cpp::getInitialSchedule 会把它收缩为单 stage，避免为毫无收益的“假流水”延长 live ranges；这不会撤销角色并发。

2.4 tt.latency 与 tt.self_latency 不同

属性 问题 结果
tt.latency 这个 op 对下游 def-use longest path 至少贡献多少 stage distance？ 决定依赖链在 iteration 时间上的拉开距离
tt.self_latency 异步 MMA 最早在哪个后续 stage 被观察、其资源何时可复用？ LowerLoops::lowerMMA 据此建立 completion mbarrier、phase/index 与 wait

self_latency=0 只表示通用 loop pipeliner 不再为这条 MMA 建立一条同角色、跨 iteration的 self wait。它不表示 TCGen05 硬件延迟为零，也不取消跨 partition ARef、TMEM ownership 或 ISA ordering。

Fully-TMA、mixed TMA+ordinary-load 与 accumulator RMW 会走不同分支：

  • fully-TMA 的 operand chains 可由 producer role 供给，MMA role 内可能没有值得重叠的普通 load，因此 self-latency 可降为 0；
  • mixed case 中 ordinary load 仍留在 compute/MMA role，通过 cp.async 双缓冲与前一次 MMA 交叠，所以保留非零 self-latency 和 MMA wait；
  • accumulator 若经过 tmem_load → ordinary arithmetic → tmem_store → next MMA 的 RMW recurrence，角色分离也不能破坏这条真实依赖，tt.latency 必须被清除或保守调整。

用一句话防止混淆

stage/phase 回答“第几轮 buffer”；partition/worker state 回答“哪组 warps”；二者会合作，但绝不是同一种状态。

3. Blackwell 的三条异步管线：TMA、TCGen05 与 TMEM

  • 解释 elected-thread issue 为什么不等于窄数据通路；
  • 把 MMA issue、MMA completion、跨线程 ordering、TMEM load completion 分成四个事件；
  • 区分 TMEM allocation permit、TMEM columns 与跨角色 owner。

3.1 TMA：发起者很窄，传输很宽

Tensor Memory Accelerator 使用 tensor descriptor 携带 base、shape、stride 与 tile 信息。一个 elected thread 可以发起 global→shared bulk tensor copy，硬件却异步搬运整个 tile，并把 transaction bytes 计入 shared-memory mbarrier。

所以理想 producer role 的特征是：

  • 指令流短；
  • 活跃标量少；
  • 寄存器预算低；
  • 能提前推进下一 stage；
  • 不承担消费 tile 的向量计算。

当前 PartitionScheduling 把 DescriptorLoadLikeOpInterface 的结果识别为 data root。它不是见到任意 tt.load 就产生 TMA role；descriptor/TMA 是当前自动路径的重要资格与角色信号。

3.2 TMEM：accumulator 不必住在普通寄存器里

可以把 Tensor Memory 想成 CTA 所有、Tensor Core 专用的二维片上空间：一维覆盖 128 lanes，另一维是动态分配的 columns。tcgen05.alloc/dealloc 管理 columns 生命周期；tcgen05.mma 把 accumulator 写到 TMEM；tcgen05.ld/st 在 TMEM 与普通 registers 之间搬运。

务必区分三个“所有权”：

  1. allocation permit：谁可以继续申请 TMEM allocation；relinquish_alloc_permit 尽早归还它；
  2. allocated columns：真正的 TMEM 空间，直到 dealloc 才释放；
  3. cross-role access ownership：MMA role 与 reader role 何时可以访问同一 allocation，由 TMEM ARef/同步协议管理。

因此 relinquish_alloc_permit 不是 dealloc 的另一种拼写，也不是把 accumulator 交给 epilogue。

3.3 TCGen05：issue 与 execute/complete 解耦

tcgen05 是第五代 Tensor Core 与 Tensor Memory 周围的一族指令，而不是一条“Blackwell MMA”的简称。后文会同时出现：

层次 典型名字
Triton TTGIR ttng.tc_gen5_mma、ttng.tc_gen5_commit、TMEM ops
PTX tcgen05.mma、commit、fence、ld/st/wait、alloc/dealloc
SASS UTCHMMA、LDTM、STTM、barrier/register-control 等

这三层属于连续 lowering，但不能按字符串一一映射。教材判断 compiler contract 时以 TTGIR/PTX 为主，SASS 只作反向导航。

一个 elected thread 发出 tcgen05.mma 后，Tensor Core 异步执行，结果落在 TMEM。于是：

MMA issued
  ≠ MMA has completed
  ≠ another thread's following TCGen05 access is correctly ordered
  ≠ tcgen05.ld has finished writing ordinary registers

这四个事件分别需要不同机制：

  • tcgen05.mma：发起；
  • tcgen05.commit + mbarrier wait：跟踪/观察此前 MMA completion；
  • tcgen05.fence::after_thread_sync：把同步点之前的 TCGen05 pipeline 与后续另一线程的 TCGen05 access 排序；
  • tcgen05.wait::ld：等 TMEM→register load 完成，之后寄存器才可消费。

名字陷阱

PTX 的 tcgen05.mma.ws 中，ws 表示 weight stationary 的卷积 MMA 变体，不表示 warp specialization。Triton WS 是 compiler 把 operations/data 分派给不同 warp partitions 的变换，不由某个 .ws opcode 后缀开启。

3.4 理想的最短生命周期

把 allocation、MMA completion 与 reader 顺序压成一条示意：

one warp       : tcgen05.alloc
CTA threads    : address hand-off / synchronization
one warp       : tcgen05.relinquish_alloc_permit
elected thread : tcgen05.mma ... [d-tmem]
elected thread : tcgen05.commit ... [full_mbarrier]
reader role    : mbarrier.try_wait ...
reader role    : tcgen05.fence::after_thread_sync
reader warp    : tcgen05.ld ... [d-tmem]
reader warp    : tcgen05.wait::ld
one warp       : tcgen05.dealloc

这是 ISA 因果关系的教学序列，不是冻结 Triton artifact 的逐条抄录。后文会看到：冻结产物有 MMA、commit、mbarrier wait、CTA barrier、TMEM load 与 wait::ld，却没有专用 after_thread_sync fence。这是一项需要单独资格化的 gap。

4. 不要再说“等一个 barrier”：六种关系、多类机制

技术文章常把任何等待都简写成“同步”。在 WS 中，这会直接掩盖错误。先把关系分清：

关系 它回答什么 一个代表机制

4.2 ARef 的“空/满”不是 TMA 的“完成”同义词

ARef 把一个可复用 slot 的生命周期写成：

producer waits empty credit
→ producer fills payload
→ producer publishes full
→ consumer waits full
→ consumer borrows/uses payload
→ consumer returns empty credit

若 producer 是 TMA，硬件 completion 可以直接参与 full side；若 consumer 最后是 TCGen05 MMA，release 又可能挂到 commit 上。但 ARef 的核心语义是谁可以复用 slot，不是给所有异步硬件操作定义一种统一 completion。

4.3 barrier 已建立 happens-before，为什么还可能需要 proxy fence

Shared memory 可能由 generic proxy 与 async proxy 访问。即使 producer/consumer 通过 mbarrier 建立了控制上的 happens-before，也不自动意味着两个 proxy 的访问已经满足可见性规则。反之，proxy fence 只解决可见性，不让两个角色在某个点会合，也不等待 TMA/MMA 完成。

所以 LowerAref、ProxyFenceInsertion 和后端 barrier lowering 分工不同：

  • ARef 建立 storage ownership lifetime；
  • barrier/completion ops 表达异步工作何时完成；
  • proxy analysis 修复不同 memory proxies 之间的可见性；
  • scheduler/reorder pass 必须保住 first/last use 边界，不能把 arrive 越过真实读取。

4.4 TCGen05 的 qualification gap

NVIDIA PTX ISA 9.3 的 canonical MMA→TMEM-load pattern仍明确给出：

tcgen05.mma
tcgen05.commit.mbarrier::arrive::one
mbarrier.try_wait ...
tcgen05.fence::after_thread_sync
tcgen05.ld
tcgen05.wait::ld

冻结 Triton 源码和 exact-SM103 artifact 能找到：

  • LowerAref 为 TC5MMA 产生 commit，并在 consumer 侧产生 wait；
  • MMAv5.cpp 发出 tcgen05.commit...mbarrier::arrive；
  • TensorMemoryToLLVM.cpp 发出 tcgen05.ld，随后立即 tcgen05.wait::ld；
  • 但冻结 dialect、lowering、tests 与该 artifact 中均未找到专用 tcgen05.fence::after_thread_sync。

artifact 中间出现的 CTA bar.sync/barrier.sync，以及别处的 FENCE.VIEW.ASYNC.S/T，都不能只凭名字相似就代替这条 PTX 指令。

精确结论：这是 ISA-contract / implementation / coverage qualification gap

compile、ptxas 与反汇编成功说明工具链接受了结果；它们没有证明跨 role 的 TCGen05 canonical ordering 已经满足。没有 exact-SM103 runtime 与更深入的 NVIDIA 保证，本教材不直接断言常见 kernel 必然错误；但也绝不把缺失 fence 写成已经实现。

4.5 setmaxnreg 为什么也属于协议

PTX 9.3 规定：

  • .dec 把当前每线程最大寄存器数降低到立即数并把尾部寄存器归还 CTA pool；
  • .inc 请求把上限提高到立即数，资源不足时会阻塞；新获得寄存器内容未定义；
  • 立即数必须是 24–256 且为 8 的倍数；
  • 一个物理 warpgroup 的所有 warps 必须执行相同指令；
  • 连续两次 setmaxnreg 之间，warpgroup 必须显式同步；
  • .sync 是 warp 内参与约束，.aligned 是 warpgroup 一致执行约束。

因此它不是一条“修改编译器属性”的伪指令，而是运行时 CTA register pool 的所有权转移。后文会看到 inactive workers 如何先降到低额度，active role 又如何按目标值增或减。

第二部分　从一个 Python 请求到角色图

5. warp_specialize=True 是请求，不是结果

Python API 只是把用户意图送进 compiler：

for k in tl.range(0, K, BLOCK_K,
                  num_stages=3,
                  warp_specialize=True):
    a = a_desc.load([m, k])
    b = b_desc.load([n, k])
    acc = tl.dot(a, b.T, acc)

python/triton/language/core.py::range 保存字段，CodeGenerator.visit_For 把它编码成 scf.for 上的 tt.warp_specialize attribute。到这一步，compiler 还没有决定：

  • 有几个 partitions；
  • 哪些 op 属于哪个 partition；
  • 是否需要 Shared/TMEM ARef；
  • 是否真的产生 ttg.warp_specialize；
  • 是否产生额外 workers 或 setmaxnreg。

5.1 用三个几乎相同的 GEMM 看清资格边界

case A/B 来源 marker ordinary SWP 当前 autoWS eligibility 可能物化角色
pointer-only 两侧 tt.load 有 是 否：无 eligible descriptor memory op 否；safe no-op
canonical TMA 两侧 descriptor/TMA 有 是 是 是，若其余图约束满足

  1. marker 不等于 WS materialization；
  2. 当前门槛不是“两侧必须都是 TMA”，而是存在合格 descriptor memory path，并且分区/通信的其余约束可满足。

5.3 eligibility 为什么要在首次 mutation 前做完

PartitionScheduling::analyze 建图、传播 data roots、执行 merge/propagation，最后用 hasEligibleMemoryOps 确认图中确实出现 descriptor 类 LOAD/STORE。没有合格 memory op 时，它不序列化临时 partition attributes，后续也就没有“半套”通信图要清理。

这是理想 fail-safe：在任何不可逆 mutation 之前退出。它不同于进入 ARef/TMEM-ARef 深处后才撞上 assert。成熟度章节会把 safe no-op、明确 diagnostic、assert/unreachable 与只有 FIXME 的边界分开。

6. 全书脊柱：同一个 GEMM 的七次形态变化

在深入算法前，先把整条链看一遍。现在不要求读懂所有细节，只要知道每层新增了什么。

6.1 形态 0：普通算法语义

for k:
  a = descriptor_load(A, k)
  b = descriptor_load(B, k)
  acc = dot(a, b, acc)
return/store acc

6.2 形态 1：TCGen05/TMEM 化，但仍是一条顺序 SSA 图

在 AutomaticWS 真正消费的层次，MMA 修改 TMEM，SSA result 常是 accumulator dependency/mod-ref token：

scf.for k iter_args(use_d, acc_tok):
  a = descriptor_load(A, k)
  b = descriptor_load(B, k)
  a_s = local_alloc(a)
  b_s = local_alloc(b)
  mma_tok = tc_gen5_mma(a_s, b_s, acc_tmem[acc_tok], use_d)
  acc, load_tok = tmem_load(acc_tmem[mma_tok])
  yield next_use_d, next_token

mma_tok 不是硬件 completion object；它告诉 compiler 对同一 TMEM allocation 的访问顺序。

6.3 形态 2：PartitionScheduling 只标归属，不创建并发

%a = tt.descriptor_load ... {ttg.partition = [2]}
%b = tt.descriptor_load ... {ttg.partition = [2]}
%mma = ttng.tc_gen5_mma ... {ttg.partition = [1]}
%acc, %tok = ttng.tmem_load ... {ttg.partition = [0]}
scf.yield ... {ttg.partition = [0, 1, 2]}

此时仍是一条 scf.for。数字只是本 loop 内的临时角色 ID，不是稳定 ABI。

6.4 形态 3：InsertAref 把跨角色 SSA 边改写成 storage transaction

LOAD role:
  slot, put = aref.put.enter(empty)
  nvws.descriptor_load(..., slot)
  aref.put.exit(... kind=tma_load)

MMA role:
  slot, get = aref.get.enter(full)
  tc_gen5_mma(slot, ...)
  aref.get.exit(... kind=tc5mma)

现在 IR 明确说“producer/consumer 对一个 slot 的借出与归还”，但还不是最终 barrier/PTX。

6.5 形态 4：LowerAref 结算事务

nvws.aref.* 被换成：

  • backing buffers 与 slot subviews；
  • empty/full mbarrier arrays；
  • stage、phase、wait、arrive、expect-tx；
  • direct-to-buffer async TMA；
  • TCGen05 commit 或普通 arrive；
  • 必要的 async proxy fence。

第一段 NVWS epoch 到此消失。

6.6 形态 5：PartitionLoops/LowerWarpGroup 形成正式并发 ABI

ttg.warp_specialize(%captures)
default {
  // control / reader / epilogue according to graph
  ttg.warp_yield
}
partition0(...) num_warps(1) {
  // role loop
  ttg.warp_return
}
partition1(...) num_warps(2) {
  // role loop
  ttg.warp_return
}

这一步不是把几条 op 移到不同 block，而是为每个 role 克隆所需的 loop/control skeleton、induction variable、iter args 与 captures。

6.7 形态 6：物理 warp pool 与 persistent switch

OptimizePartitionWarps 估计逻辑 role 宽度与寄存器请求；AllocateWarpGroups 做 4-warp physical grouping、padding、start IDs 和可行的 actual register budgets；LLVM lowering 再产生：

entry: default warps → old kernel entry
       worker warps  → persistent switch-loop

default at each WS site:
  write captures + per-worker state
  barrier release workers

worker:
  switch(state) → role block → return barrier → switch-loop

kernel return:
  broadcast exit state → all workers return

到这一层，role 并发才有了物理控制流；是否真正产生理想 overlap，仍需 runtime/profiling。

阅读源码时的固定断点

建议始终保存四个 trace 切片：PartitionScheduling 后、nvws-insert-aref 后、nvws-lower-aref 后、nvws-lower-warp-group 后。它们分别回答“分给谁”“如何通信”“通信怎样落地”“并发 ABI 是否形成”。

7. PartitionScheduling：它是 dataflow partitioner，不是模板替换

如果只把它想成“看到 TMA 就分 producer、看到 MMA 就分 consumer”，就解释不了 attention、mixed load、多个 MMA、SFU/correction 与 nested loop。冻结实现的核心更接近：

structured SSA graph
→ 标记 data roots
→ 每个 data node 先独立成 partition
→ 按有序 heuristics 反复 merge
→ 把 index/control 等 non-data 依赖传播到所需 roles
→ 必要时复制 cheap paths
→ 只有存在 eligible descriptor memory partition 才序列化结果

7.1 graph 怎样表示 structured MLIR

buildGraph 为已编码的 scf.for、scf.if 和特定单结果 tt.reduce 建嵌套 nodes：

  • loop 的 lb/ub/step 是 input ports；
  • induction variable 与每个 iter arg 是 value nodes；
  • init/yield 分别连接 iter-arg 的两端，显式形成反馈边；
  • if 的 then/else yields 连接 result 的不同 ports；
  • 普通 op 的 operands/results 形成普通 graph edges；
  • 最后用 MLIR uses 补齐跨 node 边。

这让 loop-carried accumulator token、attention 的 m_i/l_i 和 persistent tile state 不会被拍平成假直线。

“structured control flow”有精确边界

冻结实现不是任意 RegionBranchOpInterface 的通用 partitioner。graph/materialization 明确编码了 scf.for、scf.if 与单结果 reduce；scf.while、任意自定义 region op 或 multi-result reduce 不能由这些正例外推为受支持。

7.2 data roots 与 MemorySSA 类比

初始 data roots 包括：

  • descriptor load-like tile result；
  • TMEM load 的 data/token results；
  • TCGen05 MMA/scaled MMA 的 dependency result；
  • 内部显式标记为 data 的 op。

之后 data property 沿 use edges 传播。index arithmetic、loop bound、pointer offset 初始不是 data；它们随后被复制或传播到真正需要它们的 partitions。

对于 TMEM token，最有用的类比是 MemorySSA：它表示同一 TMEM object 的访问次序与 mod/ref dependency，不是把 accumulator 内容“装进 token”，也不是硬件 completion signal。

7.3 为什么从过度切分开始

每个未分配 data node 先独占一个 partition，算法再问“哪些边必须合并”。这比一次猜终局更容易维护：

graph = build_graph(loop)
mark_and_propagate_data_roots(graph)
assign_each_data_node_a_fresh_partition()

while edge_rule_can_merge(graph):
    merge(source_partition, destination_partition)

while partition_pair_rule_can_merge(graph):
    merge(partition_a, partition_b)

propagate_non_data_dependencies()
assign_ids()
clone_cheap_paths_when_profitable()

if has_eligible_descriptor_load_or_store(graph):
    serialize_temporary_attributes()

Policy 与 communication materialization 因而分离：scheduler 只决定“谁与谁同角色”，ARef passes 再决定 crossing edges 用什么 storage/protocol。

7.4 flags 与简化 cost model

冻结 partition flags 是 LOAD | STORE | MMA | TMEM | SFU | VIEW | MANUAL。分类和 cost 都有意保持简单：

MMAv5 cost  ≈ M × N × K / 8192
exp2 / elementwise inline asm cost ≈ result element count
other ops = 0

这不是周期精确模型，也不是全 kernel critical-path solver。它只给 merge rules 足够稳定的信号，避免明显不合理的分裂/合并。

7.5 最重要的 merge rules

规则 直觉
load + matching local alloc descriptor load 与承接 tile 的 shared allocation 应在 producer role
view producer/consumer 比较 view 两侧 element count，把 view 放到通信量更小的一侧
loop iter arg 普通 loop-carried value 倾向生产者；async token 倾向消费者
SFU consumer costly SFU 可吸收依赖，但避免吞掉 MMA/LOAD/另一 costly SFU
TMEM load 与其 consumer 合并，形成 reader/epilogue role
NONE/index op 尽量附着到实际计算 role，必要时复制
connected large edge 大型非 LOAD/MMA payload 倾向合并，避免巨大 ARef
load epilogue 不通向 MMA 的 load path 并入 epilogue，避免无意义 producer role

全 partition 规则还合并纯 MMA roles、纯 LOAD roles，以及共享同一 TMEM allocation 的 TMEM roles。禁止边界包括：两个 manual groups 不合并、TMEM role 不被 MMA role 吞并、非 token TMEM alloc 不被 MMA role 吞并。

7.6 复制计算，避免往返通信

若一条 cheap path 从 partition A 进入 B 后又回到 A，复制这段纯计算往往比建立 Shared buffer、两组 barriers 和 lifetime 更便宜：

duplicate a few pure ops  <  ARef allocation + synchronization + lifetime

cloneMultiPartitionDataOps 处理 data op 本身属于多 partitions 的情况。冻结历史中，小 tile attention 的 repeated users 曾让 use-list rewrite 失效并触发 assert；修复使用 early-increment 遍历。这个故事说明两件事：实现有真实 hardening；但“修复 crash”不等于已经证明相邻 shapes 有性能收益。

7.7 临时 attributes 是 pass-local ABI

最终序列化：

  • ttg.partition：op 属于哪些 roles；
  • ttg.partition.outputs：structured op 每个 result 的 owner；
  • ttg.partition.stages：各 partition 的 stage；
  • ttg.warp_specialize.tag：关联同一 WS instance 的 nested/外围 op。

这些 attributes 是 analysis scratch state，不是公共 TTGIR ABI。verifyPartitionedLoop 检查 ID、父子覆盖与 output arity 等局部一致性；它不证明跨 partition direct SSA 已被 ARef 接管。后者若残留，会在 PartitionLoops 阶段被单独拒绝。成功 materialize 后，attributes 必须清除。

8. 显式 ttg.warp_specialize：先把并发 ABI 学扎实

自动策略最终必须归一到定义明确的 TTGIR op。把 explicit contract 与 automatic discovery 分开，是理解和验证实现的关键。

%results = ttg.warp_specialize(%capture0, %capture1)
default {
  // 原 warp group；可以读取外层 SSA；可以产生 op results
  ttg.warp_yield %r0
}
partition0(%p0, %p1) num_warps(1) {
  // IsolatedFromAbove；只能通过显式 captures 读取外部值
  ttg.warp_return
}
partition1(%q0, %q1) num_warps(4) {
  ttg.warp_return
} attributes {
  requestedRegisters = array<i32: ...>,
  actualRegisters = array<i32: ...>,
  warpGroupStartIds = array<i32: ...>
} : (...) -> (...)

8.1 default 与 workers 不是顺序 regions

  • default 继承进入 op 的 base warp group；
  • worker partitions 与 default 在执行期可同时存活；
  • workers IsolatedFromAbove，必须显式 capture；
  • worker 以无 operand 的 ttg.warp_return 结束；
  • 只有 default 的 ttg.warp_yield 定义整个 op 的 SSA results；
  • 当前显式 WS 不能嵌套另一个显式 WS；普通 outer loop 包着一个 WS，或同一函数顺序出现多个 WS sites，不等同于显式嵌套。

并发 live range 是重要语义。Shared/TMEM allocator 不能因两个 region 在 MLIR 文本中先后打印就复用同一地址；它们需要进入同一 interference analysis。

8.2 为什么 worker 不能返回普通 SSA tensor

不同 worker 可能使用不同 warp 数和 layout domain。当前 ABI 没有把 worker result 变成 uniform、可由 default 顺序读取的 region result。若 worker 产生数据供另一 role 使用，必须在 materialization 前改写成：

  • Shared/TMEM ARef；
  • capture 所指向的显式 storage；
  • 或其他有明确排序的副作用。

所以“worker 无返回值”不是语法遗漏，而是并发数据所有权模型的直接投影。

8.3 三个属性数组的索引不相同

属性 索引 0 表示什么
requestedRegisters[i] worker partition i
warpGroupStartIds[i] worker partition i 的物理起始 warp
actualRegisters[0] default；actualRegisters[i+1] 才是 worker i

冻结 verifier 没有封闭 requested/actual 数组所有长度假设；正常 pipeline 维护它们，不应把下游假设误写成 arbitrary hand-written IR 已被验证。

8.4 verifier 能提前发现什么

显式 micro IR 的重要负例包括：

  • partition 数与 partitionNumWarps 数不符；
  • captures 的数量/类型与 region arguments 不符；
  • worker warp 数不是 2 的幂，或 base num_warps 不是 4 的倍数；
  • warpGroupStartIds 长度不符；
  • default yield 与 op results 的 arity/type 不符；
  • worker 内 layout warp 数与 region 宽度不符；
  • 显式 WS 嵌套；
  • partitions holder 的结构不合法。

这些应在 TTGIR verifier 阶段得到定位错误，而不是拖到 LLVM switch lowering 的 assert。

为什么 ttg.warp_specialize 更像 concurrent-region ABI，而不像 scf.if 或函数调用？请从“谁产生 SSA result”“谁可以捕获外层值”“allocations 是否并发存活”三个角度回答。

9. NVWS：一门会主动消失的“事务语言”

现在已经知道最终并发 ABI 是 ttg.warp_specialize。这时再看 NVWS dialect，定位就很清楚了：它不是用户 API，也不是 GPU ISA，更不是最后留给 LLVM 的稳定 ABI；它是一套只在 AutomaticWS 中途出现、用完就删除的事务语言。

9.1 为什么不能一上来背 16 个 NVWS op

冻结树中大约有 16 个 NVWS operations、两个 types、若干 attributes/interfaces 和 6 个 NVWS passes。但这些对象并不同时表示一台运行时机器。它们分属两个很短的 epoch，外加一条旧 channel：

epoch 先出现什么 它临时表达什么 谁把它消掉
ARef epoch nvws.aref.*、nvws.descriptor_load/gather 跨 partition payload 或 TMEM owner 怎样交接 LowerAref
role epoch nvws.warp_group/yield/return 哪几条投影后的 loop 属于并发角色 LowerWarpGroup
legacy channel !nvws.token 与 producer/consumer ops 旧 Hopper code-partition channel WSLowerToken；不是本文 Blackwell ARef 主线

把这三套对象平铺成一张“NVWS 运行时模型”会产生错觉：仿佛 ARef、warp group 和 legacy token 在最终程序中长期共存。正常路径恰恰相反：ARef 先被结算成 buffers/barriers，再建立临时 warp groups；warp groups 又立刻转成正式 ttg.warp_specialize。

9.2 生命周期表：读源码时先问“谁创建、谁消费”

对象 创建者 消费者 运行时含义
tt.warp_specialize marker frontend/codegen AutomaticWS gate 无；只是请求
stage/cluster attributes ScheduleLoops WS 分析与 Pipeline 描述迭代时间关系
ttg.partition* 临时 attrs PartitionScheduling ARef/PartitionLoops 描述角色归属；非稳定 ABI
nvws.aref.* InsertAref / InsertTmemAref LowerAref backing storage 的 ownership/completion 事务
nvws.warp_group PartitionLoops LowerWarpGroup 角色结构的短命容器
ttg.warp_specialize LowerWarpGroup 或显式 TTGIR LLVM lowering 正式 default/workers 并发语义

这张表解释了两个常见疑问：ARef 后来不见了，是因为它已经“结算”为真实 storage 和同步；NVWS warp group 后来不见了，是因为它已经归一到稳定 TTGIR op。消失是成功完成 lowering 的证据，不是功能丢失。

9.3 同一个 !ttg.async.token 类型为何有两种语义

原 TCGen05/TMEM op 的 async token 表示围绕同一片 TMEM 对象的 dependency/mod-ref 顺序，近似 MemorySSA 的访问边；ARef enter 返回的同类型 token 只负责配对 enter、buffer view 与 exit。类型名一样，不等于语义一样，更不等于硬件 completion object。

运行时真正跟踪 phase、arrival count 和 expected transaction bytes 的，是 Shared 中的 mbarrier object。#nvws.async_op<tc5mma> 也不是 token，而是一段编译期 metadata：它告诉 LowerAref，某个 full/empty arrival 应由普通 arrive、TMA completion 还是 TCGen05 commit 完成。

源码阅读 invariant

看见一种 IR object 时，不先问“它像什么硬件”，先问：它的 producer pass、consumer pass 和 lifetime 是什么？ 对 transient dialect，这比记 op 名更可靠。

10. Shared ARef：把一条 SSA 边变成可循环复用的邮箱

自动分区后，producer 与 consumer 已经不在同一顺序 region。原来的 %tile = descriptor_load ... 不能再作为普通 SSA value 从一个并发 role 直接“传”到另一个 role：SSA def-use 只说明值依赖，不说明 payload 放在哪里、TMA 何时完成、slot 何时可覆盖。

ARef 的工作就是把这条跨并发域边拆成四个东西：

  1. 一个或多个 backing buffers；
  2. producer 对 slot 的借用区间；
  3. consumer 对同一 slot 的借用区间；
  4. empty/full credits 与 completion metadata。

10.1 先只学一个 slot

一个 slot 的完整协议是：

步骤 IR 概念 所有权状态 关键问题
1 aref.put.enter producer 等到 empty，借到可写 view 上一轮 consumer 真的用完了吗？
2 descriptor bridge 写 backing producer 正在填充 是同步写还是异步 TMA？
3 aref.put.exit 发布 full full arrival 由谁完成？
4 aref.get.enter consumer 等 full，借到可读 view transaction bytes 是否也归零？
5 consumer uses consumer 持有 slot “最后使用”到底在哪里？
6 aref.get.exit 归还 empty 何时允许 producer 覆盖？

最容易忽略的是第 6 步。若编译器把 get.exit 放在第一个 use 后面，而真正的最后 use 位于 CFG 另一条路径或后一个 pipeline cluster，producer 可能提前覆盖仍在读取的 tile。InsertAref/LowerAref 因此不能只看文本顺序，而要结合 CFG post-dominance、stage/cluster 和实际 uses 决定 transaction 边界。

10.2 descriptor load 为什么改成 destination form

原始 descriptor load 看起来像“产生 tensor SSA result”：

%tile = tt.descriptor_load %desc, %coords : ... -> tensor<...>

跨角色后，payload 必须落入显式 backing。InsertAref 把它桥接成目的地形式，大意是：

%slot, %pair = nvws.aref.put.enter %channel
nvws.descriptor_load %desc, %coords, %slot {txCount = ...}
nvws.aref.put.exit %pair {async = #nvws.async_op<tma_load>}

LowerAref 随后才把 bridge 变成真正的 async TMA copy，并在 full mbarrier 上设置 expected transaction bytes。于是 %tile 这条跨角色 SSA edge 变成了“双方引用同一 backing slot + 一套可复用协议”。

10.3 empty 与 full 为什么是双向 credit

只做 full notification 不够。full 告诉 consumer“可以读”；empty 告诉 producer“可以覆盖”。这两条方向相反的因果边共同构成 bounded channel：

producer --publish full--> consumer
producer <--return empty-- consumer

若只保留第一条，第一次迭代或许正确，第二次复用 slot 就可能发生覆盖。若只保留第二条，consumer 又不知道 TMA 是否已把新 payload 填完。

10.4 从 one-slot 扩展到 numStages

多缓冲并没有改变协议，只是把 one-slot machine 复制为一个 ring：

slot = iteration mod depth
phase 在 slot 绕回时翻转；put 与 get 的初始相位互补

冻结 AssignStagePhase 的具体状态从 stage = depth - 1 开始，put phase 初始为 0、get phase 初始为 1；每次 enter 先推进 stage，发生 wrap 时再 xor phase。上式因此只保留最稳妥的环形直觉，不能把 producer/consumer 都机械写成同一个 floor(iteration/depth) mod 2。

对 producer 是 descriptor/TMA 的普通 payload channel，当前实现通常把 depth 扩为 numStages；每个 slot 仍有 empty/full generation。Generic scalar/tensor handoff 通常保持 depth 1，scale ARef 也有特殊的 depth-1 规则。不能写成“出现 ARef 就自动按 numStages 多缓冲”。

10.5 completion kind 决定谁来 arrive

LowerAref 对不同 producer/consumer 类型生成不同完成动作：

  • ordinary synchronous producer：显式 arrive full；
  • TMA producer：把 expected bytes 计入 mbarrier，full completion 由 TMA hardware 到达；
  • TCGen05 consumer/producer 边：可能用 tc_gen5_commit 把此前 MMA completion 关联到 barrier；
  • ordinary consumer：最后 use 后显式归还 empty。

因此 ARef 是统一的 ownership abstraction，但不是把所有硬件异步事件假装成同一条指令。completion kind 是 lowering 选择器。

10.6 当前最重要的不支持边界

普通 pointer load/cp.async 若留在同一 compute role，可由通用 pipeliner 双缓冲；但若它的 payload 真的跨 partition，需要 ARef 为 cp.async 建立异步完成协议，冻结 LowerAref 仍有 cpasync not supported yet 的 unreachable 边界。mixed TMA + ordinary load 能工作，是因为普通 load 留在 default/compute role，并不等于跨 partition cp.async channel 已支持。

假设 depth=2，第 0、1、2 次 iteration 分别用 slot 0、1、0。请写出第 2 次 producer 覆盖 slot 0 之前必须观察到的事件。答案若只有“第 0 次 TMA 已完成”，仍缺一条 consumer→producer ownership 边。

11. TMEM ARef：移动的不是 accumulator，而是访问资格

Shared ARef 的 payload 很直观：A/B tile 真正在 shared backing 中。TMEM ARef 若也被理解为“把 accumulator 从 MMA role 复制给 reader role”，就会彻底读错。

同一个 TMEM allocation 可以一直待在原地。跨角色转移的是：当前哪一个 owner 可以合法地沿 access DAG 对它执行 MMA、load、store 或 copy。

11.1 从 token use-chain 建 access DAG

TCGen05 MMA、TMEM load/store 等 op 周围的 async token 把同一 allocation 的访问串起来。InsertTmemAref 沿这条 token graph 收集 access nodes，并读取每个 node 的 partition 归属：

MMA(partition A) ─token→ TMEM load(partition B)
      ↑                         │
      └──── next-iteration token┘

当相邻 access 的 owner 改变，pass 才插入一次 TMEM ARef hand-off。buffer view 指向同一或轮换后的 TMEM allocation；它不是 accumulator tensor 的 memcpy。

11.2 two-owner ping-pong

典型 GEMM 的中心形状是：

MMA owner A → reader/epilogue owner B → next MMA owner A

于是协议交替成：

  • A 在 transaction 中发起/完成 MMA，然后把 ownership 给 B；
  • B wait 后执行 TMEM load/epilogue，最后把 ownership 还给 A；
  • 下一 iteration 才允许 A 再修改该 accumulator buffer。

这一层同时要维护 ownership 与硬件 completion，但两者仍不是同一概念。async token 用来找到 DAG；mbarrier/commit 等在 lowering 后真正等待；专用 TCGen05 inter-thread ordering 仍需单独审计。

11.3 为什么当前实现不是任意 owner graph

冻结实现对显式 partition IDs 有“最多两个”的断言，并在后续 lowering 中大量使用 two-owner 设计。这里还有更细的证据缺口：断言统计显式 IDs，root/default 加两个显式 owners 的形状并未被完整证明。它不能被宣传成通用 N-party TMEM ownership protocol。

TMEM subview 也是明确 NYI 边界。若 partition 只需要大 allocation 的非平凡子视图，当前分析/rewriter 未必能安全构造 owner hand-off，应期待 diagnostic/assert，而不是自动泛化。

11.4 double buffering 不是默认奖励

冻结实现只有在四个源码谓词同时成立时才让 TMEM accumulator depth=2：

  1. producer/consumer access graph 恰好出现两次 partition transition，形成受支持的 owner 往返；
  2. !hasAccReadModifyWrite；
  3. isAccMultibufferingPossible 返回 true；
  4. 没有设置 disallowAccMultiBuffer。

不满足任一项就保持单缓冲。这里应引用 pass 真正检查的谓词，而不是把“persistent/nested 看起来更复杂”自行追加成独立源码条件。

所以“有 TMEM ARef”只证明 owner edge 被显式化；“depth=2”才是另一个独立优化事实。

11.5 HoistTmemStore 为什么必须在前面

若 accumulator 每次先做一条可证明的 TMEM initialization store，再做 MMA，直接分区会把 initialization 也变成一次额外 owner hand-off。HoistTmemStore 先由 FoldTmemStoreIntoAlloc 把 store source 折成 TMEMAlloc(src)；若 canRemoveTmemStore 且跨 loop hoist 可证明，就继续 hoist allocation/token 并删除 store，否则把 allocation 归入 MMA partition。它在 InsertTmemAref 之前做这些事，目的是减少不必要的 owner transition。

顺序很关键：先生成 ARef 再 hoist，会让 pass 试图跨已经物化的 transaction 改写 storage lifetime，复杂度和风险都更高。

三个 TMEM 动词，三种不同 lifetime

relinquish_alloc_permit 归还“继续申请 TMEM”的许可；ARef hand-off 交接同一 allocation 的访问权；dealloc 才释放 columns。不要用“释放 TMEM”同时指代三者。

12. PartitionLoops：复制结构化控制流，再按角色剪枝

到这一步，partition attrs 已标好，跨角色边也已由 ARef/storage protocol 处理。现在才有资格把一个 loop 变成多条角色 loop。

12.1 它不是把几条 op 移到 if (warp_id)

PartitionLoops 对带 ttg.partition-stages 的结构化 loop 做投影：

  1. 为每个 partition 克隆相关 scf.for；
  2. 递归克隆受支持的 scf.if 与单结果 tt.reduce；
  3. 删除该角色不需要的 operations；
  4. 修剪该角色不使用的 iter args/results；
  5. 检查是否仍有无法解释的 direct cross-partition SSA dependency；
  6. 把这些投影 loop 装进 nvws.warp_group regions。

例如原循环：

for k:
  descriptor A/B → MMA → TMEM load → epilogue math

可能投影为：

TMA role loop    : get empty → issue descriptor A/B → publish full
MMA role loop    : wait A/B → issue MMA → transfer TMEM ownership
default loop     : wait ownership → TMEM load → vector epilogue

三条 loop 各自仍有正确的 induction variable、loop-carried state 和必要 control skeleton，但不是把整个 body 原封不动复制三份。

12.2 为什么 structured graph 支持范围会限制 WS

当前 partition graph 知道怎样编码 scf.for、scf.if 与单结果 tt.reduce。任意 region-bearing operation、scf.while 或 multi-result reduction 没有自动获得正确的节点、result、backedge 与 merge 语义；深处可能落到 fatal/assert 边界。

这不是 MLIR 理论上做不到，而是本实现的 graph/lowering contract 只封闭了特定 structured forms。因此通用性要按“支持哪些 region forms”报告，不能只按 op-level role flag 报告。

12.3 跨 partition SSA 为什么在这里必须归零

若一个 worker 仍直接使用另一个 worker 定义的普通 SSA value，PartitionLoops 无法凭 clone 顺序把它合法化，因为两个 regions 是并发的。这个 dependency 应在更早阶段被：

  • 改写成 Shared/TMEM ARef；
  • 克隆/重物化 cheap pure computation；
  • 合并 partitions；
  • 或保守拒绝变换。

因此“still has SSA dependencies”是一个很有价值的防线：它防止 compiler 用文本支配关系伪装并发通信。

12.4 LowerWarpGroup 怎样选 default

临时 nvws.warp_group 还不是正式 ABI。default 的选择有一条很具体的规则，并非“第一 region 永远是 default”：只有第一 group 的 warp 数恰好等于 module 的 ttg.num-warps，它才继承原 base warps；否则 lowering 创建空 default，并把全部 groups 作为 workers。若 op 有 results、第一 group 又不能成为 default，rewrite 会 match failure，因为 worker return 没有 result ABI。正常 AutomaticWS provenance 不构造这种形状，但当前 greedy rewrite 不保证把合法却未匹配的手写 NVWS residue 变成稳定 pass failure。

外部值若能安全重物化，就在 worker 内重建；pure constants/tensor expressions 优先 rematerialize，不能重物化的 ranked tensor 可先 spill 到 Shared 再由 worker local_load，其余值才进入显式 capture list。

随后生成：

  • default 的 ttg.warp_yield 与 op results；
  • worker 的 arguments 与 ttg.warp_return；
  • 每个 partition 的 logical num_warps；
  • 后续资源 pass 所需的 metadata。

到了这里，自动路径与手写 explicit WS 汇合。后端不再关心某个 role 是 heuristic 找到的还是用户构造的；它只依赖正式 verifier contract。

13. Pass 编排：WS 是夹在两次调度之间的一次复合事务

单独理解每个 pass 还不够；顺序本身就是 correctness contract。冻结 NVIDIA/SM10x 主线可压成三段。

13.1 外层调度脊柱

13.3 descriptor 为什么可能要 numStages + 1 份

在 persistent/grouped GEMM 中，每个 group iteration 可能重建 descriptor。若 stage ring 深度为 numStages，下一轮想更新 descriptor 时，最老的 TMA 仍可能引用某个 descriptor storage。于是需要额外一份 descriptor，让“下一次更新”与“最老 in-flight use”重叠：

descriptor buffers = numStages + 1

源码中若又看到 CoarseSchedule(numDescs + 1)，第二个 +1 是 schedule 使用最大 stage 编号加一的构造约定，不是再额外分配一套 descriptor。把这两个 +1 混起来会把资源账算错。

第三部分　从逻辑角色到物理常驻执行机

14. logical partition 怎样装进 physical warpgroups

ttg.warp_specialize 中的 worker num_warps(1) 只是逻辑执行宽度。NVIDIA setmaxnreg.sync.aligned 的参与单位却是连续 4 warps 的 physical warpgroup。两者不能靠名字自动相等。

14.1 一个贯穿物理 lowering 的数字例子

设 kernel 的 default group 有 4 warps，自动策略选择：

  • MMA role：1 logical warp；
  • TMA role：2 logical warps。

workers 的有效需求合计为 3 warps。AllocateWarpGroups 向物理 warpgroup 宽度 4 补齐，因此额外分配 4 worker warps；总 kernel 是 8 warps：

absolute warp 角色 是否执行有效 partition work
0–3 default 是
4–5 TMA workers 是；allocator 按 partition size 降序先放 2-warp role
6–7 一个 MMA worker + 一个空 padding worker 哪个占 6/7 不作为稳定顺序承诺；padding region 不做有效计算

这里“TMA 至少 2 warps”“TMEM role 当前至少 4 warps”是冻结 compiler 的吞吐/布局 policy，不是 PTX ISA 宣布每次 TMA 或 TMEM op 必须有这些 warp。

14.2 为什么按全函数最大需求分配 worker pool

同一函数可顺序出现多个 WS sites。后端不会为每个 site 各生成一批新硬件 warps；它计算全函数所有 sites 所需的最大 worker 数，向 4 对齐，建立一个可复用 pool。padToMaxWarpGroups 会为较小 site 补真正的空 worker partition，使未承担有效工作的 warps 仍沿受控 region/return path 参加协议。

这带来两个结论：

  1. kernel 的总 warp 数由最大同时 worker 需求决定，不是所有 sites 的 worker 数相加；
  2. 每个 site 必须给同一 pool 写不同 dispatch states，workers 执行后回到 loop，等待下一 site。

14.3 start ID、relative ID 与 partition ID

  • absolute warp ID：CTA 内真实 warp 编号，用于入口把 base 与 extra workers 分开；
  • worker start ID：某 logical partition 在 extra pool 中的物理起点；
  • relative warp ID：worker 进入 partition 后看到的从 0 开始编号，用来满足 role 内 layout 语义；
  • partition state/tag：shared dispatch table 中用于 switch 的任务编号。

它们是四个坐标。把 partition ID 当作 warp ID，会在 layout、named barrier 编号和 state switch 中同时出错。

14.4 physical group packing 的保守退化

allocator 即使不能为 requested register budgets 找到可行分配，也可以保留 total warps 和 start IDs，只是不写 actualRegisters、不强制插入 setmaxnreg。这是资源优化的安全退化，不代表 WS 结构本身必须回滚。

TMEM worker start ID 的 4 对齐在冻结树仍有 FIXME，属于“缺统一 verifier/guarantee”的边界。应报告证据缺口，而不是把它夸大成所有 case 都必错。

15. 寄存器也被角色化：requested、actual 与 setmaxnreg

角色分工的价值之一，是让搬运 role 把暂时不用的寄存器额度归还给 CTA pool，让 reader/epilogue role 获得更宽的 per-thread budget。但这不是静态改一个 launch attribute：额度会在运行时随 role 切换。

15.1 OptimizePartitionWarps 先给启发式请求

冻结实现按 worker region 中最大的 RankedTensor i32-register footprint 是否为零做粗分：

  • 没有 tensor footprint：请求约 24 registers/thread；
  • 有 tensor footprint：请求约 88 registers/thread。

这常与“轻量 TMA role / tensor-heavy compute role”相关，却不能按角色名字直接推导。24/88 都只是 compiler guess，用来探索资源重分配，并非 ptxas 最终分配、硬件常数或 occupancy 证明。实际 role 内 live ranges、spills 与 launch constraints 仍由后续工具链决定。

15.2 AllocateWarpGroups 再解物理预算

一个 physical 4-warp group 可能装有多个 logical roles和 padding warps；硬件要求整组执行同一 setmaxnreg。allocator 因此要把共享 physical group 的需求合并，检查 CTA register pool、default leftover 与 legal immediate，最后才产生：

  • requestedRegisters[i]：worker partition region i 的逻辑请求，不是单个 warp 的独立数组项；
  • actualRegisters[0]：default 的实际额度；
  • actualRegisters[i+1]：worker i 的实际额度。

requested[i] 与 actual[i] 直接对齐是典型 off-by-one 误读。

15.3 .inc 88 不是“再加 88 个”

setmaxnreg immediate 是每线程的绝对上限：

  • 从 24 切到 88，发 .inc ... 88；
  • 从 88 切到 24，发 .dec ... 24；
  • 若 entry current budget 比 role target 更高，worker 进入 role 也可能 .dec；
  • 若某个 over-allocation 策略让 default 退出时需要更高 budget，退出方向也可能反过来。

所以 lowering 必须比较 current → target，不能把“进入 worker”等同于 inc、“离开 worker”等同于 dec。

15.4 为什么 .inc 可能阻塞

.dec 把尾部寄存器归还 CTA pool；.inc 请求从 pool 获得更多，pool 不足就等待。因此正确协议必须保证其他 physical warpgroups 已在适当同步之前 release，且连续两次 setmaxnreg 之间满足 PTX 的显式同步要求。

它只管理资源，不传递 payload、不等待 TMA/MMA，也不建立 Shared/TMEM 数据顺序。把它当 barrier 会掩盖一条真正缺失的数据边。

15.5 lowering 的合法化边界

PTX immediate 合法范围是 24–256，且为 8 的倍数。冻结 lowering 明确做了上限 clamp 到 256；最小值与 8 对齐主要依靠上游预算构造，不能宽泛写成“LLVM lowering 会自动把任意整数完整裁剪到合法值”。

若任一 WS op 带 tti.disable_setmaxregister，LLVM lowering 会对整个 kernel 禁用 dynamic register reallocation，而不是只跳过该 region。

某 physical WG 当前额度 88，目标 role 请求 24。它进入 role 时应发 inc 还是 dec？这条指令是否足以保证它随后能读 producer 写入的 Shared tile？分别说明原因。

16. LLVM persistent worker：一台全函数级任务状态机

如果把 WS 想成每到一个 site 临时创建 workers，就无法解释多 site 复用、capture transport 和 kernel return。实际 lowering 更像一个微型 thread pool：extra warps 从 kernel 入口开始就常驻，反复读取 shared state，跳到当前任务 region，完成后回到 switch。

16.1 入口：先用 absolute warp ID 分流

函数 entry 被拆成两条：

  • absolute warp ID 小于 base warp 数：进入原 default CFG；
  • extra worker warp：进入 persistent header/switch loop。

worker 不能直接沿 default path 走到某个 WS op，因为 default 可能在到达该 site 前执行任意控制流，甚至不执行该 site。它必须等待显式 dispatch。

16.2 shared i8 state table

每个 extra worker warp 有一个 shared state byte。default 到达一个 WS site 时，为相关 workers 写入 partition task ID；较小 site 已由 padToMaxWarpGroups 补成空 padding partitions，所以这些 warps 也得到一个合法的空 region state。default 随后用 named CTA barrier 发布。

worker 醒来后读取自己的 state，在 LLVM switch 中跳到对应 partition blocks；空 padding region 直接 return 到循环。kernel 退出时，default 广播 exit state 255，让所有常驻 workers 跳到共同 return。有效 partition states 使用 0…254；第 256 个 state 会在分配阶段得到上限 diagnostic，因此这里没有必要保留“255 与 padding -1 已知碰撞”的旧推断。

16.3 为什么 partition 内要重写 relative warp ID

worker role 的布局通常假定本 partition 的第一个 warp 编号为 0。若直接暴露 absolute ID 4、5、6，layout conversion、elected-thread 条件与 barrier lane mapping 都可能改变含义。lowering 进入 region 后用 absolute - partitionStart 构造 relative warp ID。

16.4 captures 不是 ARef

worker region IsolatedFromAbove，不能隐式读 default 的外层 SSA。更早的 LowerWarpGroup 会重物化 ConstantLike/安全的 pure ranked-tensor chain；无法重物化的 ranked tensor 先经 Shared spill/load，剩余值进入正式 capture list。LLVM 阶段的 elideTrivialCaptures 还可为至多 16 个 pure ops 的小子图再做一轮重物化；最终留下的 captures 才打包进 shared scratch record：

default writes capture record
→ control barrier publishes record + task state
→ worker reads capture fields
→ worker executes region
→ join/control barrier allows reuse

这块 scratch 解决“任务参数怎样到 worker”，没有 ARef 的 ring slots、empty/full credits、TMA bytes 或 TMEM owner semantics。二者都可能位于 Shared，但抽象和 lifetime 完全不同。

16.5 三个逻辑 rendezvous 不能压成“发布/完成”两个词

一次 dispatch 至少要区分三件事，即使实现可在不同 phase 复用同一个 named switch barrier：

  1. state/capture publish：default 写完任务与参数后释放等待的 workers；
  2. capture-consumed：workers 已把 capture scratch 读完，default 才能复用这块 transport storage；
  3. role join：default 的 warp_yield 与 workers 的 warp_return 会合，随后 workers 才返回 persistent switch。

第二项不是“worker 已完成整个任务”的同义词；第三项才对应角色 region 的完成会合。这些都是控制面 rendezvous，不跟踪 TMA transaction bytes，也不代替 ARef empty/full。

16.6 named barrier 资源不是无限的

冻结 mapping 大意为：

  • ID 0：default local use；
  • ID 1：worker switch/control；
  • ID 2 + partition：partition-local barrier handles。

硬件只有 16 个 named barrier IDs，因此最多约 14 个 partition-local handle regions；超界应得到 lowering diagnostic。这里的 partition-local 编号也不是 dispatch state ID、ARef mbarrier index 或 cluster barrier slot。

16.7 为什么禁用 switch-loop LICM

源码给 switch-loop latch 加禁用 LICM 的 annotation，明确理由是寄存器 lifetime：若只在某个 partition 使用的计算被 hoist 到 persistent loop 外，结果可能跨多次 dispatch 长期存活，扩大 live range，甚至诱发 partition spill。不要把它改写成“state/capture 会永远读到第一次值”这种源码未给出的语义断言。

到这里，整个执行机终于闭环

default 决定“何时派任务”；ARef 决定“数据 slot/owner 何时可用”；persistent switch 决定“哪组 worker 跑哪段代码”；setmaxnreg 决定“当前角色能占多少 register budget”。四者各自解决一个正交问题。

17. 从 TTGIR 到 PTX：怎样审计一条完整因果链

看到 ttg.warp_specialize 不等于证明后端协议完整。最可靠的方法是选一条 payload/owner path，从 IR 一直追到 PTX，并把每个等待标注成 completion、ordering、visibility、control 或 resource。

17.1 TMA → Shared consumer

理想审计表：

事件 要找的结构 证明什么
backing allocated Shared allocation + ring subview 跨 role payload 有物理位置
producer waits empty empty mbarrier phase wait 上一 consumer 已归还 slot

冻结源码、tests 与 compile-only artifact 没有呈现 PTX ISA canonical cross-thread pattern 中的显式 after fence。这是 ISA 契约覆盖差异，需要 exact-hardware runtime、SASS/工具链语义或 NVIDIA 明确说明进一步资格化；仅靠 compile/assemble 既不能证明 wrong-code，也不能宣告协议已完整。

17.3 TMEM alias barrier 不替 MMA completion 重复记账

TmemBarrierInsertion 的冻结覆盖更窄：它处理同步 TMEM load/store 的别名关系，以及 load/store→MMA 的相关 hazard；MMA→load/store 明确依赖 mbarrier completion wait，并不再由该 pass 泛化成一条 alias barrier。MMA commit/mbarrier 处理异步 Tensor Core completion；after-thread fence 处理 TCGen05 inter-thread execution ordering。三者可能围绕同一 accumulator 出现，却没有互相取代关系。

17.4 ConSan 的正确定位

Concurrency sanitizer 能建模 partition active masks、proxy frontier、barrier lifecycle、部分 cluster visibility，并发现错误 arrive/wait/访问顺序；它不能凭空生成 compiler 未表示的专用 TCGen05 fence，也不能替代真实 SM103 的数值与死锁压力测试。

17.5 ws 字符串审计的陷阱

在 PTX 中搜索 .ws 可能找到 weight-stationary MMA；在 MLIR 中搜索 warp_specialize 可能只找到 marker；在 SASS 中找不到相同名字也不代表功能缺失。正确审计要追踪结构和因果边，而不是做单字符串存在性测试。

第四部分　把统一模型应用到复杂路径

18. Persistent、attention 与 grouped GEMM：复杂的是 lifetime，不只是算子更多

高级 case 最容易被“有一个同名 fixture”误导。正确做法仍是沿四条轴分析：时间 stage、角色 partition、storage owner、physical resource，然后单独列证据 provenance。

18.1 persistent GEMM：外层 tile claim 包住内层 owner machine

persistent kernel 让同一个 CTA 反复领取 output tiles。于是有两层循环状态：

  • outer：CTA 何时领取/结束一个 tile，descriptor/base/shape 是否更新；
  • inner：K-loop 的 TMA stage、MMA accumulator 与 reader owner hand-off。

若 marker 位于 outer loop，AssignLatencies::isWarpSpecialized 必须沿 ancestor 识别 nested K-loop 中的 MMA，才能选择正确 latency 分支；ARef/TMEM passes 则通过各自的 getOuterWSLoop 找到所属 WS scope。二者目的相关但不是同一个 helper，也不应一句话写成同时控制 latency 与 ownership。

18.2 attention：两套 accumulator 与更多标量 recurrence

典型 fused attention inner body包含：

QK MMA → TMEM load → max/sum/exp2 → P×V MMA

同时携带 m_i/l_i 标量 recurrence、QK/PV 两条 accumulator/token lifetime、K/V payload channels。这里的挑战不是“再做一次 MMA”，而是：

  • scalar recurrence 可能把 default/reader 与 compute roles重新拉近；
  • inner loop 无 marker，但 outer persistent scope有 marker；
  • 两条 TMEM DAG 的 owner transitions 可能不同；
  • small-tile/repeated-user 会影响 cheap-op cloning与 partition merge。

冻结树有 persistent attention partition、Shared ARef、TMEM ARef 和 AutomaticWS 的分层 fixtures，但它们未必来自同一个 Python 输入的完整 lineage。应写“组件/组合证据”，不能拼成全 shape 端到端承诺。

18.3 grouped GEMM：descriptor 也有 in-flight lifetime

grouped GEMM 每个 group iteration 动态读 A/B/C base 与 strides，并重建 tensor descriptors。旧 TMA 可能还引用某 descriptor storage，因此 descriptor 本身必须 multi-buffer，通常是 numStages + 1。

Python integration 与同名 TTGIR fixture 还可能在 dynamic stride、num_stages 等处不同。名字相同只说明设计 shape 相近，不等于 frontend 逐字产生该 fixture。实验记录要保存输入 hash、target、pass dump 与产物 hash，才能建立 provenance。

18.4 高级 case 的固定问卷

遇到任何新 kernel，逐项回答：

  1. 哪个 loop 真正带 marker，nested loops 是否继承 WS scope？
  2. descriptor/TMA roots 在哪，普通 loads 是否跨 partition？
  3. 有几条 Shared payload channels、几条 TMEM owner DAG？
  4. 哪些 scalar/shape/capture 必须跨 role？
  5. 每条 channel 的 depth 与 phase 是多少，依据是什么？
  6. logical workers 怎样映射到 4-warp physical groups？
  7. completion、ordering、proxy、control 与 resource protocols 是否各自闭合？
  8. 证据是 focused IR、组合编译、runtime，还是 performance？

这套问卷比“源码里有没有 attention 字样”可靠得多。

19. Scaled MMA 与 2CTA：所有权图和同步域继续扩张

19.1 scaled/blockscale 不是“普通 MMA 多两个 operands”

scales 可能来自三处：

  1. 已在 Shared 的普通 scale tile；
  2. descriptor/TMA 载入 Shared 后 reshape/transpose；
  3. 写入 #ttng.tensor_memory_scales encoding 的 TMEM。

于是一个 scaled MMA 周围可同时存在 A/B payload Shared channels、A/B scale Shared或TMEM channels、accumulator TMEM owner channel、以及 MMA dependency token。每条 storage edge都要单独回答 owner 与 completion。

scale ARef 有 depth-1 特例；Shared TMA payload可以按 numStages 扩展；accumulator TMEM depth=2 又由 access DAG决定。不能用同一个“三级流水”参数概括所有 buffers。

19.2 scaled MMA 的 async 化是条件性的

LowerAref::setIsAsync 只有在 loop 且 numStages>1 等条件满足时才尝试异步；scaled MMA 还要求两侧 scale provenance 可 pipeline。任一 scale 无法安全重叠时，会保守同步。

后续 SyncMMALowering 仍可能把同步语义实现为“硬件 async MMA + completion barrier + 立即 wait/invalidate”。因此最终 PTX 中看到异步指令和 barrier，只证明硬件形式，不证明跨 iteration overlap。

19.3 2CTA 增加第三个同步域

两 CTA TCGen05 路径必须同时维护：

  1. CTA 内 default/workers 的 WS dispatch；
  2. CTA 内 MMA completion、TMEM owner 与 TCGen05 ordering；
  3. cluster 内两个 CTA 的 rendezvous/visibility。

tcgen05.mma.cta_group::2 只回答 MMA instruction form。cluster hazard analysis、multicast commit、barrier allocation，以及初始化后的全-warps cluster 同步又是别的 passes/fixtures。

19.4 为什么 cluster barrier 常需双槽

常驻/流水执行可能在当前 generation 还未完全退出时准备下一 generation。单个 mbarrier 地址复用容易让不同 phase 混淆；实现使用双槽、mod-4 counter/phase 一类状态区分相邻 generation。具体初始化由 tid == 0 完成：初始化两个 slots 与 counter，并发 release fence；随后 default 与 extra worker warps 一起参加 cluster arrive/wait，保证初始化在入口分流前可见。不能写成“所有 worker warps 各自初始化”。

这仍不等于已有一个 SM103 输入从 frontend 自动分区一路贯通到 cta_group::2 runtime。冻结证据是“多个必要组件分别存在”，不是“组合性质已由一次 end-to-end launch 证明”。

20.1 本文能安全给出的总体判断

  • 显式 WS IR、persistent worker lowering、warp/register allocation：编译集成较完整；
  • canonical simple descriptor/TMA GEMM：冻结 Blackwell autoWS 最完整的中心 compile-time 路径；
  • automatic partition policy：明确、可用但仍是 loop-local coarse heuristic，不是 profile-guided whole-kernel scheduler；
  • attention、grouped、scaled、2CTA：有不同层次的源码与 focused/composed tests，不能据此给任意 shape 的公共端到端承诺；
  • 原研究为 compile-only，没有建立 exact-SM103 数值、无死锁、occupancy 或性能结论。

公开 tl.range 文档仍把 warp_specialize 口径限制在 Blackwell simple matmul loops；PyTorch 2026 roadmap 同时把更广 autoWS 描述为 limited/experimental、活跃开发主要在 Meta mirror 且只部分 upstream。教材因此始终把 public contract、冻结 upstream 与 roadmap 分栏。

20.2 “安全 no-op”只在部分早期边界成立

理想 fallback 是在第一次 mutation 前发现不适合分区并保留普通 pipeline。冻结实现确实对以下情况可安全 no-op：

  • marked loop 没有 eligible descriptor LOAD/STORE；
  • serialization/merge 后只剩 0 或 1 partition；
  • 函数没有任何 WS marker；
  • pointer-only loop 没有符合当前自动路径的 memory root。

但一旦进入 ARef/TMEM graph 深处，仍存在 assert/unreachable/fatal 范围：跨 partition cp.async payload、未知 region-bearing control flow、multi-result reduce、超过 two-owner 的 TMEM shape、TMEM subview NYI、某些未实现 completion-kind 组合等。不能概括成“所有不支持情况都会自动关闭 WS”。

20.3 编译通过到底证明了什么

冻结实验宣称 focused lit tests、pass-section counts、四个 SM103 变体的 compile/assemble/disassemble 均满足其结构断言；这些结果的原始 evidence/、lab/、research/ 目录没有随本次两份附件提供，因此新版保留数字时明确标为原研究报告的冻结记录，未在本次工作区独立重放。

结构 PASS 可以与 fence qualification gap 同时成立，因为 validator 检查“预先声明的 required/forbidden patterns”，不会自动证明完整 ISA contract。测试通过不是假的，只是结论范围必须精确。

21.3 原研究复现实验的正确分层

推荐把自动化拆成五个动作：

  • inspect：记录 commit、target、tool versions、input hashes、设备可用性；
  • compile：只调 triton.compile，不隐式加载/launch cubin；
  • trace：保存完整 pass-manager dump，并按 pass 切片；
  • disassemble：把 cubin 当作数据解码，不执行；
  • validate：把 required、optional、forbidden patterns 分开。

然后为每条断言打证据标签：DOC、SOURCE、TEST、IR、LLVM、PTX、SASS、RUNTIME、PERF。只有 RUNTIME 能回答数值/死锁，只有 PERF 能回答收益。

21.4 推荐的最小实验阶梯

  1. pointer-only matmul：验证 marker 可以安全 no-op；
  2. simple TMA matmul：验证 role/ARef/materialization 主线；
  3. mixed TMA + ordinary load：验证普通 load 留在 compute role 的 SWP；
  4. explicit ttg.warp_specialize skeleton：隔离后端 persistent worker；
  5. TMEM owner hand-off microcase：隔离 completion/order；
  6. multi-site function：验证 worker pool 复用与 exit broadcast；
  7. grouped/scaled/2CTA：每次只增加一个 lifetime 或同步域。

不要直接用 attention 作为第一份 WS dump；它一次增加太多 loop-carried state，任何一个中间 invariant 断裂都难定位。

22. 结课：把整条链压缩成一个可执行心智模型

现在回到开头的 canonical GEMM。你应能按以下顺序在脑中“执行编译器”：

  1. warp_specialize=True 只留下请求；
  2. 初次 schedule 给完整 loop 标时间 stage；
  3. eligibility 先确认有可分离的 descriptor memory roots；
  4. PartitionScheduling 从 data roots 出发过度切分，再按依赖、flags 与 cost 合并；
  5. cheap pure ops 可克隆，真正的跨角色 payload/owner edges 不可凭 SSA 穿越；
  6. Shared ARef 为 tile 建 backing + empty/full channel；TMEM ARef为同一 allocation 建 owner hand-off；
  7. LowerAref 把抽象事务结算成 ring views、mbarriers、TMA/commit/wait，并插入它能识别的方向性 fence markers；后续 ProxyFenceInsertion 继续做全局 proxy hazard 分析；
  8. PartitionLoops 克隆 structured control flow，按 role 剪枝并检查跨 role SSA 已归零；
  9. LowerWarpGroup 生成正式 ttg.warp_specialize，default 产生 results，workers isolated且只显式 capture；
  10. 第二次 schedule 把时间流水投影到各角色；Pipeline 物化 prologue/steady/epilogue；
  11. physical allocator 把 logical roles 填入 4-warp groups，复用一个全函数 worker pool；
  12. register allocator若预算可行，生成绝对额度的 setmaxnreg hand-off；
  13. LLVM lowering 构造 shared state、captures、named barriers、persistent switch和exit broadcast；
  14. target lowering 发出 TMA、TCGen05、TMEM、mbarrier/proxy/barrier 指令；
  15. 最后分别审计 completion、ordering、visibility、control、ownership与resource contracts，并把 compile、runtime、performance 证据分开。

可以把这 15 步再压成一个公式：

最终执行机=stage(iteration)⏟SWP 时间轴×partition(role)⏟WS 角色轴+ownership(storage)⏟ARef / TMEM+dispatch(resource)⏟persistent WG / registers \text{最终执行机} = \underbrace{\text{stage(iteration)}}_{\text{SWP 时间轴}} \times \underbrace{\text{partition(role)}}_{\text{WS 角色轴}} + \underbrace{\text{ownership(storage)}}_{\text{ARef / TMEM}} + \underbrace{\text{dispatch(resource)}}_{\text{persistent WG / registers}}

加号不是说四者独立运行，而是提醒你：任何一项都不能由另一项“顺便保证”。

22.1 五道结课自测

  1. 为什么 warp_specialize=True、多个 partition attrs、ttg.warp_specialize、额外 warps、最终 overlap 是五个不同结论？
  2. 对一条 TMA→Shared→MMA→TMEM→reader 链，分别指出 payload storage、owner credit、async completion、proxy visibility 与 TCGen05 inter-thread ordering。
  3. 为什么 partition0 num_warps(1) 仍可能让 kernel 增加 4 个 physical worker warps？
  4. actualRegisters[0] 属于谁？为什么进入 worker 不一定执行 .inc？
  5. 一个 case 有 frontend test、focused MLIR test、SM103 cubin，却没有 device launch。它能填满证据向量的哪些轴，哪些仍为空？

若你能不用术语替换术语，而是沿具体 storage object 和具体 event 回答这五题，就已经具备独立阅读下一版 Triton WS 源码的能力。

结课自测答案提纲
  1. marker 只表达许可；partition attrs 是策略结果；正式 op 是并发 IR 物化；额外 warps 是物理 allocator 的结果；overlap 还需运行时调度与足够独立工作。它们分属五道不同证据闸门。
  2. payload 在 Shared backing/TMEM allocation；empty/full 或 TMEM ARef 管 owner credit；TMA transaction mbarrier、MMA commit+mbarrier、wait::ld 管各自 completion；proxy fence 管 Shared 的 generic/async 可见性；tcgen05.fence::*thread_sync 管跨线程 TCGen05 execution ordering。
  3. logical partition 可小于 4 warps，但 setmaxnreg.sync.aligned 和 worker pool 按 4-warp physical group 管理；allocator 要补执行空 region 的 padding workers。
  4. actualRegisters[0] 是 default，worker i 位于 i+1；setmaxnreg 的 inc/dec 取决于当前绝对额度与目标绝对额度的数值方向，而不取决于“进入/退出”这个词。
  5. frontend/focused test 可填 A/B，协议 fixture 可填 C，SM103 cubin 可填 D；没有设备 launch 时 E/F 仍空，没有 profiler/benchmark 时 G 也空。

WS warp specialization：让同一执行时间中的不同角色由不同 warp partitions 推进 不等于 PTX tcgen05.mma.ws；该后缀的 ws 是 weight stationary
stage CoarseSchedule 中的跨 iteration 时间偏移，也是 circular buffer slot/latency 推导的重要输入 stage 不是 worker dispatch state，也不是 CTA cluster
schedule cluster 同一 stage 内用于保持不可交换依赖顺序的编译器调度 cluster 与多个 CTA 构成的 hardware CTA cluster 完全不同
phase / parity mbarrier ring buffer 复用时区分不同 generation 的状态；通常随 slot wrap 翻转 不是 partition ID，也不是 software stage 的同义词
TMA Tensor Memory Accelerator 的 bulk tensor data path；descriptor 携带地址、shape、stride、tile 等信息，一个 elected thread 可发起宽 tile 搬运 TMA 不是 tcgen05.cp；后者是 SMEM/TMEM 相关的 TCGen05 data movement
tensor descriptor / tensormap TMA 使用的 tensor map 描述对象；动态创建或更新时有独立的 storage lifetime 与 tensormap-proxy ordering descriptor 的 fence 不等于 payload copy 的 completion
TMEM Blackwell Tensor Memory；可视作 CTA 的 128 lanes × allocated columns 的 Tensor Core 专用片上空间 不是普通 register file，也不是 Shared Memory；MMA 结果进入 TMEM 后仍需 completion 和 ordering protocol
TCGen05 第五代 Tensor Core 指令族，包括 allocation、MMA、commit、fence、TMEM load/store/wait/copy 等 不是单一“Blackwell MMA 指令”的简称
ARef NVWS 中的 asynchronous-reference channel abstraction；把跨 partition 的 SSA dependency 物化为 Shared payload channel 或 TMEM ownership channel 不是硬件指针或最终 ABI；正常 LowerAref 后必须消失
empty/full credit ARef one-slot channel 的两种所有权状态：producer 等 empty 才能写；consumer 等 full 才能读；consumer 结束后归还 empty mbarrier 不只是“等数据”的事件，它也承担 slot reuse credit
completion 某个异步操作已经完成，例如 TMA transaction bytes 清零、TCGen05 MMA 被 commit/mbarrier 观察、TMEM load 被 wait::ld 完成 completion 不自动建立所有跨线程 TCGen05 ordering，也不自动修复不同 memory proxy 的可见性
execution ordering 确保某线程/角色之后发出的 TCGen05 operation 排在另一事件之后；TCGen05 有专用 before/after thread-sync fence 普通 CTA barrier 或 mbarrier wait 不应被无条件视为专用 TCGen05 fence 的替代品
proxy visibility generic、async、tensormap 等 memory proxy 对同一 storage 的访问可见性关系 即使 producer/consumer 已 rendezvous，跨 proxy 仍可能需要 fence
mbarrier 位于 Shared Memory 的运行时 barrier object，维护 phase、pending arrivals 与 expected transaction bytes 它不是编号 0–15 的 named CTA barrier
named barrier CTA 内编号 0–15 的 barrier resource；WS lowering 将其用于 default/worker control protocol 和 partition-local barrier handles 不追踪 TMA transaction bytes，也不跨 CTA
requestedRegisters OptimizePartitionWarps 给 worker partition 的启发式寄存器请求；冻结实现常见 guess 为 24 或 88 不是 ptxas 精确寄存器证明，也不等于实际 occupancy
actualRegisters AllocateWarpGroups 在预算可行时生成的 [default, worker0, ...] 每线程寄存器额度 与 requestedRegisters[i]、warpGroupStartIds[i] 的索引约定不同
persistent switch loop extra worker warps 驻留的 LLVM CFG；通过 shared i8 state 接收多个顺序 WS sites 的 dispatch，执行后回到 switch 不是在 kernel 入口只分支一次的静态 if/else

B.6 正常 pipeline invariant 与 dialect-wide legality 的区别

正常 AutomaticWS provenance 保证：非空backing、配对enter/exit、非空completion、同构buffer results、最多two-owner中心形状、第一role具备正确yield、workers具备return。当前verifier没有完全证明这些事实。

因此应采用两种不同措辞：

  • 可以说： 受控 AutomaticWS pipeline 正常会消费全部 NVWS transient IR。
  • 不能说： 任意能parse/verify的手写NVWS module都已被一个dialect conversion完整证明可lower。

典型未封闭边界包括：zero backing、同一buffer被多个ARef拥有、空async_ops、错配pairing token、aref.buffer错误result数量/types、zero-region warp group、worker terminator位置、root加两个explicit TMEM owners。它们是需要verifier/negative tests的边界，不应未经复现写成已确认runtime bug。

C.6 容易在主线中被压掉的调度与分区精确条件

分区后第二次 schedule 的精确行为

ScheduleLoops.cpp::getInitialSchedule 对已分区 role loop 重新统计 latency-bearing stages。集合大小不超过 1 时，它不是保留一份有空洞的旧 schedule，而是重建 numStages=1、把该 role 的 operations 归入 stage 0；有多个有效 stages 时才 shrinkToFit。这只关闭该 role 内无收益的 SWP，不撤销不同 roles 的并发。

第二次 schedule 还有 correctness 作用：PartitionLoops、ARef lowering 和 structured-control-flow rewrite 已改变同 stage 内的文本次序，需要再按 SSA/side effects 排序，避免 operation 出现在 operand 之前。冻结实现暂时不能原生表达“每个 partition 各有一份 stage/cluster metadata”，部分 TMEM ARef 路径从同 partition 前一 access 搬运 stage/cluster；源码还留有“所有 latency ops 应已有 schedule entry”的窄 FIXME。

AssignMMALatencies 的普通基线是可重叠 MMAv5 self_latency=1。进入 WS scope 后至少有两组独立检查：

  • hasAccReadModifyWrite 检测 MMA→TMEM load→ordinary compute→TMEM store→next MMA，清除 op tt.latency；
  • hasLoopCarriedAccumulatorCycle 检测经过另一 MMA 回到当前 MMA 的 cross-MMA cycle，也清除 op latency，而且该检查不只作用于 WS loop；
  • fully specialized operand chains 可把 self_latency 降为 0；mixed ordinary-load chain 保持非零，使通用 lower-loop 路径建立 completion barrier/wait。

focused attention 例子还固定了更具体的组合：persistent inner-loop 的 QK MMA 为 latency=2,self_latency=0；PV accumulator 因 RMW 没有 tt.latency，但仍可保持 self_latency=0。数值是冻结 fixture 的策略结果，不是 TCGen05 硬件延迟。

PartitionScheduling 的完整阶段顺序与阈值

去掉 bookkeeping 后，冻结顺序是：

mark/propagate data roots
→ duplicate multi-use views
→ deserialize manual partitions
→ each unassigned data node gets its own partition
→ edge merge fixed point
→ partition-pair merge fixed point
→ propagate backward to index/control
→ assign IDs with MMA/load off default
→ assign no-use operations
→ propagate again to enclosing structured nodes
→ duplicate cheap leave-and-return paths
→ eligibility/serialize attrs
→ cloneMultiPartitionDataOps after serialization

第二次 propagation 不是重复：assignPartitionsForOpsWithNoUse 新增的归属必须传播给 enclosing regions。connected merge 的冻结阈值是 payload 超过 16384 elements，且不跨 LOAD/MMA 边。SFU cloning predicate 可以接收 SFU candidate；isCostlySFU 只影响某些 merge，不能误写成 cloning 的统一门槛。

D.2 TCGen05 canonical 因果链

  • tcgen05.commit与此前同线程发起的tcgen05.mma/cp/shift隐式pipeline；
  • commit隐含before_thread_sync一侧，因此canonical MMA→commit pattern不需另发before fence；
  • mbarrier.try_wait观察completion；
  • 因后继tcgen05.ld本身是异步operation，仍需tcgen05.fence::after_thread_sync；

D.3 ARef one-slot 与 ring-buffer 协议

producer:
  wait(empty[slot], phase)
  write payload / issue TMA
  publish full[slot]

consumer:
  wait(full[slot], phase)
  use payload
  return empty[slot]

多buffer只把这条状态机按stage排成ring。LowerAref对每条channel执行：

  1. 根据unique producer/consumer groups和async kind算arrival count；
  2. 为每个slot分配empty/full mbarriers；
  3. 初始化，并在生命周期末invalidate/dealloc；
  4. put-enter→empty wait，get-enter→full wait；
  5. stage选择slot view，phase区分generation；
  6. TMA producer累加txCount并发barrier_expect；
  7. exit按kind变为普通arrive、TCGen05 commit或hardware TMA arrival；
  8. 必要时插generic/async proxy fence；
  9. 逆use-def擦除ARef/descriptor bridge，用poison收口pairing token。

普通Shared ARef初建depth为1；只有含descriptor destination op的global-to-shared producer channel按numStages multibuffer。TMEM channel是否depth 2由access DAG独立决定。

AssignStagePhase 的实际初态不能压成 producer/consumer 共用一个 generation 公式：初始 stage=depth-1，put phase=0、get phase=1；每次 enter 先推进 stage，wrap 时 xor phase。稳妥直觉只有 slot = iteration mod depth 与“绕环时 phase 翻转、两侧初态互补”。

D.4 named barrier 编号

ID 冻结WS lowering中的用途
0 kernel/default上下文中原有local barrier的warpgroup handle
1 default与全部workers的switch-loop状态发布、capture交接、完成与kernel退出
2 + partitionIdx 该worker partition内部原有local barrier或相关调用的handle

每CTA只有16个named barrier IDs。只有某个worker region确实需要partition-local handle且partitionIdx + 2 >= 16时才触发明确diagnostic；没有local barrier的partition不会仅因存在就消费一个ID。一warp local barrier可降为bar.warp.sync。

PTX artifact可能同时出现barrier.sync和legacy alias bar.sync，应按具体lowering path和上下文解读，不把某一种拼写称为唯一“当前拼写”。

switch barrier 上至少有三个逻辑 rendezvous，不能合并成“发布/完成”两步：default 发布 state/captures；workers 读完 captures 后确认 transport scratch 可复用；最后 default warp_yield 与 worker warp_return 再做 role join。第二个时点只证明 capture 已读取，不证明 worker body 已完成。

D.5 cluster 双槽协议

位于ttg.warp_specialize中且needsClusterBarrier(op)为真的top-level default/worker region，每个实际分配的region占：

kClusterBarrierMbarSlotSize       = 16 bytes
kClusterBarrierMbarBufferCount    = 2
kClusterBarrierMbarAllocationSize = 32 bytes

同一region内多个qualifying operations复用这32 bytes；不同regions各有allocation。qualifying operations包括显式cluster barrier、部分distributed layout/reduction、multi-CTA TMEM/TMA形态，以及需要cluster ordering的multi-CTA atomic/atomic_poll。

lowering使用mod-4 counter：

slot   = counter & 1
parity = counter >> 1
next   = (counter + 1) & 3

两个slots延长同一mbarrier的复用间隔；读取shared counter前的CTA barrier让所有warps取得同一(slot,parity)快照；elected thread更新counter后的第二个CTA barrier阻止部分warps过早进入下一generation。双槽、mod-4 counter和前后CTA barriers必须作为一套协议理解。

InitializeWSClusterBarriers在LLVM function entry由每CTA thread 0初始化两个mbarriers、写counter、发init-release fence，并通过临时覆盖全部workers的WS结构，让default和persistent worker warps共同完成cluster arrive/wait；随后正常WS lowering再把该临时结构并入persistent dispatch。

D.6 setmaxnreg 的硬件合同与冻结 lowering

PTX ISA 9.3给出的精确约束：

  • .inc从CTA register pool获取更多寄存器；不足时会阻塞，新获得寄存器内容未定义，使用前必须初始化；
  • .dec归还额度；
  • immediate在24–256之间（含边界），且必须是8的倍数；
  • kernel launch必须带有效的per-thread maximum register配置，否则instruction可能无效果；
  • .dec N前，warp当前maximum应大于等于N，否则行为未定义；
  • .inc N前，warp当前maximum应小于等于N，否则行为未定义；
  • .sync要求warp内所有threads执行同一指令后再继续；
  • .aligned要求physical warpgroup内所有warps执行同一指令；条件执行时所有threads/warps必须一致； -一次setmaxnreg后，在同一warpgroup执行下一次之前，所有warps必须显式同步。

冻结 lowering 的 createRegRealloc(curRegs, adjRegs)：

  1. 两个值先各自clamp到256；
  2. 若adj < cur发decrease，否则发increase；
  3. clamp后相等也落到increase分支。

典型状态转换：

kernel initial maxnreg
  workers → lowRegs
  default → defRegs

worker dispatch
  lowRegs → physical group actualRegisters
worker return
  actualRegisters → lowRegs

default跨某WS site
  defRegs ↔ 该site actual budget

常见lowRegs=24、active worker额度更高，故entry-inc/return-dec；但dynamic_register_reallocation_overalloc中lowRegs=80、partition actual=24，方向恰好相反。教材和测试不得把方向硬编码。

若register budget、完整physical warpgroup、default leftover等条件不满足，AllocateWarpGroups仍生成start IDs/total warps，但不写actualRegisters，因此保留WS控制结构而省略dynamic register protocol。任一WS带tti.disable_setmaxregister时，LLVM lowering会对整个kernel关闭动态重分配；assert/print或instrumentation可把最低预算从24抬到32。

D.7 TMEM alias barrier 与 completion 的边界

TMemBarrierInsertion按allocation slice alias分析同步访问：

  • load→store；
  • store→load；
  • store→store；
  • load→MMA；
  • store→MMA。

非alias slices不插。MMA→TMEM load/store不由该pass重复插一层CTA barrier，源码理由是已有MMA completion wait会阻止访问过早发生。该过滤规则只说明alias-hazard pass不重复记账，不能反证专用after_thread_sync fence已生成。

D.8 ConSan 能与不能证明什么

ConSan理解ttg.warp_specialize execution scopes、default/worker thread classes、shared/TMEM access effects、TMA/TCGen05 completion barrier、proxy frontier和mbarrier lifecycle。关键能力包括：

  • 为workers预留并验证consan.extra_capture_bytes；
  • active role mask按CTA运行时建立，role完成后退休，kernel exit清除；
  • async read/write先挂到对应completion object，成功wait后才发布；
  • generic→async即使read→read也保守要求proxy fence；
  • cluster barrier只向其他CTA中的matching logical partition发布visibility，而非广播给所有roles；
  • init前检查旧mbarrier lifecycle已结束，wait/arrive前检查已初始化，invalidate清除tracking。

它是高层IR语义防线，不是final PTX的完整证明。它不会凭空生成或验证冻结实现缺失的tcgen05.fence::after_thread_sync。

D.9 Shared/TMEM ARef 的 producer、consumer 与合并边界

Shared ARef 的 getProducedValues 读取 ttg.partition.outputs，跳过原 async dependency token，只把真正的 tensor/scalar/memdesc payload 作为候选。若 produced value 是 loop block argument，getStageClusterForProducer 会沿 scf.yield 回溯真实 producer；否则 attention 的 m_i/l_i/acc 会失去 producer stage。

consumer interval 也不是 direct users 的文本范围：getTransitiveConsumers 递归穿过 memdesc views，并把“loop 外定义、loop 内使用”的 enclosing loop 计作 consumer；exit placement 同时依赖 CFG post-dominance 与 pipeline first/last stage-cluster。值定义在 scheduled inner loop 外时仍可建 channel，但 pass 不强行从该 loop 推导 enter/exit schedule。

LowerAref::combineArefs 只有在 dominant consumer、consumer partition 与 producer partition 等条件一致时才合并 TMA channels，不能把所有同 shape buffers 任意并成一组 barrier。历史上 arrive 被重排越过真实 local_load 曾造成 silent wrong result；冻结提交已做定向修复，这一事件证明 last-use/reordering 是 correctness 边界，不表示旧错误仍存在。

TMEM access DAG 通常沿 token 展开，但带 src 且没有 token 的 TMEMAllocOp 有单独分支：实现要求它只有一个 user，并把该 user 直接接到 root。nested DAG 的“最近一次 async op”又按 (partition, wsTag) 保存；否则内层同步 NONE 可能覆盖外层 TC5MMA，让最终 release 丢失应有 completion kind。

E.5 Advanced case 1：scaled / blockscale

数据与owner边

在tokenized focused fixtures中，TCGen5MMAOp与TCGen5MMAScaledOp的result 0都是accumulator dependency/mod-ref data root；后继TMEMLoadOp的data/token results也被标为data。该token用于partition和ownership顺序，不是completion barrier。

scale至少有三种来源：

  1. 已常驻Shared，直接作为scaled MMA operand；
  2. descriptor/TMA载入Shared，再reshape/transpose；
  3. 写入#ttng.tensor_memory_scales编码的TMEM，并以独立TMEM ARef转移owner。

一个scaled MMA周围可同时存在：A/B payload Shared channels、A/B scale Shared或TMEM channels、accumulator TMEM owner channel、MMA dependency token。不能简化为“普通MMA多两个operands”。

buffering与async化

  • Shared TMA payload可按numStages扩展；
  • TMEM accumulator的2-stage buffering由access DAG与disallow_acc_multi_buffer决定；
  • LowerAref::setIsAsync仅在loop且numStages>1时考虑异步；scaled MMA还要求两个scales的provenance都可pipeline；
  • 任一scale不可pipeline时保守同步；SyncMMALowering仍可把它改为带completion barrier的async hardware form，并立即wait/invalidate，因此“最终看见TCGen05+barrier”不等于存在跨stage overlap。

最终conversion覆盖block_scale.block16、block_scale.block32以及FP8/FP4/NVFP4/MXFP4、TMEM LHS等组合，但冻结树没有一个scaled frontend输入贯穿完整AutomaticWS→exact-SM103 artifact的单一fixture。

E.6 Advanced case 2：2CTA / cluster

必须分开三层：

  1. CTA内部WS dispatch；
  2. TCGen05 MMA completion与后继TCGen05 ordering；
  3. cluster内协作CTA rendezvous。

tc_gen5_mma_2ctas focused conversion要求ttg.num-ctas=2、ttng.two-ctas=true并生成tcgen05.mma.cta_group::2和cluster/multicast commit。cluster analysis还覆盖distributed layout conversion/reduction、multi-CTA TMEM copy、multicast TMA、cross-CTA barrier与部分atomics。

现有证据是组件束：two-CTA instruction form、cluster hazard analysis、double-slot allocator、all-warps init各有fixture，但没有单一SM103输入同时闭合autoWS、hazard insertion、allocation、initialization和最终cta_group::2 PTX，更没有设备launch/residency结果。

E.7 Advanced case 3：persistent attention

Python shape是outer tile-claim loop带marker，inner K/V loop本身无marker，却包含QK MMA、TMEM load、max/sum/exp2、V load、P×V MMA以及m_i/l_i和两条accumulator tokens。isWarpSpecialized必须沿ancestor scf.for识别outer scope，否则inner MMA会走普通非WS latency逻辑。

persistent PartitionScheduling fixture直接证明inner loop有四个partition IDs及部分output membership，但没有固定每个descriptor load/MMA的完整partition，因此不能仅凭编号给所有roles永久命名。较小attention fixtures再分别覆盖Shared ARef、TMEM ARef、LowerAref和AutomaticWS；它们与persistent Python source不是同一输入的端到端provenance。

Python integration还含shared-memory skip条件。部分BLOCK_M=128, HEAD_DIM=128、非FP8 warp/stage组合会因资源需求跳过。disable_acc_multibuf虽然被参数化，原测试函数却没有真正读取/传递该参数，不能把两个参数值计为两种行为覆盖。

E.8 Advanced case 4：grouped GEMM

关键不是另一种矩阵shape，而是每个group iteration动态读取A/B/C base与strides，并在persistent loop中重建tensor descriptors。旧TMA仍可能引用某descriptor storage时，下一iteration不能覆盖它。

冻结实现：

numDescs = numStages + 1
CoarseSchedule(numDescs + 1)

第一个+1是真实额外descriptor buffer，为下一update与最老in-flight TMA重叠；第二个+1只是CoarseSchedule使用“最大stage+1”的构造约定，不表示再多分配一份descriptor。

Python kernel与同名TTGIR fixture存在实质差异：Python动态读取g_lds且测试使用num_stages=3；TTGIR fixture固定stride 1024、AutomaticWS RUN用num-stages=2。同名只能关联设计shape，不能证明frontend逐字产生该TTGIR。现有Python group shapes也同构，不代表任意heterogeneous ragged groups。

E.9 历史 hardening 的正确使用方式

冻结日前曾出现并随后定向修复的风险样本包括：低于四warps allocator crash；arrive越过local_load造成silent wrong result；没有MMAv5的marked loop进入ARef深处；attention yield/第三partition；small-tile repeated-user cloning；multi-CTA exit与phase snapshot。

这些历史材料证明系统经历了真实correctness/robustness hardening，不证明冻结提交仍复现旧错误。反之，某个PR已合入也不证明相邻未测shape均已production-ready。

E.10 三组不可从主叙事删掉的 focused facts

显式 WS + TMEM

python/test/unit/language/test_warp_specialization.py::test_warp_specialize_tmem_ir 手写两块 TMEM allocations，并作为 explicit captures 传给三个 worker regions；只有 4-warp 的 partition 2 执行 tmem_load(in) → tmem_store(out)，default 在 WS 返回后再从 out 读回并写 global。它绕过 AutomaticWS/TMEM ARef，只证明 TMEM memdesc 能跨内部 WS region contract 传递，以及 allocator/lowering 能统一分析外层、default 与 workers 的 concurrent lifetimes。能复用的 allocations 可共享 column offset；同时存活的 allocations 必须得到不同 offsets；capture 指向同一 allocation，不是在 worker 中复制一份 TMEM。

OptimizePartitionWarps 的算法而不只是 24/88

pass 把每个 partition region 临时取进独立 function，取最大 RankedTensor 的 i32-register footprint 并乘 2，假设最大 tensor 约占 warpgroup register usage 的一半；再以每 SM 64K 个 32-bit registers 作粗预算，尝试把 partition warp 数逐次减半。只有缩小后 per-thread tensor footprint 仍小于估算额度才接受；warp 数变化后必须清 layout，并以新 warp 数重跑 ConvertTritonToTritonGPU + Relayout + Coalesce + AccelerateMatmul。

最终 24/88 只按“region 是否有非零 tensor footprint”猜测，而不是由 TMA/MMA/reader 角色名字直接决定。没有 tensor computation 的 role 可缩到 1 warp；TMA role 当前至少 2；TMEM load/store/alloc role 当前至少 4。这些都是冻结 compiler policy，不是 PTX 普适法则。

attention、scaled 与 exact target 的窄差异

persistent attention focused partition fixture 的 inner-loop outputs 是：

partitions = [0,1,2,3]
outputs    = [[0], [0], [2], [1]]

直接固定的是：QK TMEM load/softmax register work 在 0；accumulator load/rescale/store 在 1；QK async-token output 映射到 2；outer tile_idx += num_sm 在 3。fixture 没有固定每个 descriptor load/MMA 的完整 membership，因此不能把 2 永久命名为 waiter/TMA role。当前设计也没有强制另建专职 completion-waiter role，真实 consumer sets 决定观察 completion 的位置。

scaled path 有一个必须保留的 slot race：reader 取出 scale 后，下一 iteration producer 可能覆盖同一 slot。异步 scale load + 同步 scaled MMA 是合法的保守组合，因为同步消费点仍位于 empty credit 归还前；setIsAsync 的 scale-provenance 检查决定能否放宽，而不是决定 scaled MMA 是否“支持”。

最后，cc100-focused tests不能冒充 exact-SM103：冻结 TargetFeatures 中 i8 TCGen05 MMA 仅 cc100，ld.red 从 cc103 开始，FP4 padding 又单独枚举 100/103。大量 cc100 fixtures证明共享 pass 路径的局部合同；只有 GPUTarget("cuda",103,32) artifact补 exact-target 轴，而且只覆盖实际编译的 cases。

G.1 流水线与不可越过的安全边界

inspect
  → compile
  → trace
  → disassemble

共同target：

GPUTarget("cuda", 103, 32)

原harness只接受--target sm103。_require_target在导入Triton前拒绝其他alias；所有编译入口，包括trace child worker，都在_compile_case中重新检查source、target与safety。编译环境设置TRITON_BACKENDS_IN_TREE=1，清除外部pass/backend plugins、target override及MMA/LLVM/PTX/codegen环境开关；构造ASTSource后再次清理。最终检查constructed target必须精确等于("cuda",103,32)。

它调用triton.compile并读取compiled.asm，不索引compiled kernel，不调用.run、__getitem__、binary loader或lazy _init_handles，因而按冻结CompiledKernel调用图不进入driver query/load_binary路径。compile.json中的cubin_loaded:false、cubin_launched:false是附加attestation，不是独立硬件测量。

G.2 inspect

cd docs/blackwell-warp-specialization/lab
python3 ws_study.py inspect
python3 ws_study.py inspect --json

检查内容：

  1. manifest schema、locked target、case与required/optional/forbidden families；
  2. Python fixture路径、入口与SHA-256是否命中reviewed allowlist，并做AST safety scan；IR fixture是否声明ttg.target = cuda:103且无其他CUDA target；
  3. compiler tree是否存在冻结commit之外、学习包以外的源码改动；
  4. in-tree Triton Python/native extension、triton-opt、Blackwell ptxas、cuobjdump、nvdisasm是否可用；
  5. git revision、manifest hash、source hashes与compile readiness。

AST scan拒绝非Triton imports、subscript-call形式的JIT launch、受限顶层node之外的语句，以及已知load/run/launch/dynamic-eval patterns。它不是通用Python sandbox：import与decorator仍会执行，digest allowlist才是主要信任边界。

compile_ready只表示当前checkout的API/native extension可进入编译且Blackwell assembler可用。harness记录native binary路径与SHA-256，但不能从binary内部密码学证明其source-build revision。

G.6 validate

_evaluate_record要求：

  1. record target为cuda:103:32；
  2. compiler metadata target精确为("cuda",103,32)；
  3. status为compiled-not-launched；
  4. artifacts存在、非空且hash匹配；

Family 强合同
warp_specialize TTGIR有正式op与register request；trace还要有op、warpGroupStartIds、actualRegisters

tma final PTX同时出现bulk tensor copy与tensormap；只命中descriptor mutation或单一cp.async不够

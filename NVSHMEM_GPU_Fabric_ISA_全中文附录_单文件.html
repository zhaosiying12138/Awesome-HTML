从 NVSHMEM 到 GPU Fabric ISA：为 Device-Initiated CCL 设计通信、计算与同步指令

面向懂 GPU/ISA、但还不熟悉网络的硬件与编译器读者

版本与边界。 本文以 2026 年 8 月公开资料为基线，重点对应 CUDA 13.3、PTX ISA 9.3、NVSHMEM 3.7.x 与 NCCL/NVLink SHARP 的公开语义。“PTX 9.3 已有”只表示公开 PTX 文档已有相应能力；“本文新增”是为完整承载 NVSHMEM/device-initiated CCL 而提出的 transport-neutral ISA，不代表 NVIDIA 现有产品。文中的 net.* 均是提案助记符。

一句话结论。 支持 NVSHMEM 的关键不是把 IB verbs 或 NVLink packet 搬进 GPU ISA，而是把“受保护的远端地址、单边 RMA/AMO、发布与等待、排序与分层完成、独立 ordering domain、组播/归约、错误与进度”做成正交语义，再让 NVLink、CFT、RDMA QP 或未来 fabric 成为这些语义的后端。

一、为什么 device-initiated communication 会成为 GPU 的基本能力

1. 传统 host-driven CCL 的边界

经典 GPU 程序把一次分布式迭代切成若干 kernel 与 collective：kernel A 计算，CPU 或 CUDA Graph 发起 NCCL all-reduce，通信结束后再启动 kernel B。这个模型非常适合大而规则的 collective，因为库可以在完整 tensor 上选择 ring、tree、NVLink SHARP 等算法；但每个“计算—通信”边界都会固化调度粒度。GPU 已经知道一个 tile、一个 token bucket 或一个 halo 何时就绪，却仍需等到 kernel 边界，由 host 或独立通信 kernel 重新发现这件事。结果通常不是网络带宽不足，而是启动延迟、全局同步、临时缓冲和无法细粒度重叠占据了端到端时间。

Device-initiated communication 把发起权放回正在执行的 GPU 线程、warp 或 CTA：某个 producer warp 刚算完 16 KiB tile，就可直接 put 到远端并发布 signal；consumer GPU 等待该 signal 后立即计算，无需让整张 GPU 退出 kernel。更激进的 persistent kernel 或 MegaKernel 会在一次长驻执行中完成路由、传输、归约和 GEMM，通信由数据依赖触发而不是由 host 时间线触发。这不是“把 NCCL kernel 写得更长”这么简单：编译器和硬件必须能表达远端地址、异步提交、不同层次的完成、跨设备发布—获取关系以及失败。

2. NVSHMEM 有什么用

NVSHMEM 是面向 NVIDIA GPU 的 OpenSHMEM 风格 PGAS 库。它让一个 GPU processing element（PE）对另一个 PE 的 symmetric object 执行 one-sided put/get/atomic；目标 PE 不必同时执行匹配的 receive。它还提供 signal、wait/test、barrier、team collective 和 ordering API，因此应用能直接在 device code 中搭建 producer/consumer 与 collective 协议。其价值不是“又一套 MPI”，而是把跨 GPU 数据移动降到可嵌入普通控制流的内存操作：一个线程可以在分支里更新远端 counter，一个 warp 可以传一个稀疏 token bucket，一个 CTA 可以把 shared-memory tile 直接送走。

典型用途至少有五类。第一，Triton-distributed 之类的系统把通信 primitive 引入 DSL，使 distributed GEMM、reduce-scatter、attention 或 MoE 路由能够与计算融合，而不是从 Triton kernel 返回 host 后再进入 CCL。第二，persistent/MegaKernel 把多个算子、调度器与通信循环放进同一 kernel，以 signal 和远端队列推进流水。第三，MoE expert parallelism 需要先用远端 atomic 分配 expert buffer 偏移，再把大小不一的 token bucket 发给不同 GPU，并在每个 bucket 就绪时立刻消费；它天然比整 tensor collective 更细碎。第四，stencil、halo exchange、图计算和 AMR 的邻居集合或消息长度不规则，one-sided RMA 能避免匹配 receive。第五，分布式 work queue、参数/缓存服务和 task stealing 依赖 fetch-add、CAS 与细粒度通知，无法只靠 bulk all-reduce 表达。开源项目如 Triton-distributed、FlashMoE、mKernel 展示了这些方向；它们的具体 transport 不必相同，但都说明 kernel 内通信已成为编译目标，而不仅是库调用。超节点把这项需求放大：当 72 张甚至更多 GPU 位于一个低时延 scale-up domain 中，tensor/expert parallel 可以不再以 8-GPU server 为天然边界，但 O(P)O(P) peer 状态、O(P2)O(P^2) 小消息、全域 barrier 与故障传播也会迅速成为首要架构问题。

3. “支持 NVSHMEM”不等于每个 API 一个 opcode

NVSHMEM 包含初始化、PE 查询、symmetric allocation、team split、host/on-stream/device API、不同 datatype 和 thread-group 变体。逐个复制成 ISA 会把软件策略与 ABI 永久固化，也无法服务其他 CCL。更合理的分工是：driver/runtime 在 host 侧建立 PE、team、symmetric heap、注册内存、endpoint 与 context；device ISA 只承载可观察的基本语义；NVSHMEM、NCCL Device API 或 DSL runtime 再把 API lower 成这些 primitive。譬如 nvshmemx_float_put_block 与 nvshmemx_putmem_warp 的核心都是“合作式 one-sided copy”，不同之处主要是 datatype、issuer scope 和字节数，应该由修饰符与编译器处理。

真正不可下放成“不透明实现细节”的，是程序能观察到的语义：data 是否已离开 source buffer，是否已在 destination PE 可见；一个 signal 是否严格晚于它发布的数据；两个 context 是否彼此独立；一次 fetching atomic 的旧值何时可用；错误是否可能发生在异步返回之后。本文会先建立这些宏观类别，再讨论 PTX 已经公开了什么，最后给出完整的统一 ISA。

二、先从 GPU 视角补齐网络基础

1. Scale-up 与 scale-out 到底差在哪

“Scale-up”通常指一个高带宽、低时延、强连接的 GPU fabric 域，例如同一 NVSwitch island 内的多 GPU；“scale-out”通常指跨主机、跨机架、经 InfiniBand 或 RoCE NIC 扩展。两者不是以机箱边界定义的自然定律：多节点 NVLink fabric 会模糊物理边界，未来 NIC 也可能提供更强的 load/store 或 collective 能力。对 ISA 更有意义的区分是 capability profile：目标是否能被 load/store 映射，是否需要注册密钥，发起是否经过显式队列，链路是否提供可靠重传，是否支持 multicast/reduction，以及完成事件能证明到哪一层。

在 NVLink/NVSwitch 路径上，peer memory 常可进入 GPU 虚拟地址空间，SM 的 ld/st/atom 或 copy engine 可以像访问一种 system memory 那样发起请求；NVSwitch 负责路由，NVLink SHARP/NVLS 还可为 multicast 与固定归约提供 fabric primitive。对程序员而言它接近“远端内存”。在 IB/RDMA 路径上，NIC 通常要求本地与远端内存先注册，发起者在 queue pair（QP）的 send queue 中放置 work queue element（WQE），写 doorbell，NIC 再携带 remote virtual address 与 rkey 发出 RDMA request。对程序员而言它更接近“用 descriptor 驱动的远端 DMA”。两者最终都能实现 put/get，但地址、提交、完成、错误和性能粒度不同。

2. 超节点：介于单机与集群之间的新计算尺度

本文把**超节点（supernode）**定义为：跨越一个或多个 compute tray/OS node、以有界 scale-up fabric 连接、可被发现、授权、调度和隔离为紧耦合加速器域的系统。它是架构定义，不限定某个品牌、机柜数、GPU/NPU 数或一致性协议。Huawei Cloud 的官方定义也允许由单台或多台高性能 AI 服务器构成；UALink 1.0则把类似边界称为 AI computing pod 内的 scale-up memory fabric，并面向最多 1,024 个 accelerator。NVIDIA 正式资料更多使用 rack-scale system、NVLink domain/partition 等词。本文用 NVIDIA 平台深入机制，但不是把“超节点”偷换成某个 SKU。

当前具体锚点中，GB200 NVL72 的单 rack 72-GPU 配置以 18 个 compute tray（每 tray 4 GPU/2 Grace CPU，并运行各自的 OS image）与 9 个 NVLink switch tray，把 72 张 GPU 组成一个 NVLink domain；每个 switch tray 含 2 颗 NVSwitch，所以这一实例共有 36 颗 Grace CPU 与 18 颗 NVSwitch。物理上它是多节点系统，算法上却能做全域 GPU-to-GPU scale-up 通信。物理 rack 也不是定义边界：IMEX guide同时列出 single-rack 72-GPU 与 dual-rack 36-GPU×2 配置，而 DGX SuperPOD 的 compute fabric 在不同 NVL72 系统之间使用 InfiniBand；NVIDIA 另有使用 Spectrum-X Ethernet 的多 rack reference architecture。因此 vendor-neutral ISA 应写成“经 NIC 进入 scale-out fabric”，而不是把 rack 边界、IB 或 Ethernet 任一种固化成定律。到 2026 年公开的 Vera Rubin NVL72 仍延续“rack-scale domain 是紧耦合基本单元”的方向。产品数字会演进，ISA 不应把 72、18 条 link 或某代 switch 数写进编码。

超节点既不是“一颗拥有统一 HBM 的大 GPU”，也不是普通的松耦合集群。每张 GPU 仍有自己的 HBM、MMU、执行与故障状态；PGAS 恰好提供“分区但全局可寻址”的正确模型。它也不能被简化成均匀 UMA：距离、switch path、partition、peer mapping、multicast membership 与故障域仍会影响 capability 和算法。超节点最有价值的用法是把过去跨 server 的 tensor parallel、MoE expert exchange、KV/cache 访问和 collective 放入更低时延域，同时用 device-initiated pipeline 消除 rack 内几十次 host 边界。

从 ISA 角度，超节点带来六项额外压力：第一，endpoint/rank table 必须可分层、压缩或间接寻址，不能让每个 SM 保存几百份 raw transport state；第二，要有 group/multicast endpoint 与 push/pull reduction，否则 broadcast/all-reduce 退化为 P−1P-1 次单播；第三，context/credit/QoS 必须避免一个拥塞 peer 或大 collective 阻塞整个 rack；第四，completion 要按 event/epoch 聚合，不能每个 packet 一个 token；第五，barrier、collective launch 与 wait 要支持大 team 的可抢占进度；第六，错误必须报告 failed member/partial group，支持 partition 与 fault containment，而不是任一链路错误让全 rack 永久 hang。这些要求会在后文的地址、同步、collective、RAS 与手册中分别落到具体指令。

3. GPUDirect 不是一种网络

“GPUDirect”是一族减少中间拷贝或 CPU 热路径参与的技术名称，不能与 NVLink、RDMA 或 GPU-initiated networking 互换。理解它最稳妥的方法是拆成三条正交轴：payload 走哪里、每次操作由谁提交、哪个事件证明哪一级完成。GPUDirect RDMA 主要改变第一条轴；GDAKI/IBGDA 主要改变第二条轴；CQE、flush、quiet、signal 与 acquire/release 才回答第三条轴。GPUDirect RDMA 官方指南、DOCA GPUNetIO

GDAKI；RDMA 场景常称 IBGDA kernel 到 NIC 的控制路径也留在 device GPU kernel 生产/排队网络工作并推进 doorbell/completion 不等于不再需要 host 初始化、连接与权限配置

GPUDirect Storage Design Guide把 P2P、RDMA、Storage 与 stream/graph-triggered 形式分开；DOCA GPUNetIO 则把 kernel-initiated networking 称为 GDAKI，并说明在 RDMA 场景中又称 IBGDA。GDRCopy 也不是网络：它让 CPU 低延迟地映射读写一段 GPU memory，常被 proxy/control path 使用。

GPUDirect RDMA 的“direct”只发生在每台机器本地 GPU 与 NIC 之间；跨机器的 packet、路由、可靠性、拥塞与重试仍由 NIC 和 IB/RoCE fabric 负责。典型路径要求 GPU 与 NIC 位于合适的 PCIe P2P topology，最好只经 PCIe switch/同一 root complex；IOMMU 或 ACS 若把 peer traffic 重定向回 root complex，可能破坏或显著拖慢直接路径。完整 GPU-initiated 路径则可能是：SM 在 GPU-resident SQ 中写完整 WQE；以 release 顺序发布描述符后更新 DBR/doorbell；NIC 读取 WQE 与 GPU source buffer，经 InfiniBand/RoCE 发到远端 NIC；远端 NIC 依据 rkey 与权限 DMA 到目标 GPU memory；本地 CQE 或其他完成记录回到 GPU；目标 GPU 再通过 signal/wait 获得应用级通知。零拷贝、GPU 发起和目标可见是三件不同的事。

4. NVLink、NVSwitch、NVLink Fabric 与 NVLink SHARP

NVLink 是 GPU 间点到点高速互连及其协议能力，NVSwitch 是把多个 NVLink 端口连接成高带宽交换 fabric 的交换芯片。GPU 的 ordinary load/store/atomic、CUDA copy engine/TMA、NVSHMEM P2P 路径都可能利用它们，但“经过 NVLink”不等于使用同一条 ISA 路径：一个 peer pointer 访问属于 generic memory proxy，PTX 9.3 CFT handle 操作属于 fabric proxy，TMA 又有 async copy proxy；它们访问同一底层 allocation 时必须遵守跨 proxy 的可见性规则。超节点还需要 Fabric Manager/NVLSM/IMEX 一类控制面完成路由、partition、跨 OS process sharing 与健康管理；普通 kernel 只消费已授权 resource，不能把 route table 当应用 ABI。

NVLink Fabric/NVLink domain 是 GPU、NVLink 与 NVSwitch 已被控制面配置后形成的可达 memory fabric，不是 NVSwitch 的另一个名字，也不必等于单机或单 OS。Fabric Manager负责 fabric 初始化、GPU routing/port map 与错误监控；NVLSM 发现拓扑、分配 LID、计算 forwarding table 并编程 PKEY partition。跨 OS node 的 memory sharing 还要由 IMEX/CUDA VMM 显式 export、import、map 并设置访问权限。DGX GB networking guide把该平台的 NVLink 称为 memory-coherent scale-up fabric；这是平台级可编程性描述，不能单凭这个词外推出“任意 GPU cache line 自动互相 snoop”。它也不等于 72 张 GPU 变成一个 CUDA context、所有 HBM 自动映射，或程序获得 sequential consistency；cacheability、atomic width、memory scope 和发布—获取仍须按具体 capability 与 memory model 定义。

NVLink SHARP（在软件文档中常与 NVLS、multicast object、multimem.* 一起出现）的核心价值是避免每个 GPU 分别发送 N 份数据，或让一张 GPU 串行读 N 份数据做归约。CUDA host 侧创建一个 multicast object，并把各 GPU 的 backing allocation 绑定为 replicas；device 侧的 multicast store 可把一份值复制到所有成员，push reduction 可把更新归约进多个目标，multimem.ld_reduce 或 PTX 9.3 fabric.try_pullred 可从多个成员 pull 并归约。它是固定数据类型/操作/布局约束下的 fabric primitive，不是“交换机里能运行任意 CUDA kernel”，也不等同于完整 all-reduce API；team 构造、分块、阶段同步和 fallback 仍由 collective runtime 负责。

5. IB/RDMA 的资源对象：PD、MR/key、QP、WQE、doorbell 与 CQ

GPU 读者可以把 RDMA NIC 理解成一台受保护的异步内存执行器。应用先授权 memory、建立 transport endpoint 与 completion resource，再把异步 work 放入 queue。目标 CPU 或 GPU 不必为每个 one-sided operation 运行匹配代码，但 host/control plane 仍要创建和连接资源。NVIDIA DOCA RDMA Verbs对下面这些对象给出了一手定义：

6. Put/Get 与 Send/Receive 的根本区别

Two-sided send/receive 要求双方在协议上匹配：sender 提供 payload，receiver 预先或及时提供 receive buffer，长度与接收进度属于双方协作；MPI 等高层协议还可能做 tag matching，但 raw verbs SEND/RECV 本身通常依赖 QP/RQ 与 posted receive，而不是 MPI tag。One-sided put/get 把操作所需信息都带在发起端：put 指定本地 source 和远端 destination，get 指定远端 source 和本地 destination；目标 CPU/GPU 不需要同时运行一条 receive。RDMA Write 自然对应 put，RDMA Read 对应 get；NVLink peer store/load 也可实现同样语义。

但 one-sided 不意味着“目标什么都不用做”。目标 memory 必须预先授权和映射，consumer 仍需知道数据何时可用，队列溢出与错误仍要处理。signal、wait/test、barrier 正是 PGAS 为 one-sided 数据流补上的控制协议。正确的抽象不是取消同步，而是把数据移动与目标参与解耦，再显式选择最小必要的同步。

三、PGAS 与 symmetric heap：把网络地址变成编程模型

1. PE、私有对象与 symmetric object

PGAS 是 Partitioned Global Address Space：全局地址空间在逻辑上可被所有 PE 访问，但物理上分区，每个对象有明确 home PE。NVSHMEM 中每张参与 GPU 通常对应一个 PE；普通 CUDA allocation 是 private，远端不能仅凭本地 pointer 命名它；symmetric object 则在相关 PE 上具有同名、同类型、同大小的对应实例，dynamic symmetric allocation还要求collective调用的顺序和参数匹配。这里“symmetric”不要求各 PE 的虚拟地址数值相同；公共模型保证的是对象对应关系，而不是把某个裸地址或heap arithmetic offset规定为跨PE ABI。

当前 NVSHMEM heap-based实现以offset完成这种对应翻译：设本地 symmetric heap 基址为 BlocalB_{local}，API 传入本地指针 pp，则 o=p−Blocalo=p-B_{local}；访问 PE qq 时，runtime可形成直接映射地址 Bqmapped+oB^{mapped}_{q}+o，也可形成CFT handle {LEq,o}\{LE_q,o\}，或查表得到RDMA的 {remote_vaq+o,rkeyq,pathq}\{remote\_va_q+o,rkey_q,path_q\}。因此，endpoint+offset是一个被真实源码验证过、也适合本文ISA的实现形式，但不能反过来声称公共PGAS规范要求所有实现暴露相同heap offset。

2. Symmetric heap 的分配、注册与可达性

nvshmem_malloc/calloc/align/free 是 collective：参与 PE 必须以相同次序调用，对allocation还要使用一致参数，runtime才能建立对应对象与远端元数据；正常非零allocation在退出时包含同步，合法非空free在释放前包含同步，而零尺寸allocation/null free属于no-op边界。初始化阶段还会发现 topology、建立 transport、交换 heap handle/rkey、映射可直接 P2P 的 peer，并为不能直达的 peer 准备网络路径。nvshmem_ptr(ptr, pe) 只有在目标可直接 load/store 映射时才返回普通 peer pointer；返回空并不代表对象不存在，而是应用必须走 NVSHMEM RMA。

“注册”与“symmetric”也不是同义词。普通 nvshmemx_buffer_register 让用户 buffer 成为 transport 可用的本地 source/destination operand，使 NIC 能 DMA 它，但不会仅凭 local registration 把它变成远端 symmetric target；当前另有所有 PE 共同调用的 nvshmemx_buffer_register_symmetric/preferred-address 形式，才把对应 mapping 纳入 symmetric heap 并返回 symmetric address。反之 symmetric heap 必须带有远端访问所需的 registration/binding。这个区分决定 ISA 要同时描述两类 operand：本地地址空间（register/shared/global）与远端 capability address（endpoint+offset）。把两者都写成普通 pointer 会丢失保护边界和 backend 选择信息。

跨 supernode 的同一逻辑 symmetric window 还可能同时拥有两套彼此独立的 data-plane binding。域内路径由 CUDA VMM/IMEX export、import、map 与 access permission 建立可映射的 fabric allocation；若使用 NVLS，还要把各成员 backing allocation 绑定到 multicast object。域间路径则把相同或对应的 GPU allocation 注册为 NIC MR，生成 local DMA 所需的 lkey 与远端访问所需的 remote VA + rkey。两套 metadata 的粒度、虚拟地址、权限与生命周期不必相同，因此 runtime 应在 endpoint table 中按 path 保存 capability，不能把一个裸 pointer 或一个 rkey 冒充“全球地址”。这里的“双路径注册”是根据公开 VMM/IMEX、multicast 与 RDMA resource model 得出的系统设计结论，并非声称当前 NVSHMEM 暴露了一个统一双注册对象；无论走哪条路径，registration 只建立可达性和权限，并不替代 fence、quiet、signal 或 consumer acquire。

3. GPU-side RMA 的实际 dispatch

NVSHMEM 开源实现把同一个 device API 分流到多条路径。若目标 heap 有 P2P mapping，可由 peer_heap_base_p2p[pe] + offset 得到地址，使用 load/store、合作式 copy 或合适条件下的 TMA；若启用实验性 CFT 路径，可把 PE 与 offset 解析为已导入 logical endpoint 加 resource offset，使用 PTX fabric operation 和 shared-memory staging；若目标只能经网络到达，则进入 device transport dispatch：IBGDA/GPUNetIO 由 GPU 构造网络工作，proxy transport 则把请求写入 GPU—CPU proxy ring，由 host progress engine 调用 transport。由此可见，“NVSHMEM API → 一条固定指令”并不存在；稳定的是 RMA/ordering semantics，变化的是 reachability 与 transport。

这也给硬件设计一个直接启示：前端 ISA 应向编译器提供统一语义，endpoint/context table 在执行时选择 P2P load/store、CFT、NVLink packet engine、RDMA WQE synthesis 或 software proxy。若公开 ISA 直接叫 post_ibv_write，同一 binary 既无法转到 NVLink，也无法让后续硬件把若干小操作合并成更高效 packet。

4. Team、context/channel、QP 与 transport abstraction

Team 是 PE 的有序子集，用于 collective 与资源管理；它回答“哪些 PE 参与、rank 如何映射”。Context/channel 是本文采用的 device ISA 概念：一组独立的 issue、ordering、completion 与流控状态，它回答“这批操作按哪个序列与策略推进”；当前 NVSHMEM 3.7.2 没有可由用户创建/传递的通用 public nvshmem_ctx_t/nvshmem_ctx_* 表面，用户可见的细粒度资源选择是 QP-specific handle。QP 是 IB/RDMA backend 的 transport object：一个 context 可以映射一个 QP，也可在满足语义的前提下映射多个 QP/rail；NVLink 后端则可把它映射 virtual channel、traffic class 或共享 injection engine 中的逻辑队列。Transport abstraction 是 runtime/ISA 合约：上层只要求 put/get/atomic/ordering/completion，下层报告 capability 并选择实现，而不是假装所有 transport 的能力与代价完全相同。

这四者不能混用。Team 不天然提供操作顺序；同一 team 上可以开多个 context。Context 也不应直接等于 QP：否则非 IB 硬件被迫伪造 verbs，且 hardware 无法把多个 logical stream 复用到有限实体。反过来，若 backend 把一个 context stripe 到多条 QP，它必须额外建立该 context 所承诺的 fence/quiet epoch；不能因为吞吐更高就悄悄破坏同一 context 的发布顺序。超节点中的物理层级可写成 GPU ⊂ tray/node ⊂ NVLink domain/supernode ⊂ cluster；hardware partition、IMEX domain 与 job team 则是叠加在这棵物理拓扑上的不同逻辑切片，不能硬塞进同一条包含关系。同一个 global rank map 可以附带 locality class，runtime 才能选择“域内 multicast/SHARP，域间 RDMA/IB SHARP”的分层算法；ISA 只消费紧凑 group handle 和 endpoint table，而不硬编码 rack 拓扑。

四、NVSHMEM communication semantics：先分类，再谈指令

1. RMA：put、get、标量、分段与 nonblocking

Remote Memory Access（RMA）是最基本的 one-sided copy。Put 把本地数据写到目标 PE 的 symmetric object；get 把目标 PE 的 symmetric object 读回本地。p/g 是单元素低延迟形式，put/get 是连续 vector，iput/iget 带源/目标 stride；vector/strided RMA 的 warp/block 变体让一组线程合作搬运，scalar p/g 没有这类 cooperative 变体；on-stream 变体把调用编入 CUDA stream。API 形状很多，但 ISA 只需区分方向、本地 state space、远端 address、长度/descriptor、issuer scope 与 completion requirement。

这里还要区分“由谁调用”和“在哪个执行域生效”：off-stream host API 属于 CPU issuance domain；*_on_stream 由 host 调用、但把动作排入指定 CUDA stream；device API 由 kernel thread 发起，_warp/_block 是必须由相应线程组一致调用的 cooperative form。三者可以表达相似 RMA，却不能把 host 的 fence/quiet 当成 device-issued operation 的完成点；QP-specific 家族除 host-side create 外又全部是 device-only。

NVSHMEM 的“blocking”不是两端同步。Blocking vector put 返回时，本地 source 已被复制出并可复用，但目标数据可能尚未完成；scalar p 按值接收 operand，没有 source-buffer lifetime，且可以在目标更新完成前返回。Blocking get 必须等本地 destination 已含结果，scalar g 则在返回值可用后返回。_nbi（nonblocking implicit）只保证操作已被初始化/发起到足以让调用返回，真正完成由后续 quiet 等待；3.7.0 新增的 nvshmemx_flush 专门让 outstanding nonblocking put 的 source 可复用，却不承诺目标可见。这个差异要求硬件至少区分 ISSUED、SOURCE_SAFE、LOCAL_RESULT_READY 与 DESTINATION_COMPLETE，而不能只有一个模糊 done bit。

NVSHMEM还特意弱化了OpenSHMEM对blocking fetching operation的跨调用顺序：一次get或fetching AMO返回后，其结果可被program order中的依赖操作使用，但两次彼此独立的blocking get/fetch不因此自动形成强返回顺序；需要这种顺序时在两次blocking operation之间使用nvshmem_fence。这条规则不适用于NBI result completion，后者仍要由quiet收束。

2. AMO：把“远端更新”放到目标 home serialization point

Atomic Memory Operation（AMO）覆盖 fetch、set、swap、compare-swap、increment、add、and/or/xor 及其 fetching/nonfetching 形式。Fetching AMO 必须把旧值送回发起者，因此返回值可用时本次操作已在目标原子序中发生；nonfetching AMO 可以提早返回，后续 quiet 或 barrier 才保证完成。AMO 的原子性应在目标 allocation 的 home serialization point 建立：无论请求来自本地 SM、另一 GPU 的 NVLink atomic，还是 NIC RDMA atomic，对同一对象都必须进入一个兼容的原子序；若平台无法做到，就必须通过 capability 禁止混用，而不能分别在两个代理里“各自原子”。

原子能力不能用一张笼统的 {op} × {type} 笛卡尔积描述。GPU、CFT、NIC 对宽度、signedness、floating point、CAS、min/max 的支持各不相同；对齐也通常强于普通 RMA。NVSHMEM 对 AMO 的原子性以相同 datatype 的 NVSHMEM AMO 及相应 wait/test 观察为边界；signal operation 则对其他 signal update、signal-fetch 与同 datatype 的 point-to-point synchronization 定义原子性。并发混用不同 datatype、atomic 与 non-atomic NVSHMEM 更新，或普通 CUDA LD/ST/atomic 访问同一位置，可能未定义。统一 ISA 因而需要逐 endpoint 的 legality matrix，以及一种 guaranteed-progress 的 software/active-message fallback；不支持时必须报错，绝不能用 load+store 静默伪造原子性。

3. Signal 与 put-with-signal：数据发布协议

Signal 是位于 symmetric memory 中的 64-bit 通知对象，目标更新操作是原子的 SET 或 ADD。它与 CQE 不同：CQE 是发起端/队列的 transport completion，signal 是目标 PE 上由应用观察的协议状态。put_signal 要求 payload destination 与 signal object 都能在目标 PE 远端访问且二者不重叠，并将“搬 data”和“更新 signal”组合成一个有序发布：consumer 一旦观察到 signal 满足条件，对应 put 的数据已经 delivery complete。它正好表达 producer/consumer、tile ready、bucket ready 与 epoch advance。

Blocking put_signal 返回时只保证本地source array已经copied out，并不意味着远端signal已更新；put_signal_nbi 只在operation initiated后返回，source lifetime和origin-side整体completion仍由后续quiet收束。目标观察到signal则是另一条边，它证明对应payload已delivery。nvshmem_signal_fetch 则原子读取calling PE本地signal object的当前值，不是一次远端get，也不替代等待条件。

这个保证有严格边界。一次 put_signal(A, sig) 证明 A 先于该 signal，不自动把此前另一条独立 put B 也纳入发布；若 B 也必须先可见，需要同一 ordering domain 中的 fence，或先 quiet，再 signal。提案 ISA 最好将 put-with-signal 设为一级 operation，以便 NVLink engine、CFT backend 或 NIC 在不做全队列 drain 的条件下实现最小 release 序列。若硬件无 fused form，合法 lowering 是“put → 同一 context/target 的 delivery fence → signal”，而不是只插一条普通 GPU threadfence。

4. Wait/Test：目标端的 acquire，而不是网络 completion

wait_until 反复等待本地 symmetric object 与 compare value 满足 EQ/NE/GT/GE/LT/LE；test 只检查一次并返回 predicate。all/any/some 与 vector variants 把同一逻辑扩展到数组。对象之所以称“本地”，是因为 consumer 读的是自己的 symmetric replica；远端 producer 用 signal、AMO 或 RMA 改写它。公共 NVSHMEM 语义要求成功的 wait/test 不得在被观察更新 fully complete 之前返回；实现还会执行相应 consistency action，使它能成为随后读取已发布 payload 的观察点。本文提案把这项作用显式写成 acquire。

用普通 load loop 可以实现功能，但 persistent kernel 中大量 warp 忙轮询会占 issue slot、L2 带宽和调度资源。硬件可提供 scheduler-aware memory monitor：第一次 test 失败后登记 address、mask/compare 与 scope，让 warp 睡眠；目标写入或周期检查触发唤醒。这个能力是本文新增，并非 PTX 9.3 Fabric Instructions 已有。它还必须定义 timeout、endpoint failure 与 cancellation，避免网络断裂把整个 kernel 永久挂死。

5. Fence、flush、quiet：三个不能合并的动词

这三个 API 分别回答顺序、source lifetime 与目标完成。nvshmem_fence 对公开 ordering 表覆盖的 memory store、blocking/NBI put 与 AMO 的远端 update，和随后发往同一目标的 symmetric-object 操作建立 per-target delivery order；它不等待这些操作完成，也不保证 nonblocking get 或 nonblocking fetching AMO 所取回值的 delivery order。当前不同 NVSHMEM 页面概述 NBI 时措辞并不完全一致，因此任何依赖 NBI completion 或 buffer lifetime 的正确性都应使用 quiet，只有 put source reuse 使用 flush，不能从 fence 推导 completion。nvshmemx_flush 只等待 outstanding nonblocking put 不再读取本地 source，便于 buffer reuse；在某些 IB/RoCE 实现上，为取得这一证据可能仍需 drain 类似 quiet 的 transport 工作，但 API 保证仍只是 source completion。nvshmem_quiet 则完成调用者所覆盖的 outstanding 操作，并使更新在 destination PE 可见；它不会自动通知目标，也不是“全系统所有观察者都可见”的 global barrier。

6. Barrier 与 sync：通信完成和集合会合不是一回事

NVSHMEM team barrier 是 collective rendezvous，并在返回前确保 team PEs 先前发出的 memory stores 与 remote RMA/AMO updates 完成；sync 只完成并传播先前 memory stores，不负责完成先前通过 NVSHMEM 发出的 remote memory updates。Barrier 的公开 visibility 保证还随系统而异：纯 NVLink 系统中这些更新全局可见，而 NVLink 与 InfiniBand 混合系统只保证对目标内存所属 PE 可见。若算法先做 NBI put 再调用 sync，不能想当然地把 sync 当 quiet；需要按 API 语义先 quiet 或采用带发布语义的 signal。这个区分很像 GPU 上“线程会合”和“异步 copy pipeline 完成”不同：参与者都到了，不代表所有独立引擎的工作已经 drain。CPU 与 GPU issuance domain 仍分开：host barrier 不会自动完成 kernel 内尚未由 GPU-side quiet/barrier 纳入顺序的 operation。

NVSHMEM 官方使用说明还明确要求：使用 synchronization 或 collective API 的 CUDA kernel 应通过 collective launch API 启动，才能保证 deadlock-free progress 与 completion。Collective launch 解决的是跨 PE 的启动一致性、grid residency 与 progress-resource 契约，不是把 barrier 本身变成一条网络包。超节点中这个契约必须绑定显式 team，而不能隐含为物理 NVLink domain 的全部 GPU；同一 hardware partition 可以同时承载多个不相交 job/team。

因此本文所谓 “global barrier” 应当至少等价于 barrier(team, slot, phase, team_epoch, order, ctxset)：team 给出参与者，phase/epoch 防止复用 slot 时发生 ABA，arrival 的 release 与 wait 的 acquire 定义 memory 可见性；当lower NVSHMEM barrier时，ctxset必须固定覆盖所有相关communication resource，而不是让调用者任选一个subset来跳过既有RMA。若成员失败或 communicator 被 revoke，wait 必须返回 terminal status，而不是把其余几十张 GPU 永久挂住。Host/runtime 可在 launch 前验证 matching kernel/collective signature、预留 barrier slot、multicast resource 与 progress warp/CTA；这些属于超节点 control-plane contract。

ISA 不必为 NVSHMEM 每个 barrier 变体复制 opcode。基础版本可用 group signal/arrival、acquire wait 与 context quiet 组合 dissemination/tree barrier；可选 collective engine 再把整次 barrier descriptor offload。规范可以让runtime在generic group synchronization中明确选择“sync-only”或“communication-completing”profile，但一旦选择NVSHMEM-barrier语义，后者就必须quiet其ALL-relevant资源；不能把硬件无条件全channel quiet的高代价强加给本来只需要sync的其他协议。

7. Collective：算法层，而不是一长串网络指令

NVSHMEM collective 包括 broadcast、fcollect、all-to-all、reduce、reduce-scatter extension、tile collectives 与 barrier/sync，作用域由 team 定义。一个完整 collective 含成员关系、scratch、分块、拓扑、到达协议、datatype/op、容错与 fallback；这些大多属于 runtime algorithm。基础 ISA 应提供可组合的 unicast RMA、signal/wait、multicast put、push/pull reduction、group arrival 与 completion event。Ring all-reduce 可由 put/get+signal 组成，树 broadcast 可由 put_signal 组成，NVLink SHARP 能力可把某阶段换成 multicast/reduction；没有必要为 nvshmemx_float_sum_reduce_block 造一条硬件 opcode。

公共 team-based collective 都是 blocking call：同一 team 的所有 PE 必须以相同 program order 参与；一次只能有每 PE 的一个实例在该 team 上调用，想并发推进独立 collective 应使用不同 team。Thread-group 变体还要求组内所有 CUDA thread 以相同参数参与。Tile collective 是单列的扩展，其中名称带 NBI 的算法要由 tile_collective_wait 完成，不能据此把标准 team collective 也描述成 nonblocking。

可选的 descriptor-based net.coll.async 仍有价值，尤其当 NIC/交换机掌握整个 aggregation tree 时；但它应是一种 capability profile，而不是基础正确性唯一来源。这样同一 binary 可在超节点 NVLink domain 内用 NVLS、超节点之间用 IB SHARP、普通网络上退回 ring/tree，并由相同 token/event 串起后续计算。超节点 team 很大时还要避免“每个 root 对 71 个 peer 单播”的 O(P)O(P) 注入以及“每个 PE 保存所有 pair 状态”的 O(P2)O(P^2) 资源；group endpoint、rank-range descriptor、聚合 arrival counter 与 topology-aware subgroup 因而从优化升级为可扩展性要求。

8. QP-specific API：把独立 ordering domain 交给 device code

NVSHMEM 3.5.19 起加入 nvshmemx_qp_* 系列。3.7.2 的公开表面包括 host collective nvshmemx_qp_create，以及 device-only 的 typed scalar p/g、typed contiguous put/get 与 put_nbi/get_nbi、signal_op、typed blocking/NBI put-with-signal、QP fence/quiet；vector RMA、put-with-signal和QP fence/quiet另有 warp/block cooperative forms。它没有公开 QP-specific generic AMO、collective、wait/test、strided iput/iget、byte/fixed-size RMA或 flush。创建得到的 handle 不是“到某一个 PE 的连接句柄”；一个 custom QP handle 可与任意 PE 通信，runtime/backend 决定实际 resource mapping。在不支持 custom QP 或仅 NVLink 的环境中，API可回退为 default handle。公共 QP 文档列出的 custom-QP transport 是 IBRC、IBDEVX、IBGDA（RC QP）和 GPUNetIO；应用应检查create返回值与所得handle，并接受 unsupported配置下的default fallback。

nvshmemx_qp_create(num_qps, &array) 必须在NVSHMEM初始化后、任何device QP operation之前，由 WORLD 中所有PE在host上一致调用；库分配handle array，handle保持有效直至finalize，当前没有public QP destroy，用户只在finalize之后释放该array。普通QP communication把一个handle按值作为最后一个参数；QP fence/quiet接受PE、handle array与数量，因此可选择某一PE/QP集合。Communication中的NVSHMEMX_QP_DEFAULT等同相应非QP API，NVSHMEMX_QP_ANY允许实现选择default或custom资源；synchronization中的NVSHMEMX_QP_ALL覆盖default+custom，它与NVSHMEMX_QP_ANY是数值alias但角色由API语境区分；NVSHMEMX_PE_ALL（alias NVSHMEMX_PE_ANY）覆盖所有target。Fence/quiet若使用QP_DEFAULT或QP_ALL，参数是指向该特殊值的pointer且num_qps=1。QP页的概述文字提到strided RMA，但同页实际函数清单与current public header都没有QP iput/iget，本文按真实声明划定边界。

不同 QP 之间没有隐含 ordering；同一 QP 也不意味着所有 put 自动按目标可见顺序串行，仍需 nvshmemx_qp_fence 建立规定的 delivery order。NVSHMEMX_QP_ANY 可能让实现逐次选择不同资源，适合不要求固定 QP 顺序的负载均衡，不能把它当作一个稳定 ordering domain。nvshmemx_qp_quiet 可按 PE 与 QP 集合等待完成。它们让算法把 control、小消息、大 payload 或不同 rail 分开，减少 head-of-line blocking，也允许多条 pipeline 独立推进；代价是 QP 占用 NIC/GPU memory，quiet/fence 要处理更多 domain，跨 QP 发布必须显式 join。

因此本文 ISA 采用 context/channel 而不采用 “QP” 作为通用名。一个 context 是 architectural ordering/completion domain；IB backend 可以一对一映射 QP，也可用 DC/多 rail，但必须兑现 context 语义；NVLink backend 可以用虚拟 lane。QP-specific NVSHMEM handle lower 到 context handle 后，API 的独立性得以保留，又不把某代 ConnectX WQE 格式固化进 GPU ISA。

五、四套容易混淆的机制：NVSHMEM、Logical Endpoint、PTX Fabric 与 NVLink SHARP

1. 四者各自解决什么问题

这四套机制处在不同层，不能按发布时间连成“一套新网络 API”。NVSHMEM 给出 PGAS 编程模型与 RMA/AMO/signal/ordering/collective 语义；CUDA 13.3 Logical Endpoint（LE） 是 host control/address plane，创建受保护的 unicast/multicast resource aperture；PTX 9.3 Fabric Instructions 是 device data plane，用 <leId, offset> 发异步 get/put/reduction，并以 mbarrier/report 观察完成与失败；NVLink SHARP/NVLS 是 NVSwitch fabric 内的 multicast/reduction 能力，既有 VMM multicast object + multimem.* 路径，也可成为 CFT multicast/reduction 的底层资源。它们的交集很大，但没有一个单独覆盖其他三个。

2. CUDA 13.3 Logical Endpoint 的完整 host 生命周期

Logical Endpoint 首次在 CUDA 13.3 Driver API 中公开。它的 device-visible ID 是 32-bit CUlogicalEndpointId；PTX CFT handle operand 再加 64-bit resource offset。另有一个 opaque CUlogicalEndpointFabricHandle 作为 CU_LOGICAL_ENDPOINT_IPC_HANDLE_TYPE_FABRIC 的 host 进程间 export/import token，不能把这个 IPC blob 与 device 指令中的 <leId,off> 混为一谈。CUDA VMM 的 CUmemFabricHandle 又是用于分享 memory allocation 的另一种 handle，也不是 LE；导出 endpoint 不会自动导出它的 backing allocation。

完整生命周期如下：host 先查询 device 的 unicast/multicast/counted-op support，填好 CUlogicalEndpointProp 并用 cuLogicalEndpointGetLimits 得到 binding alignment 与最大 size；随后 cuLogicalEndpointIdReserve 预留连续 ID，cuLogicalEndpointCreate 以 unicast owner 或 multicast member count 创建。Multicast endpoint 要先 cuLogicalEndpointAddDevice 加齐永久成员；两种类型都必须用 nonblocking cuLogicalEndpointQuery 确认 ready。接着 cuLogicalEndpointBindAddr 或 BindMem 把 allocation 子区间绑定到 endpoint offset；BindAddr 只接受 cuMemCreate 或 cudaMallocAsync allocation，BindMem 只接受 cuMemCreate 得到的 generic allocation handle，CUDA 13.3 的 bind flags 均必须为零。跨进程共享时，导出方 Export opaque endpoint token，接收方先 reserve 自己的 ID 再 Import；因此同一 endpoint 在不同进程中的 leId 数值不保证相同，import 还可因无访问权限或平台不支持而失败。销毁时 Destroy 去掉本进程的 ID association，解除由本进程建立的 bindings，最后一个 reference 才销毁底层 endpoint resource；之后才能 IdRelease 归还数字 namespace。CUDA 13.3 公开 LE 文档没有单独规定 in-flight teardown 的完成合同；因此“先停止新 issuer 并等待所有 fabric operation 完成，再 Unbind/Destroy”是本文采用的安全生命期规则，不应写成 Driver API 已公开的额外保证。

3. LE 与 NVSHMEM symmetric heap 如何接上

NVSHMEM 3.7.0 release note 将 Logical Endpoint/CFT 支持明确标为 experimental，并限定为 fabric-PTX unicast communication；它是一个可选 NVLink-domain transport path，不是新编程模型，也不是 IB transport 的替代品。在 NVIDIA 官方 NVSHMEM 2026-08-27 源码快照中，host 为每个 GPU 的整个 symmetric heap 建一个 unicast endpoint，以 heap offset 绑定 VMM chunks；owner export endpoint token，bootstrap allgather 后各进程为每个 peer import 一个本地 ID，并把本进程的 PE → leId table 复制到 device。这张表中的 leId 是 process-local association，不是作业内所有进程共享同一数值的 rank ID。Kernel 收到 symmetric pointer p 和目标 pe 时计算：

CFTAddr(pe,p)={leIdTable[pe],p−Blocal_heap}.\operatorname{CFTAddr}(pe,p)=\{\operatorname{leIdTable}[pe],\;p-B_{local\_heap}\}.

接下来 aligned bulk put/get 才能进入 fabric.try_*。Global/local buffer 与 16-byte 尾部可能需要 shared staging、mask 或 fallback；NVSHMEM 的 flush/quiet/signal/collective 仍在更高层闭合。这个实现案例非常漂亮地说明两者互补：PGAS 保证“对应对象有相同 offset”，LE 保证“本进程如何受保护地引用那个 peer resource”。只有其中一个都不能完成寻址。

4. LE 不是 QP，CFT 也尚未统一 IB

LE 是 destination identity + resource aperture；QP/context 是 source-side issue/progress/ordering state。CUDA 13.3 LE property 没有 send queue、CQ、producer index、PSN、priority、route 或 ordering selector，PTX fabric.submit 也只是提交当前 thread 先前 issue 的 fabric operations。公开 CFT 模型不暴露一个可由指令选择的 context/QP；本文提案才允许多个 source-side context 访问同一 endpoint、或一个 context 先后访问多个 endpoint。因此两类对象的基数、生命周期和故障状态都不同，不能把 leId 当作隐含 QP handle。

公开 PTX 9.3 用 NVLink failure 与 NVLink domain 描述 CFT，operand 中没有 rkey、QP 或 NIC selector；同一版 NVSHMEM release note 又把 CFT、GPUNetIO remote transport、IB routing/QP controls 分列。因此严谨结论是：<endpoint,offset> 已证明是一种优秀的 scale-up resource address，本文建议将同一抽象扩展成 transport-neutral address；但“CUDA 13.3 已用 CFT 统一 NVLink 与 IB/RDMA”不是公开事实。统一必须由本文的 context、capability 与 transport adapter 再补一层。超节点恰好证明“跨 OS node”不必等于“走 IB”：同一 NVLink domain 内的多节点可继续用 LE/CFT，跨超节点才转到 NIC；路径选择必须来自 endpoint capability/topology，而不能用 node ID 的比较写死。

5. Host control plane 与 device data plane 的闭环

可以把一个可工作的系统分成两条时间线。初始化时，host/runtime 发现 topology，collectively 分配 symmetric heap，注册/绑定 memory，创建 LE 或 MR/rkey，建立 QP/context/team，交换 peer metadata，并把只读 capability tables 下发 GPU。稳态时，kernel 只携带 endpoint/context handle 与 offset，发 RMA/AMO/signal，提交/等待 completion；它不能任意创建 rkey、伪造 route 或修改 endpoint ownership。结束时 host 先阻止新 issuer、drain device context，再解绑和销毁资源。

这个分工也为安全与虚拟化提供了正确施力点，但必须分清已公开事实和本文提案。CUDA 13.3 公开事实是：leId 是 opaque 32-bit ID，import 会做 access-permission/support 检查，binding 有 size/alignment/owner 约束，fabric operation 可通过 mbarrier report 报告失败；文档没有公开 endpoint-table 格式、generation/PASID 编码、route entry 或 revoke 协议。本文的 transport-neutral ISA 则进一步要求 ep、memory capability 与 context handle 经驱动验证，offset 做 bounds/permission check，rkey、PKEY、route、UAR 与 generation-specific descriptor 留在受保护的 table，并在 preemption/进程退出时以 revoke 与 terminal status 收束旧 handle。

六、PTX 公开能力：按功能理解，而不是逐条背手册

1. 三条地址/执行路径先分开

与 NVSHMEM 最相关的公开 PTX 并非一套单一路径。第一条是 ordinary pointer path：peer allocation 已映射进地址空间时，用 ld/st/atom/red 与 system scope 访问，优点是标量低延迟和原子操作丰富，缺点是依赖 pointer reachability，fabric fault 通常没有 CFT 那样的 per-operation report。第二条是 multimem VA path：一个 CUDA VMM multicast mapping 指向 group 中多个 physical replicas，只能用 multimem.*；它适合 NVLink SHARP broadcast/reduction。第三条是 PTX 9.3 新增的 CFT handle path：以 <leId,off> 对 Logical Endpoint 发 fabric.*，重点是异步 shared-staged bulk、multicast/reduction和可报告 fabric failure。

这三条路径可访问同一底层 allocation 的不同 alias，却属于 generic、async 或 fabric proxy。它们不是可以随意替换的 pointer spelling。超节点 runtime 会同时用到它们：极小 peer flag 可能走 pointer atomic，tile 走 CFT/TMA，域内 all-reduce 走 multimem/NVLS；编译器必须保留 proxy identity 与 handoff，而不能在优化时把三者都当普通 global load/store。

2. PTX 9.3 Fabric 类恰好六个 mnemonic

PTX ISA 9.3 首次公开 CFT device data plane，Fabric Instructions 类完整集合是 fabric.try_get、fabric.try_put、fabric.try_red、fabric.try_pullred、fabric.submit、fabric.wait，全部要求 sm_100+。四条 data operation 固定 asynchronous、.relaxed.sys，通过 local .shared::cta 与 fabric 交换数据，并用一个 .layout::v1 mbarrier 跟踪 full completion、聚合 fabric failure report。地址、size 与 local pointer 都以 16B 为基本约束：offset/local address 16B aligned，size 是 u32 且为 16 的倍数。一次 operation 可能拆成多个 request；规范明确赋予 try_get source-handle access 的是 128-bit-wide atomicity，这只覆盖每次 16B source access，不能提升成整个大 transfer 原子，也不能外推为其他三条 data operation 的整块 16B 原子保证。

指令 方向/endpoint 主要变体 mbarrier tx 单位 对 NVSHMEM 的贡献

fabric.try_put CTA shared → unicast；.multimem → multicast plain、16-bit .cp_mask、destination .counted::bytes size/16 put、multicast put、remote byte progress
fabric.try_red CTA shared → unicast/multicast，逐元素 push reduction bitwise、min/max、add；可 counted size/16 nonfetching reduction/collective primitive

try_get 只接收 unicast endpoint；try_put/red 无 .multimem 时接收 unicast，有 .multimem 时要求发起 device 是 multicast endpoint member；try_pullred 要求 pull-reduction-capable multicast endpoint，且 PTX 9.3 的 immediate member mask 固定为 0xFFFFFFFF，即完整 warp 以相同 operands rendezvous。try_put 的 .cp_mask 对每个 16B chunk 用 16-bit mask 选择 byte，但并不解除 16B size/alignment。Counted form 在同一 endpoint 内再给一个 8B counter offset：counter 必须 256B aligned、不与 data overlap，以 system-scope atomic 按实际 destination byte 累加；多个 operation 可共享它但彼此无序。它能表示 destination progress，不是任意值 signal，也不能替代 full error completion。

try_red 的合法矩阵不是任意组合：bitwise and/xor/or 对 b32/b64；min/max 对 u32/s32/u64/s64/f16/bf16；add 对 u32/u64/f16/bf16/f32/f64。它没有 fetch result、swap 或 CAS。try_pullred 还支持部分 FP8 min/max、低精度 input 配 add.acc::f16/f32，但这些子形式有 sm_120a/sm_121a 或 architecture-family 限定，不能只检查 sm_100+。

3. 一次 fabric operation 的生命期

最短正确流程不是“发一条 try 指令然后等”，而是：初始化 v1 mbarrier；issue 一个或多个 try_*；每个 issuing thread 执行 fabric.submit；在 phase advance 前用 mbarrier.arrive.expect_tx 登记正确 transaction count；最后等待 primary phase，读取 report predicate/value。所有 operation 必须在 grid exit 前 submit 并完成，否则行为未定义。Get/pullred 的 expected tx 按 bytes 求和，put/red 按 16B transaction 求和；把 256B put 登记成 256 而不是 16 会延迟/破坏 phase，把 256B get 登记成 16 则可能过早宣布完成。

// PTX 9.3 schematic: 256-byte shared -> CFT unicast put
// Producer-to-issuer thread synchronization is omitted.
mbarrier.init.layout::v1.shared::cta.b64 [bar], 1;
fence.proxy.async::generic.release.sync_restrict::shared::cta.cluster;
fabric.try_put.async.shared::cta.
  mbarrier::complete_tx::16B.mbarrier::report::fabric.
  relaxed.sys.b128 [dstLeId, dstOff], [src], 256, [bar];
fabric.submit;
mbarrier.arrive.expect_tx.release.cta.shared::cta.b64 state, [bar], 16;
// mbarrier.test_wait/try_wait phase_type::primary; completion 后读取 report

.layout::v1 mbarrier 是 8B-aligned shared object；.layout qualifier 在 PTX 9.3 引入、要求 sm_90+，v1 expected-arrival count 范围是 1–511，tx-count 范围是 [-(2^20-1), +(2^20-1)]。它降低了 arrival-count 位宽以容纳每个 primary phase 的 report payload；primary phase 在 arrivals 与 tx-count 都归零时完成，即使 operation 失败也会前进。report::fabric operation 成功时不修改 payload；失败时设置 report predicate，opaque report value 可能含更多信息；同一 mbarrier 若混合不同 reporting mechanism，行为未定义。只有 mbarrier.test_wait/try_wait.phase_type::primary 返回 waitComplete=true 后，程序才能检查对应的 reportPredicate/reportValue；提前读取这些 report operand 是未定义行为。Opaque status 可由 CUDA Runtime 的 cudaFabricOpErrorStatusCount/Get 解码。Conditional phase 则要求 report 为零才前进，错误时可能一直不前进，不能把这种等待误判为“网络还没完成”。复用 phase 还必须遵守一条容易漏掉的纪律：每个 primary phase 至少要被一次返回 true 的 test_wait/try_wait 观察，随后才能在下一个 primary phase 执行 arrive-on；若要把这 8B storage 改作其他用途，则必须先 mbarrier.inval。一个 mbarrier 可聚合许多 op 和 failure，这对超节点尤其重要：用 phase/event 聚合数千 packet，而不是为每个 packet 保留 completion token。

4. fabric.wait、mbarrier、counted counter 各回答不同问题

fabric.wait.sync_restrict::reads 只等 submitted fabric operations 不再读取 local shared source，因而可以覆盖双缓冲中的 outbound tile；它不等 remote write/reduction 结束，不报告完整错误，对只写 shared destination 的 get 也不提供所需 completion。Mbarrier primary completion 表示所有显式关联 operation 的 full completion，并聚合 error；counted counter 位于 destination endpoint，表示 put/red 已执行的累计 data bytes，可由 receiver 观察。这三条反馈路径分别服务 source reuse、issuer-side batch completion/error、destination-side progress，不能统称为 quiet。

对应到 NVSHMEM：fabric.wait 最像 3.7 新增 flush 的 source-lifetime 目标；mbarrier 可作为某个已知 batch 的 quiet building block，却没有“某 context、某 target、所有先前操作”的 architectural selection；counted counter可构造 ready protocol，却不是 signal SET/ADD 的完整替代。超节点中，mbarrier 只在 issuing CTA 的 shared memory，绝不等于 72 个 GPU 的 barrier；全域到达仍需 group protocol/collective engine。

5. Proxy ordering：三条 fence 不能混写

Fabric operation 对 <leId,off> 的 access 走 fabric proxy；其 local shared data 走 async proxy；mbarrier update 与 ordinary ld/st 走 generic proxy。PTX 9.3 新增的 fabric cross-proxy fence 完整方向是 generic::fabric、fabric::generic、fabric::fabric，搭配 .alias.{release|acquire}.sys。例如：

fence.proxy.generic::fabric.alias.release.sys;
fence.proxy.fabric::generic.alias.acquire.sys;

它们处理“同一 resource 先经 fabric alias 写、后经 generic alias 读”等跨访问方法的 happens-before。计算线程先用 st.shared 填 outbound tile，再让 fabric/TMA async proxy 读取，走的是另一条 generic→async shared handoff，例如 fence.proxy.async::generic.release.sync_restrict::shared::cta.cluster。普通 fence.sys、fabric-specific proxy fence 与 shared async proxy fence解决三个不同问题；fabric.submit 也不是其中任何一个。正文和手册中的 release/acquire 都会同时标出 memory order 与 proxy transition。

6. multimem.*：NVLink SHARP 的 pointer/VA 数据面

multimem.ld_reduce/st/red 在 PTX 8.1、sm_90+ 已出现，不是 9.3 才有。ld_reduce 从 multicast VA 对应的所有 replicas 读取并把 min/max/add/bitwise 结果返回寄存器；st 把一个值复制到所有 replicas；red 把输入与每个 replica 做 reduction update。它们有 relaxed/acquire/release、CTA/cluster/GPU/system scope 与逐版本扩展的 integer、floating、vector/accumulation 矩阵。对 multicast VA 使用 ordinary ld/st 是未定义行为。

PTX 9.1 又加入 multimem.cp.async.bulk 与 multimem.cp.reduce.async.bulk，把 CTA shared 大块 copy/reduce 到 multicast mapping，以 cp.async.bulk.commit_group/wait_group 管理 per-thread bulk group。PTX 9.3 为 copy form 增加显式 .weak/.relaxed、.scope 与 .b128，为 reduce form 增加显式 .sem.scope；其中 copy 的 .relaxed...b128 form 才是指定 scope 的 naturally aligned strong element-wise access，不能把默认 .weak form 一并称为 strong。Copy 的这些显式 qualifier 只支持 sm_90a、同 family 的 sm_100f+ 或 sm_110f+，.cp_mask 另要求 sm_100+；新加入的 multimem.st.async、multimem.red.async 则是 sm_100+ 的 nonblocking strong-release form。Bulk-group completion、CFT mbarrier completion 与 ordinary pointer atomic 是三套不同 tracking model。

在超节点内，这一族指令是避免 PP 次复制、减少 switch 上重复流量的关键，但仍只是 collective primitive。Runtime 要先建立 multicast object/team、确保每个 replica 的 phase data 已准备好、做 arrival/barrier、选择 chunk 与 accumulator precision，最后才调用 load-reduce 或 push reduction。成员数、partition 与失败 bitmap也不在 multimem.* operand 中，因此超节点级 resilient collective 还需要 group generation 和 status 层。

7. Ordinary atomics 与 MMIO：可作为后端，不是统一语义

Ordinary pointer atom 支持 returning add/min/max/bitwise/exchange/CAS 以及 acquire/release/system scope，red 支持 nonreturning reduction；当 peer pointer 可达且平台保证跨 GPU atomic domain 时，它们可实现部分 NVSHMEM AMO/signal。但 pointer operand不能替换为 CFT handle，PTX 9.3 Fabric 类也没有 handle-addressed fetch-add/CAS/swap。是否能与 NIC atomic 混用仍需 endpoint capability 声明共同的 home serialization point。

PTX 的 ld.mmio/st.mmio 与 async MMIO store/reduction能让 GPU实际访问 I/O register，可能成为 GPU 写 NIC queue/doorbell 的底座；它们没有定义 WQE layout、rkey/lkey、QP、credit、CQE、retry 或 remote visibility。IBGDA 可以用这些低层 primitive 实现某代 NIC backend，但统一 ISA 不能让用户从 st.mmio 猜出 NVSHMEM fence/quiet。Raw descriptor/MMIO 适合受控 vendor escape hatch，不适合作为可移植编程模型。

七、从语义反推一套统一 GPU Fabric ISA

1. 设计原则：统一可观察语义，分离 transport mechanism

统一 ISA 不应规定“一条 put 必须是一条 NVLink packet”或“一条 put 必须是一条 RDMA WQE”。它规定的是逻辑 operation：从哪种 local state space 读取多少字节，写到哪个受保护 remote resource，属于哪个 ordering domain，在什么 completion level 才能复用 source/消费结果，失败可能产生什么 effect。Backend 可以把 4 MiB put 分成很多 packet/WQE，也可以把一个 warp 的小 put 合并；只要 endpoint protection、operation order 与 completion contract 不变。

这一分层保留两个必要事实：NVLink 的小粒度 load/store 与 NIC 的 descriptor DMA 有不同性能曲线，不能强迫同一个 micro-path；NVLink 与 RDMA 都能实现“远端内存操作”，因此没有必要让编译器面对两套完全不同的语义 IR。我们采用 unified semantic frontend + capability profiles + transport adapters：NET-BASE 保证可移植正确性，NET-LINK、NET-RDMA、NET-COLL、NET-SUPERNODE 提供可选加速。

2. 五个 architectural object

Remote address 统一为 raddr=[ep:u32,off:u64]。ep 索引当前 process/VM 的受保护 endpoint table，entry 至少含 generation、type、size、permission、canonical resource identity、transport/path 和 target coherence contract；RDMA 的 rkey/remote VA、NVLink 的 LE/VMM mapping 都留在表内。Context ctx 是 issue、credit、ordering、completion、error 与 QoS domain，可映射 QP/VC/injection queue。Token 是单 operation 的 <context generation,sequence>，可按 completion level test/wait。Event 以 phase/expected/completed/error 聚合多条 operation，可映射 shared mbarrier 或 GPU-global CQ/event。Group 是有 generation 的 immutable endpoint membership snapshot，用于 multicast/reduction；team 与 hierarchy 仍由 runtime 管理。

这些对象彼此正交：endpoint 选“访问谁的哪段 resource”，context 选“从哪个顺序/进度域发”，event 选“哪些完成合在一起观察”，group 选“哪些 endpoint 共同接受一次 group op”。超节点中同一 endpoint 可被许多 context访问，一个 context 可轮流访问几百 endpoint，而一个 group 可以只表示当前 NVLink partition 的 36/72 个成员。把这些对象合成一个巨大 handle 会迫使每种组合都重复建状态。

3. Scalar、bulk 与 descriptor 三条 issue path

标量 p/g/signal/AMO 应从寄存器直入/直出，避免为了 8B 值占一块 16B shared staging；bulk put/get 从 global 或 CTA shared 异步搬运，硬件负责 packetize/coalesce；strided/IOV/tensor/collective 使用有界、版本化 descriptor。Descriptor 只能有固定上限的维度/segment，不允许任意 linked list，否则执行时长、page fault、preemption 与错误 effect 都不可界定。

Issuer mode 是 .issue::thread/.vector/.warp/.cta。Warp/CTA cooperative form 产生一条 logical operation，uniform control operand 必须一致，硬件或库可以让 lanes 协作供数/写 descriptor；它不是 32/128 条独立网络请求。Group issue 自带参与者 rendezvous，但不自动发布此前另一个 warp 写入的 shared tile，仍需 CTA synchronization 与 proxy release。这一规则直接支持 Triton warp specialization 与 NVSHMEM _warp/_block。

4. 四级 completion 与两个观察者

提案把 operation 的 origin-side 状态分成四级：ISSUED 表示 local command 已接受；SOURCE_CONSUMED 表示 engine 不再读 source/descriptor；REMOTE_ACCEPTED 表示 destination transport 已接受，主要供诊断/流控；put/update 的第四级是 REMOTE_VISIBLE，表示 remote effect 已在 endpoint 声明的 coherence point 完成并可见；get/fetch 在该等级的方向特定名称则是 RESULT_VISIBLE，表示 local destination/返回值已可使用，绝不是一次“远程写可见”。手册因此分别提供 .complete::remote_visible 和 .complete::result_visible，两者只能用于方向匹配的 operation。REMOTE_ACCEPTED 只有在 endpoint capability 明确与方向对应的最终可见等级等价时才能实现 NVSHMEM quiet；一般 NIC CQE、NVLink inject ack 都不能凭名字自动升级。

还有第二个观察者：target consumer。Origin token/event 的 remote-visible completion不等于 consumer 已收到通知；目标 signal/wait 是另一个 happens-before 边。put_signal 同时生成 data effect 和 publication effect，consumer 成功 acquire-wait 后才能读数据。这个两观察者模型能避免把 PTX local mbarrier、RDMA CQE 和目标 symmetric signal画成同一个 completion box。

5. Ordering model：主键、epoch 与跨 context join

基础 ordering key 是 (context, canonical target resource)。Operation 默认 relaxed，编译器可跨无关 context/target 调度；net.fence(ctxset,targetset) 为所选 domain 截止一个 delivery epoch，保证调用者在 fence 前的可排序 operation先于 fence 后 operation 到达，但不等待前者完成。net.source.wait 完成 source lifetime；net.quiet(ctxset,targetset) snapshot 所选 watermark 并等待 remote-visible。多个 issuer 共享 context 时，只保留各自 program order；跨 thread 的 producer ownership 必须先以 CUDA synchronization 建立 happens-before。

不同 context 默认独立。若 payload stripe 在 C0—C3，而 ready signal 只发在 C0，信号可能越过其他三条路径。正确协议是 quiet/fence 一个 ctxset={C0,C1,C2,C3} 后发布；或者由 communication warp 等待 aggregate event 再发 signal；支持 optional V2 net.event.trigger.signal 时，才可由 completion engine自主触发。IB backend 可通过 per-QP drain/marker 建 cross-QP epoch；NVLink backend可在 logical injection streams 上实现。这就是 context set 必须进入 ISA，而不是让 runtime 用一个全局 __threadfence_system 猜测。

6. Memory proxy 与 acquire/release

每条 operation 要同时标 semantic order 和访问 proxy。net.proxy.fence generic→network release 把 local producer stores交给 network engine；network→generic acquire 让后续 SM loads 看见 fabric/NIC DMA effect。它们可 lower 到 PTX generic/fabric、generic/async fence，或 RDMA backend 的 WQE/doorbell publication与 GPU cache consistency sequence。普通 remote RMA 仍可 relaxed；publication 用 release signal/put_signal，成功 wait/test 用 acquire。Scope 至少有 CTA/GPU/system，remote effect以 endpoint coherence point定义。

NET-SUPERNODE 不是多造一条 supernode.allreduce。它要求几项可组合的可扩展语义：net.group.query/capability能返回层级与原生 group op 限制；net.mcast.* 对一组成员只占一个 logical command；net.event 支持 large expected count 与 global/coherent wakeup；net.coll.async descriptor 可携带 subgroup/hierarchy/algorithm/numerical mode；context 有 priority/traffic-class 与 bounded credits；group operation失败时 status指出 NO_EFFECT/EXACT_EFFECT/MAYBE_PARTIAL 及 opaque member bitmap；endpoint/group generation变化让 stale kernel及时失败。硬件不一定每项单独编码 opcode，也可由 queryable object field+现有指令实现，但这些语义必须是 architecture contract。

8. Progress、backpressure、安全与错误

Device-initiated 的基本进度承诺是：一条已 accepted 的 operation 不依赖 host 稳态 poll，最终成功或以 terminal status 结束。Queue full 不能让不可抢占 warp 无限占住所有 SM；ISA 要有 nonblocking .try、credit test 与 scheduler-aware credit wait，runtime需保证 completion consumer有调度机会。超节点中的循环依赖更危险：若 72 个 PE 都拿满 outbound credit 后等待 inbound signal，而 completion warp无法运行，软件 barrier 会死锁；每 context reserve credit、fair arbitration 与 collective/control traffic 的独立 class 是正确性机制，不只是调优。

Endpoint/context/group handle 必须 generation-checked、bounds/permission-checked并绑定 VM/PASID。同步 issue error（bad alignment、unsupported op、no credit）与异步 transport error分开。Status 至少包含 class、retryability、effect class、endpoint/member、context generation、operation sequence。普通 put若明确 NO_EFFECT 可安全 retry；AMO ADD、signal ADD 或 partial multicast 在 ambiguous completion 后不能盲目重发，否则重复生效。Exactly-once 需要 transport request ID/dedup 或由 runtime终止本轮协议。超节点扩大 link/switch/tray fault域，所以“error report + group generation + partial bitmap”是长驻 kernel 能否收敛退出的必要条件。

P2P sync net.mem.{test,wait} symmetric signal compare/acquire、warp suspend dedicated form新增

2. 什么保留给 runtime

PE discovery、symmetric allocation、registration、LE/MR/QP creation、team split、rank translation、route、scratch、collective algorithm选择、timeout/retry policy和资源 teardown都不应成为普通 device instruction。net.coll.async 也只消费 runtime 已验证的 bounded descriptor，不能在指令里动态跑一个任意 ring/tree规划器。Raw WQE template可作为 privileged/vendor extension，但通用程序必须有 semantic net.* 路径。

反过来，delivery fence、source-safe、remote-visible、put-with-signal、context independence、partial-error effect不能藏在 firmware 私约里，因为 compiler/application 能观察它们。一个清晰判据是：若改变行为可能让正确程序读到旧数据、提前复用 buffer、重复 atomic 或永久等待，它属于 ISA/ABI contract；若只改变 route、packet size 或具体 algorithm，它属于实现策略。

3. 最小 V1 与后续 V2

V1 应优先实现 endpoint+offset、至少两个 context、linear global/shared RMA、integer AMO、signal/put_signal、fence/source-wait/quiet、token/event、scheduler-aware wait/test与完整 error。它已足够让 NVSHMEM RMA/AMO/signal/barrier和软件 collective无 host progress。V1 的硬件可把 descriptor、floating AMO、multicast/reduction设为 capability。

V2 再扩展 stride/IOV/tensor descriptor、TMEM operand、global event wakeup、group partial bitmap、native collective descriptor、cross-context release trigger 与 stronger fault profile。对超节点，group/multicast、large event和fault epoch应比“更多 exotic datatype”更早，因为它们决定 PP 扩大后协议是否可运行；对 NIC path，virtual context与 WQE coalescer比每 thread 一条物理 QP更重要。

九、同一 ISA 如何适配 NVLink 与 IB/RDMA

1. NVLink/NVSwitch backend

Endpoint table entry 可解析为 peer VA、CFT LE、multicast mapping或 switch group。Scalar p/g/AMO优先走 system-scope peer load/store/atomic；shared tile put/get在满足条件时走 PTX fabric/TMA；multicast/reduction走 multimem.* 或 CFT .multimem。Logical context映射 virtual injection stream，若底层普通 load/store没有显式 queue，context sequencing可由 GPU fabric proxy的epoch scoreboard实现。Remote-visible completion必须在 endpoint声明的 GPU memory coherence point产生，而非 request刚进入NVSwitch。

超节点中 endpoint table要支持二级索引（partition/group base + rank-local index）或压缩 contiguous ID range，switch/group command按成员 bitmap/generation执行。控制与data context应保留独立credit，避免大bulk占满injection后阻塞barrier/signal。Partition重配或成员故障更新group generation；旧operation要么在effect前失败，要么带partial status完成，不能静默发送到新成员集合。

2. IB/RDMA backend

Endpoint entry 隐藏 remote VA/rkey、PD/PASID、route与atomic capability；context映射 RC QP、peer-indexed QP set、DCI或多rail virtual lane。SM front-end接受 net.* 后由 WQE synthesizer从预验证template填 SGE/remote fields，batch更新DBR/doorbell；CQ engine把signaled CQE推进context watermark。在所选 RC/ordered transport 的 completion rule 允许时，同一SQ中更早的unsignaled WQE可由后续signaled completion覆盖；这不能笼统称为“fence CQE”，跨QP更要分别取watermark再join。Queue credit、owner bit、wrap与doorbell ordering是backend状态，不成为上层ABI。

Put lower成RDMA Write，get成Read；supported AMO lower成NIC FAA/CAS，否则走active-message/proxy service。Put-signal可在同一RC QP中发data Write再发ordered 64-bit Write/Atomic，或者用具备正确target protocol的通知形式；跨QP payload先做ctxset join。CQE/transport ACK若不足以保证target GPU cache-visible，backend还要发flush/consistency protocol再推进REMOTE_VISIBLE。Non-idempotent request在retry ambiguity下必须借助transport exactly-once或request-ID dedup。

3. 为什么不是两套 ISA

如果为NVLink设计remote.st、为IB设计post.wqe，compiler必须分别理解两套buffer lifetime/order/error，混合topology collective还要在kernel里切换协议。统一 net.put 后，runtime只改变endpoint/context binding；编译器的async dependency图、put_signal发布证明与quiet范围不变。硬件仍是两套adapter，统一的是front-end contract而不是physical packet。

反过来，一套 ISA 也不能假装 capability一致。CFT 16B shared-only、NIC global DMA、不同atomic矩阵、NVLS multicast、IB SHARP collective offload都通过query/profile暴露。非法组合在issue前返回unsupported，runtime选择软件fallback。统一语义加显式差异，才比“最低公分母”或“伪装成同一硬件”更可移植。

4. 超节点内外的分层路径

在一个72-GPU NVLink domain中，PE-to-endpoint可能全部走scale-up路径；跨两个超节点则同时存在域内CFT/NVLS和域间RDMA。一个hierarchical all-reduce可先在每个supernode做reduce-scatter/NVLS reduction，leader或shard owners经多rail RDMA/IB SHARP交换，再在域内multicast/allgather。ctx_intra与ctx_inter并行，event以chunk为单位join，而不是先全域内结束再全域间开始。

因此 path选择不应写成“同node用NVLink、异node用IB”。Multi-node NVLink supernode已经破坏这个假设。Endpoint capability应直接说明 LDST/CFT/RDMA/MCAST/REDUCE reachability与locality class；team descriptor保存层级subgroup。这样同一算法可在36/72/未来不同规模partition上运行，也可在故障后缩成健康subgroup。

十、把单条 ISA 组合成真实 NVSHMEM 与 CCL

1. 真实源码的第一步永远是 dispatch

NVIDIA/NVSHMEM 当前 device path 已经展示了统一语义前端的雏形：以 peer_heap_base_p2p[pe] 和 symmetric offset 检查 direct reachability，按配置/eligibility 选择 ordinary mapped copy、TMA 或 CFT；不能 direct 时，transfer_device.cuh.in 再在 IBGDA、GPUNetIO GDAKI 和 CPU proxy transport 间 dispatch。Proxy path让GPU在内部ring预留credit、写请求，host progress thread代发；GDAKI path则在GPU选择QP、查lkey/rkey、预留WQE、写doorbell并poll CQ。也就是说一个 nvshmem_put 的真实实现已经是 decision tree，不是一行内联PTX。

在提案 ISA 下，runtime在初始化时把这棵树部分折叠进endpoint/context table；JIT或device library仍可根据local state space、size/alignment和capability选 scalar/bulk/descriptor。语义 IR 不变：

r = [endpoint_for_pe(pe), sym_ptr - local_heap_base]
t = net.put.async.issue::warp.shared r, src, bytes, ctx, event

Backend 若选CFT，补v1 mbarrier、proxy handoff与16B tail；选RDMA，合成WQE；选P2P，合作式store。Token/event把三个分支重新汇合，所以后续pipeline不需知道路径。

2. Blocking put、get 与 NBI 的 lowering

Blocking vector put只等source-safe：net.put.async 后对token做 source wait；若local operand已被硬件copy-in，wait可立即满足。Scalar p 的 value 是按值 operand，不存在调用者 source buffer，API可在目标更新完成前返回，因此只需确保命令已被接受/发起；需要远端完成时仍用 quiet。Blocking get必须等本地RESULT_VISIBLE，再以acquire让SM消费local destination；手册对get直接使用.complete::result_visible，不把它误写成remote write visibility，scalar g则同步返回读取值。put_nbi/get_nbi 在 ISSUED 后返回，不给每个API调用暴露显式handle，但communication resource内部记录watermark；ordinary nvshmem_quiet 完成其规范覆盖的 NVSHMEM issuance domain，QP-specific operation则用带显式 PE/QP set 的 nvshmemx_qp_quiet。

put_blocking:  t = net.put.async(...); net.token.wait.source(t)
p_scalar:      net.put.scalar.async(...); wait_until_issued_if_required; return
get_blocking:  t = net.get.async.complete::result_visible(...); net.token.wait.result_visible.acquire(t)
put_nbi:       net.put.async(...); return
flush:         net.source.wait(covered_nvshmem_resources)
quiet:         net.quiet.remote_visible.acquire(covered_nvshmem_resources, all_targets)

这组 lowering 解释了为何一个只会返回“done”的DMA engine不够：它要么让blocking put过度等待network round trip，要么让get提前返回。双缓冲中，communication warp在A的source-safe后就能让compute warp覆写A，同时remote completion在event中继续推进。

3. Put-with-signal 的最小正确序列

Producer先完成local tile，CTA sync并做generic→network release；随后发一条一级 net.put_signal.async.set.release，data offset与signal offset必须属于同一target endpoint/PE。Consumer在自己的symmetric signal上 net.mem.wait.acquire.u64.eq(epoch)，然后读payload。Epoch应单调增长或配phase，避免buffer复用产生ABA。

无fused硬件时，backend可在同一context内lower为：

net.put.async.release [ep,dataOff], src, n, ctx
net.fence.release ctx, ep        // delivery order, not completion
net.signal.async.set.release [ep,sigOff], epoch, ctx

NVLink pointer path可用copy+system/proxy order+atomic/store；TMA要先满足该payload的TMA依赖。Current NVSHMEM CFT lowering对payload使用blocking handle put，再执行system与fabric/generic proxy ordering，最后调用可用的signal path：SET可lower为masked 16B handle put，ADD则需要fabric atomic（current devel门控到CUDA 13.4）或其他atomic transport，不能把两种operator都概括为普通flag put。IBGDA可在同一RC QP排RDMA Write WQE与signal Atomic/Write WQE。若data跨多个context，先join ctxset，不能仅在signal所在QP做fence。

4. Fetching AMO 与分布式 work queue

一个worker用fetch-add在远端head预留index，再get descriptor：

idx = net.amof.sync.add.u64 [queue_ep, head_off], 1, ctx_ctrl
t   = net.get.async [local_slot], [queue_ep, item_base+idx*stride], bytes, ctx_data
net.token.wait.result_visible.acquire t

Fetching AMO同步形式适合立即依赖旧值；异步形式可把旧值写到shared/global result slot并返回token，以batch隐藏往返。NVLink backend用system atomic，NIC用FAA/CAS，unsupported endpoint走有guaranteed progress的service endpoint。当前NVSHMEM公开QP-specific API没有generic AMO，这里的context-scoped AMO是本文新增，不能误标为已有API。关键正确性条件是所有路径共享target atomic domain；若queue head可能同时被local SM和NIC更新，而平台没有共同serialization point，runtime必须固定一种路径。

5. QP-specific 双流水与跨 QP 发布

假设activation走custom QP A，checkpoint/control走QP B。二者独立可以让A的large read不阻塞B的小signal，也能只quiet A而不drain B。当前NVSHMEM public QP surface覆盖typed scalar p/g、typed contiguous put/get及put_nbi/get_nbi、signal_op、typed blocking/NBI put-with-signal和QP fence/quiet；vector RMA、put-with-signal、QP fence/quiet有warp/block cooperative forms，scalar p/g没有。不应虚构QP-specific strided、byte/fixed-size RMA、generic AMO、wait/test、collective或flush。

源码中的IBGDA/GDAKI实现还揭示一个有用事实：指定单个custom RC QP的fence在底层可退化，因为该QP已有必要顺序；需要覆盖多个/default communication resource的分支当前调用较便宜的quiet-like send-side drain（不做target-consistency upgrade）建立顺序，但API fence本身仍不保证完成。提案把这种复杂性放在net.fence(ctxset,target)后端。若A/B数据共同发布一个ready signal，最清晰的是aggregate event等两者remote-visible后触发signal；若只要求delivery order而非完成，则使用明确的cross-context epoch capability。

6. Wait/Test 与长期 producer-consumer 流水

Producer每轮把payload与epoch放到consumer PE；consumer的communication warp等待epoch，成功后以acquire把buffer交给compute warp。普通实现是volatile/load-compare-backoff，提案 net.mem.wait 可让warp suspend，并在remote NIC/NVLink写触发coherent monitor后唤醒。它必须重读验证，允许spurious wake但不允许spurious success。

只有producer使用put_signal，或使用合法的put→fence/quiet→signal发布协议时，成功wait才证明与该signal配对的data；任意RMA恰好把同一flag值写出来，只能证明比较命中，不能自动发布无关payload。即便采用正确发布协议，wait也不quiet无关context；event wait只证明origin-side tracked operation完成，不等同target signal。编译器可以把两者都放进async dependency graph：origin event控制outbound buffer复用，target memory wait控制inbound compute开始。一个MegaKernel同时需要这两条边。

7. Barrier 与 sync 的软件/硬件组合

NVSHMEM源码的device barrier先按QP_ALL范围drain network QP，并drain TMA/CFT等先前通信，再执行可配置radix的dissemination arrival；current source有2/4/8/16/32的特化，P2P-connected block team还可把radix设为team size。只有radix-2分支才可简写成第kk轮联系rank+2k2^k伙伴、约⌈log2P⌉\lceil\log_2P\rceil轮；最后实现还按需做target consistency。sync则省去完成先前remote work的部分。用提案表示，NVSHMEM barrier lowering是net.quiet(ALL_RELEVANT_CONTEXTS)加group arrive/wait，sync只是group arrive/wait与必要acquire；允许调用者传subset ctxset是本文通用ISA能力，不能用它弱化NVSHMEM barrier必须覆盖先前相关通信资源的语义。

超节点可把同一协议分层：tray内或NVLink subgroup用multicast arrival/reduction counter，subgroup leaders再做树，最后域内multicast release；net.coll.async.barrier若存在可接管descriptor。重要的是control context保留credit，group generation固定；一名failed member应让event返回member bitmap/terminal status，而不是让其余71张GPU无限等待。

8. Broadcast、fcollect 与 all-to-all

NVSHMEM broadcast源码包含tree put-signal、root-to-all+barrier、direct mapped copy和inter/intra-node层级算法；all-to-all在mixed connectivity下对remote peer用put-with-signal、对direct peer用NBI put，随后等待signals并quiet。统一ISA可自然表达“每条edge选最佳endpoint path，team协议统一闭合”。

Broadcast在超节点内优先 net.mcast.put.async(group)，无group capability退tree；跨超节点先RDMA tree到各域leader，再域内mcast。Fcollect/allgather可用rank-derived offset的direct all-to-all或ring chunk；all-to-all/MoE则把非空bucket组成IOV descriptor并跨多个context发。每个target最后用ordered signal或team barrier发布，不可因为所有WQE已经doorbell就宣称collective完成。

9. All-reduce：软件 ring、NVLS 与 IB SHARP 的同一依赖图

软件ring把每个chunk重复执行“remote get/receive→event acquire→local reduce→put_signal forward”；NVLink group可用 net.mcast.red push contribution，或每个member先写replica再 net.mcast.pullred；完整NIC/IB SHARP可接收net.coll.async.allreduce descriptor。Runtime显式携带datatype、op、accumulator precision与reproducibility mode，不能在要求确定性顺序时擅自换成任意switch reduction。

层级超节点版本按chunk流水：域内reduce-scatter → 域间RDMA/IB SHARP → 域内allgather/multicast。ctx_intra与ctx_inter并行，event把每个chunk的三个阶段连接，避免全局阶段barrier。只有最后API要求blocking时才等待所有chunk；MegaKernel可在某chunk完成域内allgather后立即消费它。

10. Triton-distributed/分布式 GEMM 的 tile pipeline

Distributed GEMM常见结构是compute warp算本地tile，communication warp预取下一remote tile或发送partial，另一组warp在event到达后做MMA。每个shared buffer配phase event：net.get.async.shared 把remote tile直接落B并attach event；compute等B的result_visible.acquire，消费后以local arrival允许复用。Outbound A只需在SOURCE_CONSUMED后复用，不必等target完成。Compiler IR必须把async get视为对destination的延迟写，把async put视为对source的延迟读，否则寄存器/shared allocation会被过早重用。

CFT 9.3已经为“shared tile + mbarrier + fault report”提供了重要底座；提案补global/scalar/context与统一completion。未来若硬件允许TMEM直接成为fabric operand，应新增有owner-warpgroup/lifetime规则的state-space profile，而不是把TMEM伪装成普通pointer。

11. MoE expert dispatch：AMO、稀疏 RMA 与 signal 的闭环

Routing lanes先对目标expert counter做fetch-add取得slot；小bucket用lane-vector scalar/short put，大bucket切bulk或IOV；每个expert的数据和最终count固定到同一context，或在多rail striping后join再release signal。目标expert warp acquire-wait count/epoch，随即做GEMM；结果用另一条put_signal返回。Credit不足时通信warp等待credit而不阻塞compute warp，control signal保留独立高优先级context。

这个案例同时使用symmetric heap（buffer/counter offset）、AMO（slot allocation）、RMA（token record）、signal/wait（ready）、context（traffic isolation）、event（buffer lifetime）和transport abstraction。它说明device-initiated CCL不是只有collective：最有价值的往往是用这些primitive构造数据依赖驱动的稀疏collective。

12. Fault-aware supernode collective

一次group put或reduction附带reporting event。若返回PARTIAL_GROUP，status给出effect class与opaque failed-member bitmap；runtime仅对确认缺失且幂等的put用健康unicast endpoint重试，不能对ADD reduction或signal ADD盲目重放。Put-with-signal必须保证失败成员不会观察到“成功epoch”，否则其payload可能部分更新却被消费。Group generation改变后，旧descriptor停止接受新issue，已有operation按captured generation完成或报错。

Supernode fault policy一般需要所有相关PE对新membership达成一致，再从checkpoint/phase boundary重建team、LE/group与context；这属于runtime。ISA负责让kernel从wait中醒来、准确报告“谁/哪一段/是否可能部分生效”，并允许安全drain/revoke。没有这条错误闭环，超节点越大，persistent device protocol永久hang的概率越高。

十一、从指令集到一台真正可运行的系统

1. Host control plane：先创建能力，再让 kernel 消费

Job bootstrap 先发现GPU/NVLink partition/NIC/topology；collectively建立symmetric heap与PE offset invariant；为direct path映射peer VA，为CFT reserve/create/import LE并bind heap chunk，为RDMA register MR、交换rkey/route并创建QP/CQ；再构造team/group/context/event pool，把只读handle table下发GPU。超节点还需要Fabric Manager/NVLSM/IMEX或等价系统服务配置routing、partition与跨OS process access。所有这些是慢路径，一次建立后被大量device operation复用。

Kernel退出/作业撤销按相反顺序：停止新issue，quiet/drain所有context，等待event终态，revoke device handles，解绑memory，destroy endpoint/QP/group，最后释放ID/registration。只销毁host object而不先处理in-flight operation会让异步engine访问已复用resource；规范必须定义generation与terminal error而不是依赖“用户别这么做”。

2. SM-side issue front end

每个SM或GPC需要小型command coalescer与per-context credit cache。Scalar op从register捕获value，cooperative op选leader并收集lane metadata，bulk op记录local range而非复制全部payload，descriptor op在bounded validation后缓存必要字段。Front end返回token/accepted predicate，只有source被copy-in或engine真正读完时才推进source-safe。

Hardware可把多条相邻lane request合并，也可让同一CTA批量commit一次doorbell；architectural token仍追踪logical operation。Queue full时.try立即返回，blocking/wait form挂起warp并让completion warp继续运行。公平仲裁至少区分control/signal、latency与bulk class；超节点全域barrier的signal不能饿死在几个大tensor后面。

3. Endpoint、context 与 capability translation

Fabric proxy用ep+off+size+op查endpoint table，检查generation、bounds、permission、endpoint type和op/type/alignment capability，产生canonical resource ID。Context table提供sequence、credit、priority、traffic class、target mapping、error stream与backend binding。两次查询可以并行，随后route到link或NIC adapter。TLB/IOMMU/PASID与rkey/LE细节对unprivileged code不可见。

为了超节点规模，table需支持多级缓存和压缩rank ranges；miss可由firmware walker读取GPU-global metadata，但accepted operation的progress不能依赖host page fault无限等待。Group entry保存immutable member generation和hardware multicast/reduction resource；membership update创建新entry，而不是原地改变in-flight operation含义。

4. 两条数据 engine 与一个 atomic home

低时延engine处理scalar put/get/AMO/signal，目标是少量cycle的issue与direct register path；bulk/descriptor engine处理shared/global tile、packetization、IOV和DMA，目标是带宽、合并与少doorbell。用一个通路包办两者会让标量承担descriptor启动成本，或让大copy占满SM load/store issue。

所有AMO必须在target-declared coherence/serialization point线性化。Link atomic、local SM atomic、NIC atomic若能进入同一home domain即可混用；否则endpoint capability规定单一路径或software service。Cache maintenance与proxy fence是可见性机制，不是原子序本身。Fetch result走completion response写回register spill/shared/global，再以token acquire释放给consumer。

5. Completion、event 与 wakeup engine

Backend不断推进per-context source、accepted、visible watermark；token比较sequence即可覆盖大量unsignaled operation，event将多个context/operation的完成原子汇总。Shared event可映射PTX mbarrier，global event适配NIC CQ与跨CTA/长驻kernel；event同时记录error predicate和opaque status reference。Target-side memory monitor订阅signal address，remote write/atomic使其失效/唤醒，warp重读并做acquire。

Completion engine还可提供条件trigger：一个aggregate event成功后自动发release signal，能在多QP stripe后避免SM先wait再signal；但trigger必须以预验证descriptor限制target/effect，错误时禁止发布success signal。超节点large-team event应分层聚合或用switch counter，避免72个成员竞争一个global cache line。

6. Scale-up adapter、RDMA adapter 与 collective engine

Scale-up adapter完成peer/CFT/multimem/TMA选择、16B staging/tail、proxy fence、NVSwitch request与group reduction；RDMA adapter维护WQE template、SQ/CQ producer、doorbell、registration split、RC/DC/multi-rail和CQ polling，并把transport ACK升级到endpoint visibility contract。两者向上只输出同样的completion/error vocabulary。

Optional collective engine消费runtime plan descriptor而不是裸team API。它可选择NVLS、IB SHARP或microcoded schedule，但必须尊重datatype/accumulator/reproducibility、group generation、scratch bounds与failure policy；不能honor时在issue阶段返回unsupported。超节点内/间两级engine可以为同一chunk产生一个aggregate event，使compiler仍看到一张依赖图。

7. Compiler/IR 的责任

IR必须显式保留endpoint、context、issuer scope、local state space、completion level、release/acquire和event。Async put是持续到source-safe的延迟读；async get是持续到result-visible的延迟写。优化器不能因instruction已经issue就复用buffer，也不能把signal越过未join的context；alias analysis还要知道generic/fabric/multimem地址可能指向同一resource但proxy不同。

Compiler可做lane coalescing、size/alignment specialization、shared staging、event allocation、double-buffer phase与capability multiversioning。DSL如Triton可以把distributed pointer lower成(endpoint,offset) IR，tile layout lower成descriptor，并在第一次实际use前插token wait，而不是在API call处立即阻塞。

8. 验证、性能计数器与可观测性

Correctness测试至少覆盖：每种RMA的buffer lifetime；data→signal litmus；跨context乱序与join；mixed proxy alias；AMO与local atomic compatibility；queue full/preemption；endpoint revoke；multicast partial effect；grid exit有outstanding op。Formal model应以operation/epoch而非packet描述，backend refinement再证明WQE/NVLink序列实现该模型。

性能计数器应按context/endpoint class统计issued bytes、coalescing ratio、credit stall、source/remote latency、CQ batch、retry、proxy fence与collective offload；不能把原始route/rkey暴露给普通进程。超节点还需按partition/switch/tray汇总拥塞与failed-member，帮助runtime重新分块/选路径。没有这些telemetry，用户只会看到“GPU kernel慢”，无法区分计算等待、queue starvation、网络拥塞或过强quiet。

十二、PTX 还缺什么，以及建议的演进顺序

1. 已有基础足以证明方向

PTX 9.3已经给出五个非常重要的架构判断：remote resource可用logical endpoint+offset而非裸pointer命名；fabric access是独立proxy；shared tile能异步进出fabric；source-read与full completion必须分开；failure是operation report而非必然process-fatal。更早的multimem又证明multicast/reduction应成为组primitive。这些不是边缘扩展，而是统一GPU fabric ISA的核心骨架。

2. 面向完整 NVSHMEM 的缺口

第一，CFT只有shared、16B bulk，缺register scalar、global operand与stride/IOV/tensor descriptor。第二，缺handle-addressed fetching AMO/CAS/swap与完整legality query。第三，缺64-bit signal SET/ADD和fused put-signal。第四，缺显式context/QP与ctxset fence/quiet。第五，completion只围绕显式mbarrier batch，没有transport-neutral token/watermark、global event和target coherence level。第六，缺scheduler-aware symmetric-variable wait/test。第七，CFT公开contract仍是NVLink domain，没有portable RDMA queue/context adapter。

3. 面向超节点的额外缺口

超节点把“能发一次远端copy”提升为“能让数十/数百GPU长期共同推进”。因此还需要group endpoint/generation与大team capability query，rank-range或hierarchical descriptor，multicast/push/pull reduction的统一错误语义，large event/arrival aggregation，context priority/credit reservation，partition/revoke/fault epoch，partial-member bitmap与effect class，以及域内/域间collective plan的异步event接口。现有multimem/CFT可承担data plane的相当部分，却没有公开这些resource-scale与RAS contract。

最值得优先硬化的并不是一条固定allreduce opcode，而是：group + event + context + status。它们让软件能在不同超节点规模、partition与故障条件下安全组合broadcast/allreduce/MoE；固定algorithm仍可由可选collective engine加速。

4. 推荐路线

第一阶段在PTX/CUDA层补transport-neutral context、scalar/global RMA、AMO/signal/put_signal、source/quiet/token/event与wait/test；CFT成为NET-LINK backend，NIC runtime提供NET-RDMA backend。第二阶段补bounded IOV/tensor、context-set epoch、global event trigger与group fault status。第三阶段标准化hierarchical group/collective descriptor、TMEM operand与可选SHARP/NIC offload。每阶段都保留capability/fallback，且将“PTX已有”与“新提案”在ABI文档中显式标注。

5. 不应加入的东西

不要把raw rkey/lkey、QPN、PSN、WQE bit layout、doorbell address、NVLink route/packet、MTU或retry counter写入通用ISA；它们既不跨硬件，也扩大攻击面。不要为每个NVSHMEM datatype/API/thread-group变体造opcode。不要用一个全局net.sync同时承担fence、flush、quiet、barrier与signal。也不要让硬件在ambiguous partial AMO后静默retry。这些“少做的事”与新增指令同样决定架构寿命。

十三、结论：把通信设计成异步远端内存语义

1. 完整逻辑闭环

NVSHMEM用PGAS和symmetric heap把“哪个PE的哪个对象”变成稳定的逻辑地址；runtime把它翻译为endpoint+offset，并创建context/team/registration；GPU发RMA/AMO/signal，ordering与分层completion规定何时复用buffer、何时目标可见；wait/barrier/collective再把one-sided effect编成跨PE协议。NVLink、CFT、TMA、RDMA WQE、NVLS与IB SHARP只是这条链的不同backend。至此从API、memory、network、ISA、hardware到consumer同步形成闭环。

2. 最终架构判断

一套能支撑NVSHMEM、device CCL、Triton-distributed与MegaKernel的ISA，应把自己描述为“对受保护endpoint的异步memory operation”，而不是“GPU发送packet”。它的核心不是opcode数量，而是五个不被混淆的对象/语义：endpoint+offset、context/order domain、RMA/AMO/signal、source/remote completion、group/event/error。NVLink与IB在adapter层分开，在这些语义上统一。

超节点进一步证明这个判断：物理上跨tray/node，逻辑上仍可能是一个scale-up memory fabric；若ISA按“本机/远程”二分就会失效，若按capability、group与context组织则自然扩展。面向几十到数百GPU，multicast/reduction、层级team、聚合completion、QoS/credit与fault containment不再是附加优化，而是系统能否持续运行的基础。

十四、附录：与编码无关的 net.* ISA 指令集手册 v0.1

1. 通用定义

规范性状态。 本附录规定了所提议的 net.* 架构。标签 [PTX 9.3 精确对应/概念相近/部分对应] 标识其与公开 PTX 的对应关系；标签 [新增] 标识本文提出的设计。组合标签统一写作 [新增；PTX 部分对应] 或 [新增；PTX 概念相近]；可选扩展写作 [新增；可选]。除非明确标注为 PTX，否则 net.* 助记符不是 NVIDIA 指令。本规范与编码无关（encoding-neutral）：语法定义的是架构行为，而不是指令位域。

A.1.1 架构操作数类型

ep          不透明的 32 位逻辑端点标识符
off         端点资源地址窗口内的无符号 64 位字节偏移
raddr       二元组 [ep, off]
ctx         不透明的通信上下文句柄
ctxset      有界 CTXSET 描述符的本地地址，或 DEFAULT/ALL
ctxsel      一个 ctx、一个 ctxset，或特殊选择器 DEFAULT/ALL
group       不透明且不可变的组端点/句柄
team        由运行时配置的不透明通信组/秩映射句柄
member_sel  ALL_MEMBERS、内联掩码，或有界 MEMBERSET 描述符
token       不透明的 64 位操作令牌
event       自然对齐的本地完成事件地址
status      32 位状态码；零表示 SUCCESS
status_ref  不透明的 64 位诊断记录引用；零表示没有详细记录
accepted    谓词；当且仅当异步命令在架构上已被接受时为 true

bytes       无符号传输大小
local       指定 GPU 存储空间中的本地虚拟地址

targetsel   一个端点、端点集合描述符，或 ALL_ENDPOINTS

ctx、group 和 team 的确切位宽是实现能力档（profile）的属性。它们通过通用寄存器或一致寄存器（uniform register）传递，应用程序代码不得解释其内容。描述符选择使用普通的本地地址位宽，并以带标签编码表示特殊选择器。

所提议的 [ep:u32, off:u64] 形式有意映射公开 PTX 9.3 的 CFT 句柄操作数，但并未声明它在 ABI 上与 CUDA 中进程本地的 CUlogicalEndpointId 关联兼容。CUDA 13.3 公开定义的逻辑端点类型只有单播和多播。本附录中的端点代次、权限掩码、传输后端选择、原子域、路由策略、规范资源身份、健康纪元和端点表布局，全部都是新增提案字段，并非 CUDA 逻辑端点对象中有文档记载的成员。导入的 CUDA 端点在每个进程中可以与不同的预留 leId 关联。

A.1.2 通用限定符

.try                       绝不等待发射信用额度；返回 accepted 谓词/status
.issue::{thread,vector,warp,cta}
.shared::cta | .global     本地操作数的状态空间
.relaxed | .release | .acquire | .acq_rel
.scope::{cta,gpu,sys}      本地内存有序性作用域
.complete::{source,remote_accepted,remote_visible,result_visible}
.report::{none,event}      异步错误的目的地
.count::{ops,bytes}        事件完成计量单位

除非另有说明，发射指令默认采用 .issue::thread.relaxed.scope::sys.report::none，并采用与方向相匹配的最终可见完成级别：远端写入/更新使用 .complete::remote_visible，远端读取/取值/拉取归约使用 .complete::result_visible。.scope 控制本地网络代理的有序性；端点上的效果始终具有系统/互连织构作用域。若所选端点或上下文不支持某个限定符，则这是发射错误，不得静默弱化该限定符。

.issue::thread 为每个参与线程创建一个逻辑操作和一个结果元组。.issue::vector 为每个活跃 warp 通道创建一个独立的操作/结果元组；实现可以合并数据包，但不得合并令牌、错误或原子效果。.issue::warp 和 .issue::cta 是要求参与者会聚的协作形式，它们恰好创建一个逻辑操作：控制操作数必须一致，参与的通道/线程共同搬运所指定的范围，结果谓词/寄存器也必须一致。除非明确支持掩码的能力档另有规定，否则发散或参与不完整属于集合不匹配错误。协作式会合不会发布由另一通道/warp 产生的数据；程序仍须在发射之前执行必要的 warp/CTA 同步以及释放语义/网络代理所有权移交。

.complete::source 和 .complete::remote_accepted 分别选择 SOURCE_CONSUMED（源已消费）和 REMOTE_ACCEPTED（远端已接受）。.complete::remote_visible 为远端写入/更新选择 REMOTE_VISIBLE（远端可见），而 .complete::result_visible 为远端读取/取值/拉取归约选择 RESULT_VISIBLE（结果可见）；把任一最终完成限定符用于错误方向都会产生发射错误。RESULT_VISIBLE 表示本地结果已经可见，而不是某个远端写入已经可见。对同一操作而言，达到更强的完成级别蕴含已经达到每个较弱的完成级别；但任何完成级别都不蕴含无关操作或无关上下文已经完成。

A.1.3 .try 与非 .try 发射

本提案中通用的异步结果元组为：

{token, accepted, status}

对于 .try，accepted=false 表示该操作在架构上没有产生任何数据效果、有序性效果、事件贡献或远端效果，并且 token 无效。QUEUE_FULL 可以重试，其他发射错误也可能返回 accepted=false。对于非 .try 形式，实现可以暂停执行，直到存在本地命令信用额度；保护、能力和操作数错误仍遵循所配置的受检执行（checked execution）策略。

命令被接受仅表示达到 ISSUED。它不表示源数据已被消费、数据包已被注入、远端已接受操作或远端已经可见。

本提案中的 .try 拼写不等同于 PTX fabric.try_* 的契约。公开 PTX 9.3 Fabric 操作不会返回本提案中的 accepted 谓词、令牌和同步状态元组；操作失败通过报告型 mbarrier.layout::v1 异步上报。不得因为二者都使用 try 一词，就推断它们具有相同的发射信用额度或无效果语义。

A.1.4 事件附着

带有 .report::event 的指令以 event 作为最后一个操作数。当所请求的 .complete 级别到达时，该操作为事件贡献一个操作计数；在 .count::bytes 下，则贡献其架构定义的字节数。发生错误时，必须先置位事件的错误谓词并记录一个不透明的状态引用，然后再贡献完成计数。事件必须具有充足的期望计数、匹配的活跃阶段，以及一个不强于指令所选 .complete 级别的完成层级下限。该下限防止把“源已消费”事件误认为远端发布已经完成。

如果软件在 .try 发射之前调用 net.event.expect，而发射返回 accepted=false，则它必须不断重试直至命令被接受，或者使用 net.event.arrive.error 补偿未被使用的期望项，并把发射状态带入聚合事件。成功形式的 net.event.arrive 不能用于失败补偿，因为它可能使触发器发布并未完成的工作。非 .try 发射可避免这类簿记。实现可以提供可选的自动增加期望计数附着模式，使 expected 只在命令被接受时以原子方式递增，但基础代码不得假定该模式存在。

A.1.5 对齐与边界

基础能力档支持字节传输，但可以报告优选/最小对齐要求。仅仅导致速度变慢的未对齐访问是合法的；如果原子性、事件布局、所选加速模式或描述符编码要求特定对齐，则必须检查该要求。除非显式启用了特权非受检能力档，否则每个远端字节和每个描述符分段都必须根据端点资源执行边界检查。

A.1.6 失败原子性

线性复制、描述符复制、组复制和归约在异步失败时可能已经产生部分效果，不隐含回滚。本提案的可靠能力档要求标量信号和 AMO 操作必须满足“恰好一次或无效果（exactly-once or no-effect）”；公开 PTX 9.3 的 Fabric 报告机制本身并不建立这一失败原子性保证。除非状态能够证明操作没有效果，或者协议使用幂等键，否则运行时不得重试一个可能非幂等的操作。

A.1.7 同步错误交付

具有显式 status 目的操作数的指令返回稳定的状态类别，并且不会因一个已被表示的动态错误而触发陷阱。对于 .try，accepted=false 还进一步证明没有产生任何架构命令效果。没有 status 目的操作数的指令，要么在编译/汇编阶段拒绝非法的静态限定符，要么针对动态操作数、布局或保护错误触发该能力档的同步受检执行异常；它绝不会静默弱化限定符，也不会在对象无效时继续执行。异常记录携带下文定义的同一状态类别命名空间。实现可以暴露特权非受检模式，但可移植的 NVSHMEM/CCL 代码不能依赖它。

A.1.8 进展与公平性

操作被接受后，无需主机轮询即可取得进展，也不要求发射操作的 warp 或目标 PE 执行匹配的接收。只要其端点/上下文代次仍处于活跃状态，它最终就会到达所请求的终态成功或终态错误状态。非 .try 发射、信用额度等待、令牌/事件等待和内存等待都是调度器感知的挂起点；在架构上，它们不得忙等，也不得阻止完成代理获得调度。实现通过能力查询公布上下文信用额度、优先级/流量类别、前向进展和有界饥饿类别。软件仍有责任避免会消耗掉全部预留信用额度的循环协议，并负责为控制/完成路径配置执行资源。

A.1.9 保护与虚拟化

每个端点、上下文、上下文集合、组和通信组都是由运行时创建、绑定到 VM/PASID，并检查代次的受保护对象。应用程序可见的句柄绝不暴露 RDMA rkey、原始 NIC 门铃或传输队列地址。端点偏移检查、权限、原子域和资源代次对 NVLink/NVSwitch 与 IB/RDMA 传输后端一视同仁。导入可以在另一进程中分配不同的数值句柄；可移植代码把所有句柄都视为进程本地的不透明值。创建、绑定、撤销、导出/导入和拆除仍是主机运行时/驱动程序的职责。

A.1.10 上下文与有序域规则

ctx 是逻辑上的注入域、进展域、完成域和有序域；传输后端可以把它绑定到一条 NVLink 注入流、一个 RDMA QP、一个 DCI，或一条复用在物理队列之上的虚拟通道。不同上下文默认彼此无序。ctxset 只是一个选择/快照对象：只有当 net.fence、net.quiet 或事件汇合等指令显式建立跨上下文关系时，才存在跨上下文的交付顺序或完成关系。在一个共享上下文内，每个发起者都有各自的程序顺序；只有在普通 GPU 同步把所有权转移给负责捕获水位线的发起者后，另一发起者的水位线才会被纳入覆盖范围。

2. 能力与资源指令

A.2.1 net.cap.query — 查询架构级 Fabric 能力 [新增]

语法

net.cap.query.u64 d, cap, object;

操作数

  • d：目的寄存器。
  • cap：立即数/寄存器形式的能力选择符，包括 ISA 版本、支持的能力档、端点/上下文/事件数量限制、本地地址空间、描述符最大分段数、数据类型/操作符掩码、完成级别、事件大小/对齐以及执行作用域。
  • object：根据 cap 的要求，取 DEVICE、某个 ep、某个 ctx 或某个 group。

功能与语义 — 返回 object 的不可变能力值，或由健康纪元限定有效期的能力值。仅对布尔选择符而言，返回零表示不支持；带类型的选择符分别定义其零值含义。

排序 — 不产生排序或完成效果。

完成 — 同步地产生寄存器结果；不会创建网络操作。

异常与能力 — 基础指令。BAD_QUERY 或陈旧对象以同步方式报告。

PTX 对应 — 设备侧 ISA 层没有对应指令。 CUDA 主机 API 可以查询 CFT/逻辑端点属性，但公开 PTX 中没有等价的通用设备侧能力查询指令。

A.2.2 net.ep.query — 查询端点状态 [新增]

语法

net.ep.query.u64 d, ep, property;

操作数 — d 接收一个 64 位属性值；ep 是被查询的受保护端点；property 取 READY、TYPE、PERMISSIONS、SIZE、TRANSPORT_CLASS、ATOMIC_DOMAIN、HEALTH_EPOCH、MAX_TRANSFER、ALIGNMENT、COMPLETION_MASK 或 ERROR_POLICY 之一。

功能与语义 — 读取当前进程/VM 可见的端点表属性。READY 仅供参考：查询之后就绪状态仍可能变化，因此发射状态才是权威结果。

排序 — 不产生数据排序。相对于驱动程序对新就绪端点代次的发布，该读取具有获取语义。

完成 — 同步产生寄存器结果。

异常与能力 — 基础指令；可能报告 BAD_ENDPOINT、STALE_HANDLE、BAD_QUERY。

PTX 对应 — 无。 CFT 端点的生命周期和就绪状态由主机管理。CUDA 13.3 提供主机侧 cuLogicalEndpointQuery，用于查询构建就绪状态，并提供主机侧属性/限制与设备能力属性；它不提供这里的设备侧查询指令，也不提供本文提议的 PERMISSIONS、TRANSPORT_CLASS、ATOMIC_DOMAIN、HEALTH_EPOCH、COMPLETION_MASK 和 ERROR_POLICY 属性集合。

A.2.3 net.ctx.query — 查询上下文状态 [新增]

语法

net.ctx.query.u64 d, ctx, property;

操作数 — d 接收一个 64 位属性值；ctx 是被查询的上下文；property 包括 VALID、CREDIT_AVAILABLE、CREDIT_LIMIT、PRIORITY、RELIABILITY、ORDERING_MODE、TRANSPORT_CLASS、ERROR_EPOCH 和 COMPLETED_WATERMARK。

功能与语义 — 返回上下文配置或一个采样得到的动态计数器值。动态结果仅供参考，并且可能立即发生变化。

排序 — 不产生 Fabric 数据排序效果。

完成 — 同步产生寄存器结果。

异常与能力 — 基础指令；陈旧或未获授权的上下文报告 BAD_CONTEXT。

PTX 对应 — 无。

A.2.4 net.addr.check — 验证远端范围与操作权限 [新增]

语法

net.addr.check pred, status, [ep, off], bytes, access, type;

操作数 — 验证成功时 pred 为 true，否则 status 给出失败类别；[ep,off],bytes 指定精确的受保护远端范围；access 取 READ、WRITE、ATOMIC、SIGNAL、REDUCE 或 COLLECTIVE；在相关情况下，type 给出原子操作/归约的数据类型。

功能与语义 — 执行与发射阶段相同的端点代次、范围、权限和静态能力检查，但不创建操作。它面向带检查的 DSL 和描述符预检；它不预留任何资源，也无法消除之后发生的动态故障。

排序 — 不产生数据排序或资源预留效果。

完成 — 同步产生谓词/状态结果。

异常与能力 — 基础指令。返回失败结果而不触发陷阱。

PTX 对应 — 无。

A.2.5 net.ctx.credit.test — 测试本地命令信用额度 [新增]

语法

net.ctx.credit.test pred, available, ctx, needed;

操作数 — pred 报告采样比较结果；available 接收采样得到的信用额度数量；ctx 是被查询的通道；needed 是所需信用额度数量。

功能与语义 — 采样当前是否至少有 needed 个发射信用单位可用，并返回采样得到的数量。该指令不预留信用额度。

排序 — 不产生命令或数据排序，也不预留信用额度。

完成 — 同步完成采样。

异常与能力 — 基础指令；可能报告 BAD_CONTEXT。结果为 false 并不表示错误。

PTX 对应 — 无。

A.2.6 net.ctx.credit.wait — 以调度器感知方式等待命令信用额度 [新增]

语法

net.ctx.credit.wait{.issue} status, ctx, needed;

操作数 — status 报告成功/拆除；ctx 选择通道；needed 是建议的最小信用额度数量。.issue 选择线程/warp/CTA 参与形式。

功能与语义 — 挂起参与者并暂停其调度，直到采样得到的可用信用额度至少为 needed，或者上下文出错或被拆除。该指令不预留信用额度；紧随其后的 .try 发射仍可能在竞争中失败。

排序 — 不产生网络命令或数据排序效果。

完成 — 当采样到信用额度条件为 true 或发生终止性上下文错误时完成；不意味着任何网络数据已经完成。

异常与能力 — 基础指令；可能报告 BAD_CONTEXT、CONTEXT_CLOSED。warp/CTA 形式要求集合式调用。

PTX 对应 — 无。

A.2.7 net.group.query — 查询组的成员、代次、层次结构和健康状态 [新增]

语法

net.group.query{.u64|.handle} d, group, property {, index};

操作数 — group 是一个不可变的受保护组句柄。property 取 VALID、GENERATION、MEMBER_COUNT、LOCAL_RANK、HIERARCHY_LEVELS、SUBGROUP_HANDLE、NATIVE_OP_MASK、INLINE_MEMBER_BITS、HEALTH_EPOCH 或 FAILED_MEMBER_REF；在需要时，index 选择某个层次级别或子组。标量属性使用 .u64；SUBGROUP_HANDLE 使用 .handle，其宽度是通过查询获得的实现能力档句柄宽度。

功能与语义 — 返回不可变的成员关系元数据，或一个由健康纪元限定有效期的值。FAILED_MEMBER_REF 是由运行时解码的不透明值。查询从不改变成员关系；重新配置会创建一个新的代次。

排序 — 相对于驱动程序对被查询组代次的发布具有获取语义；不产生数据排序或集合式操作排序。

完成 — 同步产生寄存器结果。

异常与能力 — NET_GROUP；可能报告 BAD_GROUP、STALE_HANDLE、BAD_QUERY。动态健康状态仅供参考；操作发射结果才是权威结果。

PTX 对应 — 无。 CUDA/NVSHMEM 主机 API 可以创建通信组、多播对象和逻辑端点；公开 PTX 没有通用的设备侧组查询指令。

3. 提交与 RMA 指令

A.3.1 net.submit — 提交此前暂存的操作 [新增；PTX 部分对应]

语法

net.submit{.op_restrict::fetching}{.issue} ctx;

操作数 — ctx 选择上下文。.op_restrict::fetching 选择此前的远端读取、拉取归约和取值操作；若不使用该限定符，则选择当前执行发起者此前暂存的所有网络操作。

功能与语义 — 使选中的、此前暂存的操作具备由传输层执行的资格。已经提交的操作不受影响。线程/向量形式选择每个发射线程此前的操作；收敛的 warp/CTA 形式选择所有参与发起者的并集，截止位置为各发起者捕获的水位线。立即入队的实现可以将其视为保持排序的空操作。在本文提案中，令牌/事件/完成等待的观察会隐式提交其覆盖的操作；这是一个新增提议语义，并非 PTX 已有事实。降低到 PTX 时必须插入 fabric.submit：PTX 要求发射线程在关联的 mbarrier 阶段前进之前，显式提交被跟踪的 Fabric 操作，否则行为未定义。

排序 — 保持被提交操作在上下文中的顺序；它不是交付栅栏。

完成 — 在记录提交后返回，而不是在源完成或远端完成后返回。

异常与能力 — 基础指令；可能报告 BAD_CONTEXT、集合不匹配。

PTX 对应 — 部分对应： PTX 9.3 fabric.submit 及 .op_restrict::fetching 提交当前线程此前发出的 Fabric 操作。PTX 没有 ctx 操作数、组发起者作用域、结果令牌，也没有本文提议的上下文顺序契约。

A.3.2 net.put.async — 异步线性远端写入 [新增；PTX 部分对应]

语法

net.put.async{.try}{.issue}{.shared::cta|.global}
             {.relaxed|.release}{.scope}{.complete}{.report}
    token, accepted, status, [ep, off], [src], bytes, ctx {, event};

操作数 — [ep,off] 指定首个目标字节；[src] 是本地源地址；bytes 是传输大小；ctx 是有序域/进展域；使用 .report::event 时必须提供 event。

功能与语义 — 接受一个逻辑上的单边远端写入。引擎可以拆分或合并传输请求。在达到 SOURCE_CONSUMED（源已消费）之前，源范围必须保持有效且不得修改。零字节操作不产生数据效果，但如果实现支持，它仍可产生令牌/事件完成；否则以 BAD_SIZE 拒绝。

排序 — .release 在引擎读取源数据以及本操作产生远端效果之前，以 .scope 指定的作用域导入此前的通用内存写入。仅当上下文模式与显式 net.fence 有相应规定时，同一上下文内才存在交付顺序；仅仅被接受并不构成栅栏。

完成 — 令牌支持 SOURCE_CONSUMED、REMOTE_ACCEPTED 和 REMOTE_VISIBLE。事件按所选 .complete 级别作出贡献。在达到相应完成级别之前，远端可见数据可能发生撕裂。

异常与能力 — NET-BASE。发射错误包括端点、上下文、权限、边界、事件、描述符错误以及不满足规定的对齐。异步路由错误、保护错误或部分写入错误附着在令牌/事件上。本地共享内存源要求 NET_LOCAL_SHARED。

PTX 对应 — 仅在数据移动方面部分对应到概念相近： PTX 9.3 fabric.try_put 从 .shared::cta 写入 CFT 句柄。必须区分它的不同机制：fabric.wait.sync_restrict::reads 只等待已提交操作对本地 CTA 共享内存源的读取；报告型 mbarrier.layout::v1 的一个阶段观测被跟踪操作的完整完成状态和错误；受支持远端写入变体上的 .counted::bytes 通过独立的远端计数器跟踪目标数据访问，它本身只表示部分完成。上述机制都不会自动与本文提出的每一种可移植完成级别完全等价。PTX 的 try 也不返回本文提案中的发射接受谓词/令牌。本文提案还覆盖全局内存源、显式上下文和更广泛的发射作用域。

A.3.3 net.get.async — 异步线性远端读取 [新增；PTX 部分对应]

语法

net.get.async{.try}{.issue}{.shared::cta|.global}
             {.relaxed}{.scope}{.complete}{.report}
    token, accepted, status, [dst], [ep, off], bytes, ctx {, event};

操作数 — [dst] 是位于限定地址空间中的本地目的地址；[ep,off],bytes 指定受保护的远端源范围；ctx 选择有序域/进展域；token、accepted、status、event 遵循通用异步约定。

功能与语义 — 接受一个逻辑上的远端读取。在结果完成之前，不得读取或覆盖本地目的范围。完成之前，中间产生的部分字节可能已经可见，但不得被消费。

排序 — 远端读取顺序遵循上下文与端点契约。使用 .acquire 进行等待会把结果导入通用内存代理。交付栅栏不对非阻塞远端读取的返回值进行排序；这需要令牌、事件或完成等待达到相应完成级别。

完成 — RESULT_VISIBLE（结果可见）：所有请求的字节均已在本地目的范围中可见。通过 .complete::result_visible 选择该级别；它不是 REMOTE_VISIBLE，因为远端读取不会产生远端写入效果。SOURCE_CONSUMED 仅覆盖本地描述符元数据，通常并不重要。

异常与能力 — NET-BASE；发射错误和异步错误与远端写入类似。失败时，可能已经写入的目的子范围内各字节的值未指定；状态不提供回滚保证。

PTX 对应 — 仅在数据移动方面部分对应到概念相近： PTX 9.3 fabric.try_get 将 [srcLeId,srcDataOff] 复制到 .shared::cta，并使用 mbarrier.layout::v1 的字节完成计数/报告机制。fabric.wait.sync_restrict::reads 不为 try_get 提供排序，因为远端读取操作写入共享内存，而不是读取共享内存源。PTX try 没有本文提议的 accepted/令牌元组。本文提议的全局内存目的地址、上下文以及与传输后端无关的可见性范围更广。

A.3.4 net.put.scalar.async — 异步寄存器到远端写入 [新增]

语法

net.put.scalar.async{.try}{.issue}.{type}
                    {.relaxed|.release}{.scope}{.report}
    token, accepted, status, [ep, off], value, ctx {, event};

操作数 — [ep,off] 是远端目的地址；type 取 b8/b16/b32/b64/b128，但须受端点能力支持；value 保存在寄存器中；ctx 选择有序域/进展域；token、accepted、status、event 遵循通用异步约定。

功能与语义 — 不使用本地暂存缓冲区，直接写入一个标量。除非端点另外声明该大小的自然对齐标量写入具有原子性，否则该操作不具备原子性；需要原子性时应使用 AMO 或信号操作。

排序 — 与远端写入相同；.release 将此前的本地写入排在该远端写入之前。

完成 — 不存在源缓冲区生存期约束。令牌支持“远端已接受”和“远端可见”两个级别。

异常与能力 — NET_SCALAR_RMA；可以通过暂存缓冲区高效模拟，但若硬件不原生支持，则编译器/运行时必须提供存储空间。

PTX 对应 — 没有通用的 CFT 句柄对应指令。 指针形式的 st 可以把直接映射的对等端内存作为目标，但这只是一种传输后端特定的部分替代方案。

A.3.5 net.get.scalar.sync — 同步远端标量读取 [新增]

语法

net.get.scalar.sync{.issue}.{type}{.relaxed|.acquire}{.scope}
    value, status, [ep, off], ctx;

操作数 — value 接收标量；status 接收最终状态；[ep,off] 是远端源地址；ctx 是有序域/进展域；type 选择标量的宽度和解释方式。

功能与语义 — 读取一个标量，并在该值可用于 value 后返回。在等待传输延迟期间，发起者可以被暂停调度。仅当结果一致，或者按照执行作用域能力档显式分发时，warp/CTA 形式才有效。

排序 — .acquire 将之后的通用内存访问排在已经完成的读取之后，作用范围由 .scope 指定。除非上下文的读取顺序明确要求，否则它不完成 ctx 中此前无关的操作；如有此需求，应使用完成等待。

完成 — 同步达到“结果可见”完成级别。

异常与能力 — NET_SCALAR_RMA；由于该指令会等待完成，异步错误通过 status 返回。不支持的类型会被拒绝。

PTX 对应 — 没有通用的 CFT 句柄对应指令。 从映射的对等端内存执行指针形式的 ld 是一种部分替代方案。

A.3.6 net.xfer.desc.async — 执行传输描述符 [新增]

语法

net.xfer.desc.async{.try}{.put|.get}{.issue}
                   {.relaxed|.release}{.scope}{.complete}{.report}
    token, accepted, status, [desc], ctx {, event};

操作数 — desc 指向有界且带版本号的 LINEAR、STRIDED、IOV 或 TENSOR 描述符。它包含全部本地/远端分段及形状元数据；强制使用的 .put/.get 指令限定符是唯一的传输方向字段。ctx 选择有序域/进展域；token、accepted、status、event 遵循通用异步约定。

功能与语义 — 验证并执行描述符；在完成与错误聚合方面，将其视为一个逻辑操作。各分段的数据效果等价于实现以同一上下文中某个由实现决定的合法线性操作序列来执行。在达到 SOURCE_CONSUMED 之前，描述符内存本身必须保持不变；远端写入载荷则遵循各自的源缓冲区生存期。

排序 — 仅当设置 ORDERED_SEGMENTS 时，分段顺序才是描述符顺序；否则，不重叠的分段可以按任意顺序执行。.release 与上下文栅栏把该描述符视为一个逻辑操作。彼此重叠且无序的分段非法。

完成 — 令牌/事件可以按一个描述符操作计数，也可以按总载荷字节数计数。“远端可见”完成级别覆盖全部分段。

异常与能力 — NET_DESCRIPTOR；检查长度、种类、分段数、算术溢出、范围与权限。异步失败可能只影响部分操作，并标识一个分段或不透明位图。

PTX 对应 — 公开 PTX 9.3 Fabric 指令族中没有对应指令。TMA/张量描述符解决的是另一类本地/全局内存复制问题，并不提供远端端点语义。

4. 原子操作与信号指令

A.4.1 net.amo.async — 无返回值的远端原子操作 [新增；PTX 部分对应]

语法

net.amo.async{.try}{.issue}.{op}.{type}
             {.relaxed|.release}{.scope}{.complete}{.report}
    token, accepted, status, [ep, off], operand {, compare}, ctx {, event};

.op   = set | add | and | or | xor | min | max | cas_nofetch
.type = u32 | s32 | u64 | s64 | b32 | b64 | f32 | f64 | profile-defined

操作数 — [ep,off] 是按要求对齐的原子操作目标；operand 是更新值或交换值。cas_nofetch 还要提供 compare，且仅在目标值与之相等时才执行更新，但不返回旧值。ctx 选择排序与进展资源；token、accepted、status、event 遵循通用异步约定。

功能与语义 — 在端点所声明的原子性域内执行一次可线性化的目标端 AMO。set 是丢弃旧值的原子交换。整数 inc 被降低为 add 1。有符号性只影响 min/max；按位操作使用 b32/b64。浮点操作遵循端点所声明的 NaN、舍入、非规格化数清零（flush）和可复现性模式。

排序 — .release 将此前的本地通用代理效果排序到网络代理中。远端操作之间的相对顺序由上下文与排序栅栏语义建立。原子操作的线性化顺序本身并不排序无关地址上的访问。

完成 — token 支持远端已接受和远端可见两个完成级别；远端可见表示 AMO 已经线性化，其效果已在目标端一致性点可见。

异常与能力 — 基础能力要求支持端点所声明的、按要求对齐的 32/64 位整数 add、set 和按位操作；其他所有 op/type 组合都受能力门控。可靠能力档要求错误语义为恰好一次或无效果（exactly-once or no-effect）。

PTX 对应 — 只有受限的部分子集： PTX 9.3 fabric.try_red 是一种源位于 CTA 共享内存、要求 16 字节对齐且长度为 16 字节整数倍的批量逐元素归约。其文档化操作族涵盖 b32/b64 上的按位 and/xor/or、部分整数及 f16/bf16 的 min/max，以及部分整数和浮点 add 变体。它不支持 set/exchange、CAS 或取回结果，也没有公开建立本提案所要求的任意端点原子性域、可线性化性（linearizability）或失败时恰好一次契约。PTX atom、red 和 multimem.red 使用的是指针或 multimem 地址模型，并不是通用的 CFT 句柄 AMO。

A.4.2 net.amof.async — 异步带返回值的远端原子操作 [新增]

语法

net.amof.async{.try}{.issue}.{op}.{type}{.global|.shared::cta}
              {.relaxed|.release}{.scope}{.report}
    token, accepted, status, [result], [ep, off], operand {, compare}, ctx {, event};

.op = fetch | set | swap | add | and | or | xor | min | max | cas

操作数 — 位于限定符指定本地地址空间中的 [result] 接收旧值；[ep,off] 是按要求对齐的原子操作目标。fetch 没有更新操作数；cas 接收比较值 compare 和替换值 operand。ctx 选择排序与进展资源；token、accepted、status、event 遵循通用异步约定。

功能与语义 — 对远端对象进行原子读/修改，并将更新前的值异步写入本地 result。fetch 是位于同一修改顺序中的原子读。在达到结果可见之前，不得使用目标缓冲区中的结果。

排序 — .release 作用于向外发送的更新。以获取语义等待 token 或 event 会导入取回的结果。net.fence 不负责排序带返回值的结果；该结果由其自身的完成机制排序。

完成 — 结果可见表示 AMO 已经线性化，并且旧值已在本地可见。对于会修改目标的操作，它蕴含更新已经达到远端可见。

异常与能力 — 需要 NET_FETCH_AMO；本地地址空间、op/type 组合以及所需的共同原子性域都必须受支持。本提案的可靠能力档要求恰好一次或无效果。NET-NVSHMEM 强制要求原生的 32/64 位 fetch/CAS 或自主服务路径，但其他带返回值的操作可以通过组合方式实现。

PTX 对应 — 不存在面向通用 CFT 句柄的对应指令。 当远端对象被直接映射并且共享所需原子性域时，PTX 指针形式的 atom 可以作为部分替代。

A.4.3 net.amof.sync — 同步带返回值的远端原子操作 [新增]

语法

net.amof.sync{.issue}.{op}.{type}
             {.relaxed|.release|.acquire|.acq_rel}{.scope}
    old, status, [ep, off], operand {, compare}, ctx;

操作数 — old 接收更新前的值；status 是最终状态；[ep,off] 是原子操作目标；operand 是更新值或替换值；CAS 还包含 compare；ctx 选择上下文。

功能与语义 — net.amof.async 的同步寄存器结果形式。发起者被挂起或取消调度，直至操作完成或发生错误。

排序 — .release 和 .acquire 限定符分别作用于此前向外发送的效果，以及向内返回的结果和后续通用代理访问。

完成 — 成功时，更新已经远端可见，旧值已经可在寄存器中使用。

异常与能力 — op/type 要求与异步形式相同。状态被同步返回。

PTX 对应 — 不存在面向 CFT 句柄的对应指令； 指针形式的 atom 可以部分对应。

A.4.4 net.signal.async — 远端 64 位信号更新 [新增]

语法

net.signal.async{.try}{.issue}.{set|add}
                {.relaxed|.release}{.scope}{.complete}{.report}
    token, accepted, status, [ep, off], value:u64, ctx {, event};

操作数 — [ep,off] 指定 64 位信号对象；value 是 set/add 操作数；ctx 选择排序与进展资源；token、accepted、status、event 遵循通用异步约定。

功能与语义 — 在端点指定且具备信号能力的位置上执行原子的 64 位信号 set 或 add。除非端点策略报告溢出，否则信号加法按模 2^64 运算。在可靠端点上，更新具有恰好一次或无效果语义。

排序 — 具有释放语义的信号将此前覆盖范围内的通用代理效果排序到网络代理中，并参与上下文的交付顺序。若要发布此前的远端 RMA，这些 RMA 操作必须处于同一上下文/目标域中并配合交付栅栏，或者由跨上下文纪元覆盖。

完成 — token 或 event 达到远端可见，表示信号更新已经线性化，并能被目标端的 net.mem.test/wait 观察到。

异常与能力 — 需要 NET-BASE 信号能力；要求 8 字节对齐并具有 SIGNAL 权限。

PTX 对应 — 不存在完整的公开 CFT 句柄对应指令。 指针原子操作或存储可以实现特定于传输后端的情形。PTX fabric.try_put 具有批量与对齐限制，本身不能提供这里所需的 64 位原子信号契约。

A.4.5 net.put_signal.async — 有序远端写后更新信号 [新增]

语法

net.put_signal.async{.try}{.issue}{.shared::cta|.global}.{set|add}
                    {.release}{.scope}{.complete}{.report}
    token, accepted, status,
    [data_ep, data_off], [src], bytes,
    [sig_ep, sig_off], sig_value:u64, ctx {, event};

操作数 — [data_ep,data_off],bytes 指定远端数据范围；[src] 是位于限定符所指定本地地址空间中的源；[sig_ep,sig_off] 是按要求对齐且具备信号能力的 u64 对象，sig_value 是其 SET/ADD 操作数；ctx 是二者共同的发布域；token、accepted、status、event 遵循通用异步约定。只有当上下文声明数据端点与信号端点共享同一个发布顺序域时，二者才可以不同；否则发射失败，软件必须采用显式的跨目标协议。

功能与语义 — 执行一次写入，并在全部数据写入都按发布顺序交付后，以原子方式 set/add 信号。以获取语义观察到信号的消费者能够观察到已经成功交付的数据。对于排序、token 和事件状态而言，这是一个逻辑操作，尽管传输层可以发出多个请求。

排序 — 相对于源数据的生产始终具有释放语义。信号排在每一个数据分片之后。除非普通的上下文/排序栅栏规则建立了顺序，否则信号之后的操作不会自动排在信号之后。

完成 — SOURCE_CONSUMED 允许复用源。REMOTE_VISIBLE 表示数据和信号都已可见。若部分数据传输失败，可靠实现必须抑制成功信号，或者报告信号状态不确定；当已知所发布的数据不完整时，实现绝不能报告成功。

异常与能力 — NET_PUT_SIGNAL 作为融合实现是可选能力，但其语义可以降低为写入、交付栅栏与信号三个步骤。实现会检查信号的对齐与权限，以及两个资源范围。

PTX 对应 — 不存在作为一级 CFT 句柄指令的对应形式。 只有当可用的 PTX 或运行时操作能提供所需的同域交付排序时，才可以组合实现。

PTX 9.3 的计数式目标端完成机制可以支持一种接收端聚合完成协议，但它不是通用 put_signal(add,bytes) 的语义降低。只有受支持的 fabric.try_put/fabric.try_red .counted::bytes 变体提供该机制；端点必须声明支持计数式完成，计数器大小为 8 字节且按 256 字节对齐，计数器与数据不得重叠，并且 .cp_mask 与之不兼容。计数器以系统级原子方式、按未指定的粒度为每个目标字节递增一次；共享该计数器的并发操作彼此无序，而且 multimem 操作只计算其目标设备上的访问。等待最终聚合计数值能够证明目标数据访问已经发生，但其本身既不会创建本提案所要求的有序应用信号，也不会创建从 Fabric 代理到通用代理的释放/获取发布边。

5. 组与集合通信指令

A.5.1 net.mcast.put.async — 组内复制式写入 [新增；PTX 部分对应]

语法

net.mcast.put.async{.try}{.issue}{.shared::cta|.global}
                   {.release}{.scope}{.complete}{.report}
    token, accepted, status, [group_ep, off], [src], bytes,
    member_sel, ctx {, event};

操作数 — [group_ep,off],bytes 指定不可变复制式资源组中各成员彼此对应的目标字节；[src] 是本地源；member_sel 可以选择 ALL_MEMBERS、不超过 INLINE_MEMBER_BITS 的内联子集，或者一个有界、经过代次检查的 MEMBERSET 描述符；ctx 和公共的结果/事件操作数选择进展与报告方式。

功能与语义 — 将相同的源字节写入每个选定成员上相同的资源相对偏移。一个逻辑操作可能在不同成员上得到不同的传输结果。

排序 — 释放语义和上下文排序作用于每个选定成员。此后针对特定目标的排序栅栏必须指定组代次，或者逐一指定每个规范化成员。

完成 — 远端可见要求所有选定且成功的成员上的写入都已可见。部分失败会设置 PARTIAL_GROUP，并给出成员位图或不透明报告。源已消费与成员端的完成相互独立。

异常与能力 — 需要 NET_GROUP_PUT；各成员的资源大小和权限必须兼容。软件回退方案会发出多个单播写入，并用一个事件聚合其完成状态。

PTX 对应 — 部分对应： PTX 9.3 fabric.try_put.multimem 能够写入多播逻辑端点所引用的资源，但它没有可动态选择端点成员子集的操作数，也不提供本提案的逐成员结果位图/上下文契约。因此，在当前 PTX 上，本文提出的 member_sel 需要使用彼此独立的端点句柄，或者回退到单播。

A.5.2 net.mcast.red.async — 向组推送归约贡献 [新增；PTX 部分对应]

语法

net.mcast.red.async{.try}{.issue}{.shared::cta|.global}.{op}.{type}
                   {.release}{.scope}{.complete}{.report}
    token, accepted, status, [group_ep, off], [src], count,
    member_sel, epoch, ctx {, event};

操作数 — group_ep 定义归约结果是被复制到各成员、只放在根成员，还是存储在交换机/NIC 归约对象中。member_sel 使用通用的可扩展成员选择编码。epoch 区分连续的集合通信实例。count 是元素数量。

功能与语义 — 向受保护的组归约对象推送一个向量贡献。组描述符定义预期贡献者和结果放置方式。除非组能力明确将二者结合，否则一个贡献的完成并不意味着整个集合通信已经完成。

排序 — 释放语义将源数据的生产排序在贡献注入之前。各贡献可以按照数值模式所允许的任意结合顺序进行组合。

完成 — 源已消费允许复用源；远端可见表示该贡献已经在声明的归约一致性点被纳入。可选的集合通信完成事件是一种组能力，不能默认存在。

异常与能力 — 需要 NET_GROUP_REDUCE；实现会检查操作符、数据类型、元素数量、对齐、纪元和成员关系。必须明确声明重复贡献者策略；默认行为是报错，而不是重复计数。

PTX 对应 — 部分对应： PTX 9.3 fabric.try_red 的受支持句柄/multimem 变体可以执行文档化的批量逐元素归约，但它没有本提案中的成员子集操作数、纪元/贡献者跟踪、逐成员状态或上下文契约。

A.5.3 net.mcast.pullred.async — 拉取并归约组资源 [新增；PTX 部分对应]

语法

net.mcast.pullred.async{.try}{.issue}{.shared::cta|.global}.{op}.{type}
                       {.relaxed}{.scope}{.complete}{.report}
    token, accepted, status, [dst], [group_ep, off], count,
    member_sel, ctx {, event};

操作数 — [dst] 是本地归约结果缓冲区；[group_ep,off] 选择各成员彼此对应的资源；count 是元素数量；member_sel 选择参与者；ctx 和可选的 event 提供进展与完成机制。

功能与语义 — 从选定的组成员读取彼此对应的元素，对其进行归约，并将结果向量写入本地目标。归约顺序/数值模式由端点能力与限定符决定。

排序 — 该操作按照组的读一致性契约对成员值进行采样；除非能力明确声明，否则它并不是跨不同地址的原子快照。以获取语义等待 token 或 event 会导入本地结果。

完成 — 结果可见表示完整的归约向量已在本地可见。部分成员失败会报告错误；除非启用了已定义的缺失成员单位元策略，否则结果字节未指定。

异常与能力 — 需要 NET_GROUP_PULLRED；操作符、数据类型、成员数量和本地地址空间能力必须受支持。

PTX 对应 — 部分对应： PTX 9.3 fabric.try_pullred 提供文档化的 CFT 多播拉取归约，其目标位于 CTA 共享内存、粒度为 16 字节、通过报告型 mbarrier 报告完成，并要求整个 warp 同步发射。它的 imm-membermask=0xFFFFFFFF 是发射 warp 的通道会合掩码，并不是多播端点的成员选择掩码；因此不能直接降低本文提出的动态 member_sel。

A.5.4 net.coll.async — 执行集合通信描述符 [新增；可选]

语法

net.coll.async{.try}{.issue}.{kind}
              {.relaxed|.release|.acq_rel}{.scope}{.report}
    token, accepted, status, [coll_desc], team, ctxset {, event};

.kind = barrier | sync | broadcast | allgather | alltoall |
        reduce | allreduce | reduce_scatter | scan

操作数 — coll_desc 包含版本、缓冲区、计数/位移、数据类型/操作符、根成员、暂存空间、算法提示、数值模式和实例纪元。team 提供不可变的成员关系与秩映射。ctxset 提供通信资源。指令的 .kind 必须与描述符中的 collective_kind 相同。

功能与语义 — 将一个有界的固件/硬件集合通信实例入队。该指令不会创建通信组、分配暂存空间、选择任意无界算法，也不会在没有错误策略的情况下无限等待缺席的参与者。在达到 SOURCE_CONSUMED 之前，描述符及其引用的元数据数组必须保持不变；输入缓冲区遵守所选集合通信的源生命周期规则，而暂存空间必须保留到结果可见。实现可以拒绝不受支持的描述符，以便运行时启动软件调度方案。

排序 — 释放语义导入本地输入的生产效果；获取语义的完成导入输出。barrier 只排序其描述符/API 语义所要求的内容；除非设置了 COMPLETE_PRIOR_RMA，否则它并不隐含全局完成等待。

完成 — SOURCE_CONSUMED 在适用时解除描述符、其引用的元数据以及输入缓冲区的读取生命周期。按照描述符的定义，当本地参与者的集合通信义务和输出可见性均已完成时，token 或 event 达到远端可见或结果可见。若请求且能力支持，还会单独报告全通信组完成。

异常与能力 — 需要 NET_COLL_OFFLOAD；所有参与者必须使用匹配的通信组代次、纪元、kind 和兼容的描述符字段。错误包括 COLL_MISMATCH、MISSING_PARTICIPANT、SCRATCH_TOO_SMALL、UNSUPPORTED_ALGORITHM 以及部分互连织构故障。

PTX 对应 — 不存在通用指令。 特定的 PTX Fabric/multimem 原语可以实现或卸载特定集合通信的部分步骤。

6. 代理、排序与完成指令

A.6.1 net.proxy.fence — 在通用代理与网络代理之间建立顺序 [新增；PTX 部分对应]

语法

net.proxy.fence.to_net.release.scope::{cta,gpu,sys};
net.proxy.fence.to_generic.acquire.scope::{cta,gpu,sys};
net.proxy.fence.acq_rel.scope::{cta,gpu,sys};

操作数 — 无显式寄存器操作数。方向限定符和 scope 限定符选择参与排序的本地内存代理及其可见性范围。

功能与语义 — to_net.release 使 scope 范围内先前由通用代理执行的写入，对该发起者后续由网络代理进行的源数据读取或发布可见。to_generic.acquire 使已经观察到完成的网络代理写入，对后续由通用代理进行的读取可见。acq_rel 同时组合这两个方向。

排序 — 这是本地代理之间的排序操作。它既不提交、投递或完成任何网络操作，也不能替代 net.fence 或 net.quiet。

完成 — 同步完成的本地排序操作；不存在远端完成。

异常与能力 — NET-BASE；不同作用域的开销可能不同。在采用统一一致性代理的平台上，硬件或编译器可以将其实现为空操作，但仍须保留其语义。

PTX 对应 — 部分对应/概念相近： PTX ISA 9.3 增加了精确的系统作用域形式 fence.proxy.{generic::fabric|fabric::generic|fabric::fabric}.alias.{release|acquire}.sys;，要求 sm_100+。在 PTX 的 to_proxykind::from_proxykind 书写方式中，顺序由 from 代理先前的访问指向 to 代理后续的访问；.alias 涉及同一内存位置的虚拟地址别名。这些形式没有上下文/端点选择器，而且普通的 fence.sys 本身并不自动成为 Fabric 投递栅栏。

A.6.2 net.fence — 跨上下文/目标域建立投递顺序分界 [新增]

语法

net.fence.release{.issue} status, ctxsel, targetsel;

操作数 — ctxsel 是上下文或上下文集合描述符；targetsel 是一个端点、一个端点集合或 ALL_ENDPOINTS。

功能与语义 — 捕获排序栅栏纪元之前所有被覆盖的操作，并保证这些操作的投递先于该纪元之后、面向同一组选中规范目标的被覆盖操作。它保证投递顺序，而不保证完成。在映射 NVSHMEM 语义时，它不对非阻塞读取或非阻塞/异步取值 AMO 返回值的到达建立顺序；但不能把这一排除项错误地扩大到同步取值操作已经返回的结果。

对于多上下文选择，排序栅栏建立一个跨上下文的统一纪元。硬件或固件可以保守地排空所选上下文，之后才放行排序栅栏之后的操作。仅仅在各个 QP 上分别插入彼此独立的排序栅栏并不足够，除非后端能够证明这些 QP 共享同一个纪元。

排序 — 释放分界。发起参与者不能把排序栅栏之后被覆盖的操作排在该分界之前入队。其他发起者的操作只有在通过 GPU 同步或运行时协议，与被捕获的上下文水位线建立先行发生（happens-before）关系时，才会受到该排序栅栏的约束。

完成 — 当分界已经建立或被接受时返回，而不是等待排序栅栏之前的操作完成。

异常与能力 — 单一上下文要求 NET-BASE；任意上下文集合要求 NET_CTXSET_FENCE。无效集合或端点、已经关闭的上下文，或者不支持跨上下文纪元，都会在放行排序栅栏之后的操作以前报告错误。

PTX 对应 — 无。 PTX 9.3 的 fabric.submit 可以提交操作，但没有规定 NVSHMEM 所要求、针对目标/上下文的投递栅栏语义。代理栅栏解决的是另一个问题。

A.6.3 net.source.wait — 等待先前的源数据读取结束 [新增；PTX 部分对应]

语法

net.source.wait{.issue}{.acquire}{.scope} status, ctxsel;

操作数 — status 接收源数据消费状态；ctxsel 选择被覆盖的上下文；.issue 和 .scope 限定符选择参与者以及允许复用数据的本地作用域。

功能与语义 — 提交并等待，直到网络引擎停止读取所选上下文上、由当前参与者发起的所有被覆盖先前操作的本地源数据字节和描述符字节。完成后可以复用缓冲区和描述符，但它不等待远端数据效果生效。

排序 — 获取语义保证后续覆盖写入或复用发生在源数据消费之后。它不为后续操作建立远端投递顺序。

完成 — 仅达到 SOURCE_CONSUMED。

异常与能力 — NET-BASE。返回在这一层已知的任何源数据读取错误；之后才出现的远端错误仍保持待处理状态。

PTX 对应 — 相近的子集： PTX 9.3 的 fabric.wait.sync_restrict::reads 等待已提交 Fabric 操作对本地共享内存的读取结束。本文提出的指令增加了上下文选择、对更一般本地地址空间的支持以及状态返回。

A.6.4 net.quiet / net.quiet.async — 完成先前操作 [新增]

语法

net.quiet{.issue}.remote_visible.acquire
    status, status_ref, ctxsel, targetsel;

net.quiet.async{.try}{.issue}.remote_visible{.report}
    token, accepted, status, ctxsel, targetsel {, event};

操作数 — ctxsel 和 targetsel 界定要创建快照的范围；同步形式的 status 汇总该快照的状态，status_ref 指向可选的效果或成员级详细信息；异步形式返回 token、accepted、status，并可选择关联 event。

功能与语义 — 为被覆盖的先前操作创建快照、提交这些操作，并使整个快照达到请求的合法完成级别。同步形式等待完成；异步形式返回一个表示完成水位线的 token。remote_visible 是实现 NVSHMEM 风格完成等待所要求的级别。可以为诊断目的提供更弱的 remote_accepted 形式，但除非端点能力明确声明两者等价，否则不得用它实现完成等待。

排序 — 同步形式的 .acquire 引入本地读取/取值结果和完成写入。完成等待还阻止调用发起者后续被覆盖的操作重排到其快照之前，但它本身不是跨发起者的内存屏障。

完成 — 所有被覆盖的写入、AMO 和信号效果均在远端可见，所有读取/取值结果均在本地可见。错误会被汇总；成功意味着所有被覆盖的操作都成功。

异常与能力 — 单一上下文要求 NET-BASE；上下文集合和目标集合的作用域受能力控制。上下文拆除必须使完成等待以错误完成，绝不能静默返回成功。

PTX 对应 — 不存在上下文范围的 NVSHMEM 完成等待。 等待 PTX mbarrier 可以为该屏障显式跟踪的操作提供完整完成语义，因此能够实现一个批次，但公开文档中没有通用的上下文/目标完成等待指令。如果目标随后通过通用代理别名消费由 Fabric 写入的资源，那么仅有批次完成也不能替代所需的 Fabric→通用代理发布/获取协议。

A.6.5 net.token.test — 测试单个操作的完成状态 [新增]

语法

net.token.test.{source|remote_accepted|remote_visible|result_visible}
               {.relaxed|.acquire}{.scope}
    done, error, status, status_ref, token;

操作数 — token 标识操作或水位线；done 是是否达到所请求级别的谓词；error 报告终止性故障；status 提供故障类别，status_ref 指向可选的效果、成员或分段详细信息。

功能与语义 — 以非阻塞方式测试 token 是否达到请求级别。remote_visible 仅对表示远端效果的 token 合法；result_visible 仅对表示本地结果的 token 合法。当 done=false 时，error/status 只是暂定值，并且不执行获取操作。当 done=true 时，error/status 对该 token 和完成级别而言是最终值。

排序 — .acquire 仅在 done=true 时生效；它保证在后续通用代理访问之前引入已经完成的本地网络写入。

完成 — 不改变原操作的状态；只观察该操作。

异常与能力 — NET-BASE；过期的 token 或属于错误上下文的 token 报告 BAD_TOKEN。令牌保留上限可以查询；如果某个已回收令牌的水位线已知完成，则等待该令牌仍视为成功。

PTX 对应 — 部分概念对应： 非阻塞的 mbarrier.test_wait 可以测试被跟踪的 Fabric 完成阶段，但带 report 操作数时要求使用 .phase_type::primary 形式，而且仅能在 waitComplete=true 时检查报告。PTX 没有公开这里所定义的通用令牌/完成级别对象。

A.6.6 net.token.wait — 等待单个操作完成 [新增]

语法

net.token.wait.{source|remote_accepted|remote_visible|result_visible}
               {.relaxed|.acquire}{.scope}{.issue}
    error, status, status_ref, token;

操作数 — token 标识操作或水位线；error、status 和 status_ref 接收最终类别及可选的详细信息引用；完成级别、排序作用域和参与者模式由限定符给出。

功能与语义 — 必要时提交 token 对应的操作，并使调度器挂起执行，直到达到请求级别或发生终止性错误。remote_visible 仅对表示远端效果的 token 合法；result_visible 仅对表示本地结果的 token 合法。在体系结构语义上，它不是忙等轮询。

排序 — .acquire 引入本地结果或完成效果。等待一个令牌不会完成先前彼此无关的操作，除非上下文排序使这些操作成为该令牌完成的前置条件。

完成 — 达到所请求的令牌完成级别。

异常与能力 — NET-BASE；BAD_TOKEN、上下文拆除以及异步操作状态。

PTX 对应 — 部分概念对应： 围绕 mbarrier.try_wait.phase_type::primary（或 mbarrier.test_wait）构造循环，可以观察被跟踪 Fabric 操作的完成及其报告。单次 try_wait 仅可能阻塞，而且可能在阶段完成之前恢复；只有带获取语义且返回 true 的等待才建立相应的获取模式。PTX 没有通用的上下文令牌或完成级别选择器。

7. 完成事件指令

A.7.1 事件布局与生命周期

事件是一个不透明对象，其实现相关的大小和对齐要求可通过查询获得，并带有一个阶段编号。它维护 expected、completed、完成级别下限、期望计数封存位、错误谓词，以及指向首个错误或聚合错误的不透明引用。事件操作与网络完成更新之间具有原子性。事件可以位于 .shared::cta；位于 .global 的事件要求 NET_GLOBAL_EVENT。如果前一阶段仍有尚未完成的期望完成量，就不能重新初始化事件。完成级别下限规定网络操作可以为事件贡献完成量的最低级别；请求关联更弱完成级别的操作会被拒绝。

A.7.2 net.event.init — 初始化事件阶段 [新增；PTX 概念相近]

语法

net.event.init{.shared::cta|.global}.count::{ops|bytes}
              .complete::{source|remote_accepted|remote_visible}
    [event], expected, phase;

操作数 — [event] 是位于指定地址空间的不透明事件存储；expected 是精确的完成单位目标值；phase 是调用者选择的代次/阶段；.complete 声明该阶段的最低网络完成级别。

功能与语义 — 使用精确的期望完成计数初始化一个静止事件，并清除错误状态。网络操作可以按该完成级别或更强级别关联并贡献完成量，但绝不能使用更弱级别。在发起者关联操作之前，程序必须向这些发起者发布初始化结果。

排序 — 在指定本地内存地址空间中执行具有释放语义的初始化。

完成 — 同步完成的本地初始化。

异常与能力 — 共享内存事件是基础能力；全局内存事件是可选能力。对齐错误、重新初始化仍存活的阶段，以及不受支持的计数模式都会报错。

PTX 对应 — 概念相近的子集： 使用 mbarrier.layout::v1 的 mbarrier.init；PTX 的期望传输量/报告机制提供了相关的生命周期语义。本文提出的可移植完成级别下限字段是新增能力。

A.7.3 net.event.expect — 增加期望完成计数 [新增；PTX 概念相近]

语法

net.event.expect{.shared::cta|.global}.count::{ops|bytes}
    [event], delta, phase;

操作数 — [event] 和 phase 标识仍存活的事件阶段；delta 按照事件的计数模式，增加预期的操作数或字节数。

功能与语义 — 在相应操作可能完成之前，以原子方式把 delta 加到当前活动阶段的 expected 计数。程序如果在已经观察到完成之后又与之竞争地执行增加期望计数操作，则属于错误程序。

排序 — 对同一发起者后续关联操作提供释放语义。跨线程使用时仍需要普通 GPU 同步。

完成 — 同步完成的本地更新。

异常与能力 — 要求事件能力；计数溢出、阶段错误、阶段已完成，或者已经因接受触发器而封存期望计数的阶段，都会报错。

PTX 对应 — 概念相近的对应： mbarrier 的 expect_tx 机制。

A.7.4 net.event.arrive — 贡献一次本地完成 [新增；PTX 概念相近]

语法

net.event.arrive{.shared::cta|.global}{.release}{.scope}
    [event], delta, phase;

net.event.arrive.error{.shared::cta|.global}{.release}{.scope}
    [event], delta, phase, error_status, status_ref;

操作数 — [event]/phase 标识仍存活的阶段；delta 是已经在本地完成的单位数。在 .error 形式中，非零 error_status 和可选的 status_ref 是在到达操作之前记录的输入诊断值。地址空间和 scope 指明事件的位置及释放语义的覆盖范围。

功能与语义 — 增加本地 completed 计数，使本地生产者与网络操作可以共享同一个阶段事件。delta 的单位必须匹配事件的计数模式。.error 形式先以原子方式设置聚合错误，再增加 completed 单位；当发射失败且操作没有产生任何效果时，可用它闭合事先建立的期望项。

排序 — 释放语义保证先前的本地写入排在到达操作之前。它本身不对网络代理建立顺序；为此应使用代理栅栏或关联一次网络完成。

完成 — 同步完成到达更新；事件阶段可能由此变为完成状态。

异常与能力 — 要求事件能力；计数溢出或阶段错误会报错。.error 拒绝把 SUCCESS 用作 error_status，并依据当前 VM/保留域验证非零引用。

PTX 对应 — 成功的到达操作存在概念相近的对应；.error 是新增形式： mbarrier 到达操作覆盖计数更新，但公开 PTX 没有与本文所提形式等价、可由软件注入且与传输层无关的错误记录机制。

A.7.5 net.event.test — 测试事件阶段 [新增；PTX 概念相近]

语法

net.event.test{.shared::cta|.global}{.relaxed|.acquire}{.scope}
    done, error, status_ref, [event], phase;

操作数 — done/error 是谓词；status_ref 是不透明错误详细信息；[event]/phase 标识被观察的阶段。

功能与语义 — 当请求阶段满足 completed >= expected，而且所有关联的完成更新均已可见时，返回完成状态。同时返回聚合错误状态。

排序 — 获取语义只在 done=true 时生效，并保证在后续通用代理读取之前引入所有对该阶段作出贡献的完成写入。

完成 — 仅执行观察。

异常与能力 — 要求事件能力；地址未正确对齐、布局错误或阶段错误。

PTX 对应 — 概念相近的子集： 在 mbarrier.layout::v1 上使用非阻塞 mbarrier.test_wait 的 .phase_type::primary 报告形式；PTX report 操作数仅能在 waitComplete=true 时检查，而且对象位于 CTA 共享内存，而不是通用全局事件。

A.7.6 net.event.wait — 等待事件阶段 [新增；PTX 部分对应]

语法

net.event.wait{.shared::cta|.global}{.acquire}{.scope}{.issue}
    error, status_ref, [event], phase;

操作数 — error 和 status_ref 接收聚合结果；[event]/phase 标识待等待的阶段；.issue/.scope 选择等待参与者和获取语义覆盖范围。

功能与语义 — 使调度器挂起执行，直到该阶段完成或事件进入终止性无效状态。它返回事件的错误谓词和不透明状态引用。

排序 — 获取语义保证在后续通用代理读取之前，引入所有关联到该事件的成功本地目的数据和完成记录。

完成 — 聚合的期望计数完成。

异常与能力 — 要求事件能力；全局等待可能要求一致性的唤醒引擎。超时属于策略或运行时机制，不是默认 ISA 语义。

PTX 对应 — 部分概念对应： 围绕 mbarrier.try_wait.phase_type::primary（或非阻塞的 mbarrier.test_wait）构造循环，可以等待带报告的 .layout::v1 阶段。PTX 中没有 mbarrier.wait 助记符；单次 try_wait 可能在完成前返回 false，而且 PTX 不提供本文提案所定义的全局事件或终止性无效契约。

A.7.7 net.event.status — 读取事件错误信息 [新增；PTX 部分对应]

语法

net.event.status{.shared::cta|.global}
    error, status_ref, completed, expected, [event], phase;

操作数 — 目的寄存器接收错误谓词/引用/计数器快照；[event]/phase 选择事件阶段。

功能与语义 — 以原子方式取得计数器和不透明聚合错误引用的快照。运行时或驱动程序把 status_ref 解码为成员、分段和错误的详细信息；应用程序不得假定其位布局。

排序 — 除非与已经完成且带获取语义的测试/等待操作结合，否则不隐含获取语义。

完成 — 仅执行观察；既不推进事件，也不等待事件。

异常与能力 — 要求事件能力。

PTX 对应 — 部分概念对应： PTX Fabric 报告机制把谓词和报告载荷放在 mbarrier 中，而 CUDA API 解码不透明的 Fabric 错误状态。

A.7.8 net.event.clear — 回收已经完成的事件阶段 [新增]

语法

net.event.clear{.shared::cta|.global} status, [event], phase;

操作数 — status 报告回收结果；[event]/phase 标识要回收的已完成阶段。

功能与语义 — 回收已经完成的阶段，并释放实现所占用的错误记录资源。它不会初始化下一个阶段；初始化由 net.event.init 完成。在未完成的阶段上执行清除会失败，但不会取消操作。

排序 — 只对事件元数据执行释放操作。

完成 — 同步完成的本地回收操作。

异常与能力 — EVENT_BUSY、阶段错误或布局错误。这里有意不提供通用取消指令，因为远端 RMA 可能已经产生部分效果。

PTX 对应 — 不存在独立的 Fabric 指令； mbarrier 生命周期中的重新初始化具有相关约束。

A.7.9 net.event.trigger.signal — 在聚合事件成功后发布信号 [新增；可选]

语法

net.event.trigger.signal{.try}{.issue}.{set|add}.release
    token, accepted, status,
    [event], phase, [ep, sig_off], value:u64, ctx;

操作数 — [event], phase 选择仍处于活动状态，或者已经完成但尚未清除的聚合事件；[ep,sig_off] 指向支持信号的 64 位目标；value 是 SET/ADD 操作数；ctx 携带发布命令。token、accepted、status 遵循通用异步发射约定。

功能与语义 — 设置一个预先验证的一次性触发器，并以原子方式封存该阶段的 expected 计数；此后的 net.event.expect 调用将失败，从而保证完成引擎不会在迟到的期望项出现之前发布信号。当指定阶段成功完成后，引擎恰好发出一次具有释放语义的信号。如果阶段已经完成，则成功设置触发器会立即调度该信号。如果任何贡献操作出错，成功信号会被抑制，而返回的 token 以 DEPENDENCY_FAILED 和 NO_EFFECT 完成。这样可以汇合分条使用的多个上下文，而无须仅为发布就绪状态而唤醒 SM。触发器只能接受完成级别下限为 .complete::remote_visible 的事件；否则发射不产生任何效果，并报告 INCOMPATIBLE_EVENT_LEVEL。

排序 — 每个在远端可见级别成功贡献的网络操作以及事件的最终成功判定，都先行发生于该释放信号。一次本地到达操作可以控制触发器，但它本身既不传递先前的本地写入，也不把这些写入发布到 Fabric 代理；源数据生产仍须进入一次具有释放语义的网络操作，或者使用所要求的代理交接。触发器不包括无关操作。目标端具有获取语义的等待只引入该事件所覆盖的远端效果。

完成 — 接受只表示一次性触发器已经设置。返回的 token 与生成的信号一起达到 REMOTE_ACCEPTED/REMOTE_VISIBLE，通过测试/等待查询时，依赖错误或信号传输错误的详细信息由 status_ref 携带。如果已经接受的触发器仍处于待处理状态，则不能清除事件。不得把触发器令牌反向关联到其源事件，从而形成循环依赖。

异常与能力 — NET_EVENT_TRIGGER；事件阶段错误、端点未授权、信号上下文不兼容、INCOMPATIBLE_EVENT_LEVEL 或 DEPENDENCY_FAILED。.try 遇到容量不足时返回 accepted=false，且不设置触发器。ADD 要求恰好一次或无效果语义。

PTX 对应 — 无。 PTX mbarrier 完成机制可以驱动软件控制流，但公开的 PTX 9.3 没有自主的事件到远端信号触发器。

8. 点对点内存同步

A.8.1 net.mem.test — 比较本地可寻址的同步对象 [新增]

语法

net.mem.test{.global|.shared::cta}.{type}.{cmp}
            {.relaxed|.acquire}{.scope}
    pred, observed, [addr], compare;

.type = u32 | s32 | u64 | s64
.cmp  = eq | ne | lt | le | gt | ge

操作数 — [addr] 是本地可监视的同步对象；compare 是比较操作数；observed 接收采样值；pred 接收比较结果。类型、比较方式、地址空间和内存顺序均由限定符指定。

功能与语义 — 以原子且相干的方式采样 [addr]，并返回采样值和比较结果。全局地址可以由本地 GPU、对等链路操作或经由声明端点相干点的 NIC DMA 更新。

排序 — 获取语义仅在 pred=true 时生效；当它与释放发布协议配对时，会使后续通用内存访问排在产生已观测值的写入之后。测试失败不产生获取效果。

完成 — 同步完成本地采样；除观测到该发布本身所能确立的事实外，不隐含任何网络操作已经完成。

异常与能力 — 对齐的全局 u64 信号对象属于 NET-BASE；其他地址空间或类型受能力门控。地址必须位于可监视的相干内存中。

PTX 对应 — 没有专用的通用对应指令。 可以用具有获取语义的加载/原子指令配合轮询循环中的比较来实现，但这种实现不具备调度器感知的等待行为。

A.8.2 net.mem.wait — 以调度器感知方式等待同步对象 [新增]

语法

net.mem.wait{.global|.shared::cta}.{type}.{cmp}
            {.acquire}{.scope}{.issue}
    observed, status, [addr], compare;

操作数 — [addr] 和 compare 定义受监视的条件；observed 接收满足条件的值；status 报告成功或终止性失败；限定符选择类型、比较方式、地址空间、作用域和参与者。

功能与语义 — 通过重复采样或受监视采样，持续等待直到比较成功，同时允许调度器暂停调度该参与者。被唤醒后必须重新验证条件；允许伪唤醒，但不允许伪成功返回。

排序 — 成功返回在所请求的作用域上具有获取语义。它与同一相干域中的释放信号、写入后信号或其他有效的释放写入配对。

完成 — 仅在比较成功，或发生终止性的本地错误或上下文拆除错误时返回。它不表示无关网络操作已经达到完成等待条件。

异常与能力 — NET-BASE 支持可监视的全局 u64；组发射模式要求以集合式方式调用，并在满足该组指定的条件策略时返回。超时或取消属于独立的运行时策略，或未来的可选指令。

PTX 对应 — 没有可由单条指令完成的对应实现。 NVSHMEM 实现通常使用加载/比较/退避循环以及特定于传输层的进展机制；PTX mbarrier 等待监视的是 mbarrier，而不是任意对称信号地址。

9. 状态与诊断约定

本 ISA 不设置独立的 net.error.decode 操作码。解码不透明的异步 status_ref、查询路由历史、取得逐成员位图、重置端点以及选择重试或故障转移，均由运行时或驱动程序负责。这样可以保持错误分类体系的可扩展性，并避免在 ISA 中暴露传输层私有结构。

所有 .try 指令都返回发起状态。所有令牌/事件等待都返回最终异步状态。实现至少必须暴露：错误类别、是否可重试、效果类别（NO_EFFECT、MAYBE_PARTIAL、EXACT_EFFECT）、失败的端点或成员或其不透明位图引用、上下文代次，以及操作序号。诊断时间戳和数据包计数器属于可选的可查询遥测信息，而不是排序机制。

32 位 status 是稳定的体系结构状态类别。status_ref 是对上述更丰富记录的不透明、生命周期有界引用：令牌测试/等待和同步聚合完成等待直接返回它，而事件测试/等待/状态查询返回该事件的聚合引用。引用为零表示状态类别本身已经充分，且不存在详细记录。该记录至少在令牌被回收或事件阶段被清除之前保持有效；若要在此后复制、解码并保留它，则由运行时或驱动程序负责。

10. 指令到 PTX 的映射图例

  • 接近或精确的概念对应： 公开 PTX 直接提供中心操作，其操作数和完成语义高度接近，不过本文提案可能会将其推广到更多上下文或本地地址空间。
  • 部分对应： PTX 只能在指针、multimem、CFT 句柄、数据类型、本地地址空间或完成语义等限制下实现其中一个子集。
  • 无对应/新增： 公开 PTX 9.3 中没有任何指令能够给出完整且与传输层无关的语义，但软件仍然可以使用其他操作组合实现。

映射关系绝不能声称 fabric.submit 等同于 NVSHMEM fence，不能声称 fabric.wait.sync_restrict::reads 等同于 quiet，也不能声称 CQE 或传输层 ACK 自动等同于目标 GPU 可见。这些是彼此不同的体系结构事件。

本附录定义的是语义字段，而不是已经打包的字节偏移。具体 ABI 应发布带版本的打包布局，并明确规定字节序、填充和对齐。遇到未知的必需标志时应拒绝描述符；只有相应版本明确规定可忽略某个建议性标志时，才可以忽略它。

21. 核心状态类别

状态 阶段 重试/效果含义
SUCCESS 任意阶段 请求的动作/观察成功
QUEUE_FULL 发射阶段 可重试；没有产生效果
BAD_QUERY, BAD_GROUP 发射/查询阶段 没有产生效果；选择器或受保护组句柄无效
BAD_ENDPOINT, STALE_HANDLE, NOT_READY 发射阶段 没有产生效果；应按情况刷新或重新创建句柄
BAD_CONTEXT, CONTEXT_CLOSED 发射/等待阶段 没有产生新的效果；需要单独查询在途操作状态
NO_PERMISSION, OUT_OF_BOUNDS, MISALIGNED 发射/异步阶段 保护错误；如果在发射时捕获，通常没有产生效果
UNSUPPORTED_OP, BAD_SIZE, BAD_DESCRIPTOR 发射阶段 没有产生效果；应选择软件降低实现
SCRATCH_TOO_SMALL, UNSUPPORTED_ALGORITHM 集合通信发射阶段 没有产生效果；应增大临时工作区或选择已注册的降低实现
GROUP_MISMATCH, COLL_MISMATCH 发射/异步阶段 集合通信协议错误；效果需要单独报告
EVENT_INVALID, EVENT_BUSY, BAD_TOKEN, LOCAL_LIFETIME 本地阶段 完成/存储生命周期错误
INCOMPATIBLE_EVENT_LEVEL 发射阶段 没有产生效果；事件完成层级下限无法证明所请求的发布条件
DEPENDENCY_FAILED 异步触发器阶段 没有产生信号效果；源事件以错误状态完成
ROUTE_DOWN, REMOTE_RESET, RETRY_EXHAUSTED 异步阶段 可重试性与效果类别记录在状态记录中

仅凭状态类别不足以判断能否重试。软件还必须检查 effect_class，因为在 MAYBE_PARTIAL 之后重放加法、信号加法或归约，可能使数据被重复应用。
